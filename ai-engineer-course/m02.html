Messages API и stateless

Почти все современные LLM API сводятся к одной операции: «вот история диалога, продолжи её». У Anthropic это POST https://api.anthropic.com/v1/messages. Запрос содержит:

  • model — идентификатор модели, например claude-opus-5;
  • max_tokens — жёсткий потолок на длину ответа (не «желаемая длина»: при упоре ответ обрезается и приходит stop_reason: "max_tokens");
  • system — системный промпт: роль, правила, контекст. Отдельное поле, а не сообщение в списке;
  • messages — массив сообщений с ролями user и assistant. Первое — всегда user, роли чередуются;
  • опционально tools, tool_choice, thinking, output_config, metadata, stream.

Каждое сообщение — это не строка, а список content blocks: text, image, document, tool_use, tool_result, thinking. Ответ модели — тоже список блоков плюс stop_reason и usage (сколько токенов на входе, выходе, прочитано и записано в кэш). Эту структуру нужно держать в голове: почти все баги интеграции — это «я думал, что там строка, а там блоки».

API не помнит ничего

Messages API stateless: сервер не хранит диалог между вызовами. Хочешь третью реплику — отправляешь все предыдущие заново. Отсюда следствия, которые определяют архитектуру любого чата:

  • История живёт у вас — в Postgres/Redis, с id сессии. Вы решаете, что в неё попадает, и отвечаете за её обрезку.
  • Каждый ход дороже предыдущего: платите за всю историю на входе. Диалог из 30 ходов по 1 000 токенов — это не 30K, а ≈ 465K входных токенов суммарно (1+2+…+30 тыс.). Лечится prompt caching (ниже) и компакцией истории.
  • Историю можно редактировать: выкинуть старые tool_result, заменить хвост суммаризацией. Но любая правка префикса ломает кэш.
  • Горизонтальное масштабирование бесплатно: любой инстанс вашего сервиса может продолжить любой диалог, если достал историю из хранилища.
Аналогия из GoЭто как HTTP-хэндлер без сессий: всё состояние приходит в запросе или лежит в вашей БД. Модель — чистая функция f(system, tools, messages) → message (с поправкой на недетерминизм). Никаких «соединений с памятью», как у database/sql транзакции.
// Минимальный чат: история на клиенте, каждый ход — полный список сообщений.
package chat

import (
	"context"
	"fmt"
	"strings"

	"github.com/anthropics/anthropic-sdk-go"
)

type Session struct {
	client  anthropic.Client
	system  string
	history []anthropic.MessageParam // в проде — в БД, по session_id
}

func NewSession(system string) *Session {
	return &Session{client: anthropic.NewClient(), system: system} // ключ из ANTHROPIC_API_KEY
}

func (s *Session) Ask(ctx context.Context, userText string) (string, error) {
	s.history = append(s.history, anthropic.NewUserMessage(anthropic.NewTextBlock(userText)))
	resp, err := s.client.Messages.New(ctx, anthropic.MessageNewParams{
		Model:     "claude-opus-5",
		MaxTokens: 16000,
		System:    []anthropic.TextBlockParam{{Text: s.system}},
		Messages:  s.history,
	})
	if err != nil {
		s.history = s.history[:len(s.history)-1] // не оставляем «висящий» user-ход
		return "", fmt.Errorf("messages.new: %w", err)
	}
	s.history = append(s.history, resp.ToParam()) // ответ целиком, со всеми блоками

	var b strings.Builder
	for _, block := range resp.Content {
		if t, ok := block.AsAny().(anthropic.TextBlock); ok {
			b.WriteString(t.Text)
		}
	}
	if resp.StopReason == anthropic.StopReasonMaxTokens {
		return b.String(), fmt.Errorf("ответ обрезан по max_tokens")
	}
	return b.String(), nil
}

client = anthropic.Anthropic()  # ANTHROPIC_API_KEY из окружения
history = []

def ask(text: str) -> str:
    history.append({"role": "user", "content": text})
    resp = client.messages.create(
        model="claude-opus-5",
        max_tokens=16000,
        system="Ты — ассистент поддержки. Отвечай кратко.",
        messages=history,
    )
    history.append({"role": "assistant", "content": resp.content})
    return "".join(b.text for b in resp.content if b.type == "text")

Роли, system prompt и stop_reason

System prompt задаёт «кто ты и по каким правилам работаешь»; модели обучены придавать ему больший вес, чем user-сообщениям, но это приоритет, а не граница безопасности — об этом в модуле 3. В system кладут стабильное (роль, политика, формат), в messages — изменчивое (вопрос, документы конкретного запроса, текущая дата). Это важно и для кэша: всё динамическое в system убивает prompt caching.

Изменения в новых моделях (на момент написания, сентябрь 2026)
  • Prefill (последнее сообщение assistant с началом ответа, трюк «начни с {») на новых моделях Claude возвращает 400. Для формата — structured outputs.
  • temperature/top_p/top_k на Opus 4.7+, Sonnet 5, Fable удалены (400). Глубину и стоимость рассуждения регулируют thinking: {type: "adaptive"} и output_config: {effort: "low|medium|high|xhigh|max"}. На других провайдерах и open-source (vLLM, Ollama) sampling-параметры по-прежнему работают.
  • Старый thinking.budget_tokens на новых моделях отклоняется (400).

Стриминг SSE

Без стриминга пользователь смотрит на спиннер, пока модель не допишет весь ответ: при 80 токенах/с ответ на 800 токенов — это 10 секунд тишины. Со стримингом первые слова появляются через TTFT (time to first token — время до первого токена, обычно сотни миллисекунд – пара секунд; с thinking — дольше, потому что сначала идёт рассуждение). Воспринимаемая скорость определяется TTFT, а не полным временем.

При "stream": true ответ приходит как Server-Sent Events: текстовый поток text/event-stream, где каждое событие — строки event: … и data: {json}, разделённые пустой строкой. Последовательность событий у Anthropic:

event: message_start
data: {"type":"message_start","message":{"id":"msg_01…","role":"assistant","content":[],"usage":{"input_tokens":412,"output_tokens":1}}}

event: content_block_start
data: {"type":"content_block_start","index":0,"content_block":{"type":"text","text":""}}

event: ping
data: {"type":"ping"}

event: content_block_delta
data: {"type":"content_block_delta","index":0,"delta":{"type":"text_delta","text":"Привет"}}

event: content_block_stop
data: {"type":"content_block_stop","index":0}

event: message_delta
data: {"type":"message_delta","delta":{"stop_reason":"end_turn"},"usage":{"output_tokens":57}}

event: message_stop
data: {"type":"message_stop"}
  • content_block_delta бывает трёх видов: text_delta (текст), input_json_delta (кусок JSON аргументов tool_use — копить строку и парсить на content_block_stop), thinking_delta.
  • message_delta несёт финальные stop_reason и usage.output_tokens — метрики стоимости берите отсюда.
  • ping — keepalive, игнорировать. error — ошибка посреди стрима (например overloaded_error) при уже отданном HTTP 200. Статус-код не спасёт, обрабатывайте событие.

Отмена и обрыв соединения

  • Отмена пользователем (закрыл вкладку, нажал «стоп») — закрываете HTTP-соединение, в Go это отмена context. Генерация на стороне API останавливается, но уже сгенерированные выходные токены закладывайте в стоимость. Прокиньте r.Context() из вашего хэндлера до клиента LLM — иначе ушедший пользователь продолжает жечь деньги.
  • Обрыв посреди ответа — поток закончился без message_stop. Это неполный ответ, даже если текст «выглядит законченным». Докачать стрим с места нельзя, а prefill на новых моделях недоступен, так что стратегия одна — повторить запрос целиком (для UI — «перегенерировать»), а частичный текст пометить как оборванный.
  • Прокси и балансировщики: nginx по умолчанию буферизует ответ (proxy_buffering off или заголовок X-Accel-Buffering: no), у ALB/Cloudflare есть idle timeout. Длинный thinking без токенов — ровно тот случай, когда соединение «молчит» и его убивают; ping помогает, но проверьте таймауты по всей цепочке.
  • Большие max_tokens: SDK отказываются делать нестриминговые запросы, которые могут длиться дольше ~10 минут; для топовых моделей с выводом до 128K токенов стриминг фактически обязателен.

Стриминг через Go SDK

// StreamAnswer пишет текст в w по мере генерации, возвращает собранное сообщение.
func StreamAnswer(ctx context.Context, client anthropic.Client, prompt string, w io.Writer) (anthropic.Message, error) {
	start := time.Now()
	var ttft time.Duration

	stream := client.Messages.NewStreaming(ctx, anthropic.MessageNewParams{
		Model:     "claude-opus-5",
		MaxTokens: 64000,
		Messages:  []anthropic.MessageParam{anthropic.NewUserMessage(anthropic.NewTextBlock(prompt))},
	})
	defer stream.Close()

	msg := anthropic.Message{} // у Go-стрима нет GetFinalMessage — аккумулируем сами
	for stream.Next() {
		ev := stream.Current()
		if err := msg.Accumulate(ev); err != nil {
			return msg, fmt.Errorf("accumulate: %w", err)
		}
		if d, ok := ev.AsAny().(anthropic.ContentBlockDeltaEvent); ok {
			if t, ok := d.Delta.AsAny().(anthropic.TextDelta); ok {
				if ttft == 0 {
					ttft = time.Since(start)
				}
				if _, err := io.WriteString(w, t.Text); err != nil {
					return msg, err // клиент ушёл — выходим, defer закроет стрим
				}
				if f, ok := w.(http.Flusher); ok {
					f.Flush()
				}
			}
		}
	}
	if err := stream.Err(); err != nil { // сюда же попадает event: error и обрыв
		return msg, fmt.Errorf("stream: %w", err)
	}
	slog.InfoContext(ctx, "llm stream done",
		"ttft_ms", ttft.Milliseconds(), "total_ms", time.Since(start).Milliseconds(),
		"stop_reason", msg.StopReason, "out_tokens", msg.Usage.OutputTokens)
	return msg, nil
}

import time, anthropic

client = anthropic.Anthropic()

def stream_answer(prompt: str) -> anthropic.types.Message:
    start, ttft = time.monotonic(), None
    with client.messages.stream(
        model="claude-opus-5",
        max_tokens=64000,
        messages=[{"role": "user", "content": prompt}],
    ) as stream:
        for text in stream.text_stream:
            if ttft is None:
                ttft = time.monotonic() - start
            print(text, end="", flush=True)
        msg = stream.get_final_message()
    print(f"\nTTFT={ttft:.2f}s stop={msg.stop_reason} out={msg.usage.output_tokens}")
    return msg

Учебный разбор SSE руками: net/http + bufio

В проде берите SDK. Но один раз написать парсер стоит: станет понятно, что SSE — это просто строки, почему нужен большой буфер у bufio.Scanner и как отличить нормальное завершение от обрыва.

// Учебный SSE-клиент для /v1/messages. В проде используйте SDK.
func RawStream(ctx context.Context, apiKey, prompt string, onText func(string)) (stopReason string, err error) {
	body, _ := json.Marshal(map[string]any{
		"model": "claude-opus-5", "max_tokens": 4096, "stream": true,
		"messages": []map[string]any{{"role": "user", "content": prompt}},
	})
	req, err := http.NewRequestWithContext(ctx, http.MethodPost, "https://api.anthropic.com/v1/messages", bytes.NewReader(body))
	if err != nil {
		return "", err
	}
	req.Header.Set("x-api-key", apiKey)
	req.Header.Set("anthropic-version", "2023-06-01")
	req.Header.Set("content-type", "application/json")

	resp, err := http.DefaultClient.Do(req) // без Timeout: время ограничивает ctx
	if err != nil {
		return "", err
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		b, _ := io.ReadAll(io.LimitReader(resp.Body, 4096))
		return "", fmt.Errorf("status %d (retry-after=%q): %s", resp.StatusCode, resp.Header.Get("retry-after"), b)
	}

	sc := bufio.NewScanner(resp.Body)
	sc.Buffer(make([]byte, 64*1024), 4*1024*1024) // строка data: может быть длинной
	var event string
	gotStop := false
	for sc.Scan() {
		line := sc.Text()
		switch {
		case strings.HasPrefix(line, "event: "):
			event = strings.TrimPrefix(line, "event: ")
		case strings.HasPrefix(line, "data: "):
			var d struct {
				Delta struct {
					Type       string `json:"type"`
					Text       string `json:"text"`
					StopReason string `json:"stop_reason"`
				} `json:"delta"`
				Error struct {
					Type    string `json:"type"`
					Message string `json:"message"`
				} `json:"error"`
			}
			if err := json.Unmarshal([]byte(line[6:]), &d); err != nil {
				return "", fmt.Errorf("bad data for %s: %w", event, err)
			}
			switch event {
			case "content_block_delta":
				if d.Delta.Type == "text_delta" {
					onText(d.Delta.Text)
				}
			case "message_delta":
				stopReason = d.Delta.StopReason
			case "message_stop":
				gotStop = true
			case "error":
				return stopReason, fmt.Errorf("stream error %s: %s", d.Error.Type, d.Error.Message)
			}
		}
	}
	if err := sc.Err(); err != nil {
		return stopReason, err // включая context.Canceled
	}
	if !gotStop {
		return stopReason, io.ErrUnexpectedEOF // поток кончился без message_stop — ответ неполный
	}
	return stopReason, nil
}
Метрики стриминга, которые стоит писатьTTFT, общее время, выходные токены/сек (output_tokens / (total − ttft)), stop_reason, число оборванных стримов. TTFT растёт с длиной входа (prefill — обработка промпта) и падает при попадании в prompt cache: это одна из главных причин кэшировать.

Structured output

LLM отдаёт текст, а вашему коду нужна структура. Эволюция подходов, от худшего к лучшему:

  1. «Ответь в JSON» в промпте + парсинг. Работает в 95–99% случаев, и эти 1–5% — markdown-обёртка ```json, пояснение перед JSON, лишняя запятая, обрезка по max_tokens.
  2. Prefill (начать ответ за модель с {). На новых моделях Claude запрещён — 400.
  3. Tool use как экстрактор: описать инструмент record_ticket со схемой и попросить модель его вызвать. Аргументы — JSON по схеме.
  4. Structured outputs — constrained decoding: сервер ограничивает генерацию так, что невалидный по схеме JSON просто не может быть сгенерирован. У Anthropic: output_config: {format: {type: "json_schema", schema: {…}}} для ответа и strict: true у инструмента для аргументов tool_use.

Нюансы structured outputs, которые отличают сеньора:

  • Схема ограничена: поддерживаются базовые типы, enum, const, anyOf, $ref, форматы строк (date, email, uuid…), обязательный additionalProperties: false. Не поддерживаются рекурсивные схемы, minimum/maximum, minLength/maxLength. Python/TS SDK выкидывают неподдерживаемые ограничения из схемы и проверяют их на клиенте; в Go это ваша работа.
  • Гарантия синтаксиса ≠ гарантия смысла. Схема обещает, что priority — один из p1|p2|p3, но не то, что он выбран правильно. Бизнес-валидацию (сумма ≥ 0, дата не в будущем, id существует в БД) делаете сами.
  • Исключения: при stop_reason: "max_tokens" JSON обрезан, при "refusal" может не соответствовать схеме. Проверяйте stop_reason до парсинга.
  • Первый запрос с новой схемой медленнее — схема компилируется в грамматику, дальше кэшируется (порядка суток). Не генерируйте схему динамически на каждый запрос.
  • Несовместимо с prefill и citations; совместимо с batch, стримингом, thinking.

Паттерн «валидация + повтор с ошибкой»: если ответ не прошёл бизнес-валидацию, добавьте ответ модели в историю и следующим user-сообщением отдайте текст ошибки. Модель чинит конкретную проблему лучше, чем при слепом повторе. Лимит — 2–3 попытки, дальше ошибка наверх и метрика.

type Ticket struct {
	Category string `json:"category"`
	Priority string `json:"priority"`
	Summary  string `json:"summary"`
	OrderID  string `json:"order_id"`
}

var ticketSchema = map[string]any{
	"type": "object",
	"properties": map[string]any{
		"category": map[string]any{"type": "string", "enum": []string{"billing", "bug", "delivery", "other"}},
		"priority": map[string]any{"type": "string", "enum": []string{"p1", "p2", "p3"}},
		"summary":  map[string]any{"type": "string"},
		"order_id": map[string]any{"type": "string"},
	},
	"required":             []string{"category", "priority", "summary", "order_id"},
	"additionalProperties": false,
}

var orderRe = regexp.MustCompile(`^(ORD-\d{6})?$`)

// Validate — то, что схема выразить не может (maxLength, формат id, бизнес-правила).
func (t Ticket) Validate() error {
	if n := utf8.RuneCountInString(t.Summary); n == 0 || n > 200 {
		return fmt.Errorf("summary: длина %d, нужно 1..200 символов", n)
	}
	if !orderRe.MatchString(t.OrderID) {
		return fmt.Errorf("order_id %q: ожидается ORD-NNNNNN или пустая строка", t.OrderID)
	}
	return nil
}

func ExtractTicket(ctx context.Context, c anthropic.Client, text string) (Ticket, error) {
	msgs := []anthropic.MessageParam{anthropic.NewUserMessage(anthropic.NewTextBlock(
		"Разбери обращение клиента в тикет.\n<message>\n" + text + "\n</message>"))}
	var lastErr error
	for attempt := 0; attempt < 3; attempt++ {
		resp, err := c.Messages.New(ctx, anthropic.MessageNewParams{
			Model: "claude-sonnet-5", MaxTokens: 1024, Messages: msgs,
			OutputConfig: anthropic.OutputConfigParam{
				Format: anthropic.JSONOutputFormatParam{Schema: ticketSchema},
			},
		})
		if err != nil {
			return Ticket{}, err // сетевые/429 ретраит слой ниже, здесь — только логика
		}
		switch resp.StopReason {
		case anthropic.StopReasonMaxTokens, anthropic.StopReasonRefusal:
			return Ticket{}, fmt.Errorf("no valid output: stop_reason=%s", resp.StopReason)
		}
		var raw strings.Builder
		for _, b := range resp.Content {
			if t, ok := b.AsAny().(anthropic.TextBlock); ok {
				raw.WriteString(t.Text)
			}
		}
		var t Ticket
		if lastErr = json.Unmarshal([]byte(raw.String()), &t); lastErr == nil {
			if lastErr = t.Validate(); lastErr == nil {
				return t, nil
			}
		}
		// Повтор с конкретной ошибкой: модель видит свой ответ и что в нём не так.
		msgs = append(msgs, resp.ToParam(), anthropic.NewUserMessage(anthropic.NewTextBlock(
			"Ответ не прошёл валидацию: "+lastErr.Error()+". Верни исправленный JSON целиком.")))
	}
	return Ticket{}, fmt.Errorf("ticket invalid after retries: %w", lastErr)
}

Tool use

Tool use (он же function calling) — модель не выполняет код, она просит вас выполнить функцию. Вы передаёте в tools описания: имя, текстовое описание, JSON Schema входа. Модель отвечает блоками tool_use (id, name, input) и stop_reason: "tool_use". Вы исполняете, кладёте результаты в user-сообщение блоками tool_result с тем же tool_use_id и снова зовёте API. Цикл продолжается до end_turn.

  • Параллельные вызовы: в одном ответе может быть несколько tool_use. Выполняйте их конкурентно и возвращайте все результаты одним user-сообщением. Разнести их по нескольким сообщениям — частая ошибка, которая приучает модель вызывать по одному инструменту за ход (медленнее) или ломает валидацию.
  • Ошибки инструмента — это данные, а не исключения: tool_result с is_error: true и понятным текстом («заказ не найден», «таймаут, попробуйте через минуту»). Модель адаптируется: переформулирует запрос, спросит пользователя. Падать всем циклом из-за одного инструмента — плохо.
  • Защита цикла: лимит итераций, общий дедлайн через context, таймаут на инструмент, лимит размера результата (100 КБ логов в tool_result — это деньги и деградация внимания).
  • tool_choice: auto (по умолчанию), none, any/tool (принудительный вызов). На Fable 5.1 и Opus 5.5 принудительные режимы возвращают 400 — используйте auto + явную инструкцию в промпте + strict: true, либо structured outputs, если вызов был нужен только ради JSON.
  • Перед исполнением проверяйте stop_reason: при max_tokens аргументы могут быть обрезанным, но синтаксически валидным JSON; при refusal не исполняйте инструменты этого хода.

Цикл tool calling по шагам

Клиент ↔ модель ↔ инструменты. Запрос «Погода в Берлине и Париже и есть ли билеты на завтра?» — три параллельных вызова, один из них падает по таймауту, модель переспрашивает инструмент с другими параметрами.

Проектирование описаний инструментов

Модель выбирает инструмент и заполняет аргументы только по описанию. Описание инструмента — это промпт, и к нему применимы все правила промпт-инжиниринга:

  • Имя — глагол + объект: search_orders, а не orders или tool1.
  • Описание на 3–5 предложений: что делает, когда вызывать и когда не вызывать, что возвращает, ограничения («ищет только за последние 90 дней»).
  • Описания полей с форматом и примером: "date": "YYYY-MM-DD, по часовому поясу пользователя". Enum вместо свободной строки, где возможно.
  • Меньше, но крупнее: 5 хорошо различимых инструментов лучше 40 пересекающихся. Два инструмента с похожими описаниями — источник случайного выбора. При десятках инструментов — tool search или маршрутизация по подмножествам.
  • Результат — для модели, а не для машины: верните компактный, читаемый текст/JSON с нужными полями, а не сырой ответ внутреннего API на 5 000 токенов. Ошибки — с подсказкой, что делать дальше.
  • Идемпотентность и подтверждение: инструменты с побочными эффектами (оплата, отправка письма) — с ключом идемпотентности и, для рискованных, подтверждением человеком. Модель может повторить вызов.

Tool loop с параллельным выполнением на errgroup

В Go SDK есть бета toolrunner (client.Beta.Messages.NewToolRunner), который крутит цикл сам. Ручной цикл нужен, когда хотите контроль: параллельность, таймауты по инструменту, аудит, human-in-the-loop. Вот он:

type ToolFunc func(ctx context.Context, input json.RawMessage) (string, error)

func RunTools(ctx context.Context, c anthropic.Client, tools []anthropic.ToolUnionParam,
	impl map[string]ToolFunc, msgs []anthropic.MessageParam) (string, error) {

	for turn := 0; turn < 10; turn++ { // лимит итераций — защита от зацикливания
		resp, err := c.Messages.New(ctx, anthropic.MessageNewParams{
			Model: "claude-opus-5", MaxTokens: 16000, Tools: tools, Messages: msgs,
		})
		if err != nil {
			return "", err
		}
		msgs = append(msgs, resp.ToParam()) // ответ модели — в историю ДО tool_result

		if resp.StopReason != anthropic.StopReasonToolUse {
			var sb strings.Builder
			for _, b := range resp.Content {
				if t, ok := b.AsAny().(anthropic.TextBlock); ok {
					sb.WriteString(t.Text)
				}
			}
			return sb.String(), nil
		}

		var calls []anthropic.ToolUseBlock
		for _, b := range resp.Content {
			if tu, ok := b.AsAny().(anthropic.ToolUseBlock); ok {
				calls = append(calls, tu)
			}
		}
		results := make([]anthropic.ContentBlockParamUnion, len(calls)) // порядок = порядок вызовов
		g, gctx := errgroup.WithContext(ctx)
		g.SetLimit(4) // не больше 4 инструментов одновременно
		for i, call := range calls {
			g.Go(func() error {
				out, err := runOne(gctx, impl, call)
				if err != nil { // ошибка инструмента — данные для модели, а не падение цикла
					results[i] = anthropic.NewToolResultBlock(call.ID, "error: "+err.Error(), true)
					return nil
				}
				results[i] = anthropic.NewToolResultBlock(call.ID, out, false)
				return nil
			})
		}
		_ = g.Wait() // горутины всегда возвращают nil; отмену ctx поймает следующий Messages.New
		msgs = append(msgs, anthropic.NewUserMessage(results...)) // ВСЕ результаты одним сообщением
	}
	return "", errors.New("tool loop: превышен лимит итераций")
}

func runOne(ctx context.Context, impl map[string]ToolFunc, call anthropic.ToolUseBlock) (string, error) {
	fn, ok := impl[call.Name]
	if !ok {
		return "", fmt.Errorf("неизвестный инструмент %q", call.Name)
	}
	ctx, cancel := context.WithTimeout(ctx, 15*time.Second)
	defer cancel()
	out, err := fn(ctx, json.RawMessage(call.JSON.Input.Raw()))
	if len(out) > 20_000 { // ponytail: обрезка по байтам; лучше — суммаризация/пагинация в самом инструменте
		out = out[:20_000] + "\n…[обрезано]"
	}
	return out, err
}

import asyncio, json, anthropic

client = anthropic.AsyncAnthropic()

async def run_tools(tools, impl, messages):
    for _ in range(10):
        resp = await client.messages.create(
            model="claude-opus-5", max_tokens=16000, tools=tools, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text")

        calls = [b for b in resp.content if b.type == "tool_use"]

        async def one(call):
            try:
                out = await asyncio.wait_for(impl[call.name](**call.input), timeout=15)
                return {"type": "tool_result", "tool_use_id": call.id, "content": str(out)}
            except Exception as e:  # ошибка — модели, а не наверх
                return {"type": "tool_result", "tool_use_id": call.id,
                        "content": f"error: {e}", "is_error": True}

        results = await asyncio.gather(*(one(c) for c in calls))
        messages.append({"role": "user", "content": list(results)})
    raise RuntimeError("tool loop: превышен лимит итераций")
Почему errgroup, а ошибки не возвращаемerrgroup.WithContext отменяет контекст при первой ошибке — это правильно для «всё или ничего», но не для инструментов: таймаут погоды не должен убивать поиск билетов. Поэтому горутины возвращают nil, а ошибку кладут в tool_result с is_error. От errgroup остаются SetLimit (семафор) и аккуратный Wait. Запись в results[i] по индексу без мьютекса безопасна: каждая горутина пишет в свою ячейку.

Prompt caching

Большая часть входа повторяется между запросами: одни и те же tools, system prompt, документы, растущая история диалога. Prompt caching позволяет не обрабатывать этот префикс заново: сервер сохраняет вычисленное состояние (KV-cache из модуля 1) и при следующем запросе с тем же префиксом читает его.

  • Это совпадение префикса байт в порядке tools → system → messages. Любое изменение в позиции N инвалидирует всё после N.
  • Breakpoints: cache_control: {type: "ephemeral"} на блоке помечает «закэшируй префикс до этого места». До 4 breakpoint'ов на запрос. Есть и автоматический вариант — top-level cache_control, который ставит маркер на последний кэшируемый блок.
  • Экономика (на момент написания): чтение ≈ 0.1× цены input (у Opus 5.5 — 0.05×, у Fable 5.1 — 0.025×; по состоянию на октябрь 2026); запись 1.25× (TTL 5 минут) или 2× (TTL 1 час). Запись с 5-минутным TTL окупается уже на первом попадании: 1.25 + 0.1 < 2. TTL продлевается при каждом чтении.
  • Латентность: попадание в кэш сокращает TTFT на длинных промптах в разы — prefill 100K токенов не бесплатен.
  • Минимальный размер префикса зависит от модели (512–4096 токенов). Короче — кэш молча не создаётся, без ошибки: cache_creation_input_tokens: 0.
  • Проверка: usage.cache_read_input_tokens и usage.cache_creation_input_tokens. Если чтения нулевые при одинаковых запросах — где-то тихий инвалидатор.

Визуализатор prompt caching

Запрос — это последовательность блоков. Флажки между блоками — breakpoints (клик по флажку включает/выключает). «Изменить» имитирует правку блока относительно прошлого запроса: всё после неё перезаписывается. Зелёное — чтение кэша, оранжевое — запись, серое — обычный input.

Batch API

Message Batches (/v1/messages/batches) — асинхронная обработка пачки запросов со скидкой 50%. Вы отправляете до десятков тысяч запросов, каждый с вашим custom_id; обработка занимает до 24 часов (обычно заметно быстрее); результаты приходят в произвольном порядке — матчите по custom_id, не по индексу.

  • Когда: всё, где пользователь не ждёт — ночная разметка, прогон evals, обогащение каталога, генерация эмбеддинг-описаний, переобработка архива после смены промпта.
  • Когда нет: интерактив, цепочки, где следующий шаг зависит от предыдущего (каждый шаг — отдельный батч и сутки ожидания в худшем случае).
  • Частичные сбои: у каждого результата свой статус (succeeded, errored, canceled, expired). Повторная отправка — только упавших, по custom_id. Делайте custom_id детерминированным (id записи + версия промпта), тогда повтор идемпотентен.
  • Скидки складываются с prompt caching, но попадания в кэш внутри батча не гарантированы.
import anthropic
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming

                model="claude-haiku-4-5", max_tokens=512,
                system=CLASSIFY_PROMPT,

Каскады и routing

  • Routing: дешёвый классификатор (Haiku или даже не-LLM модель) определяет тип/сложность запроса и отправляет на подходящую модель. Ошибка роутера — главный риск: сложный запрос на слабой модели. Измеряйте качество по сегментам.
  • Каскад: сначала дешёвая модель; если её ответ не прошёл проверку (валидация схемы, self-check, низкая уверенность, отказ) — эскалация на сильную. Хорошо работает, когда проверка дешевле генерации и есть объективный критерий.
  • Fallback по доступности: при 529/5xx — другая модель или другой провайдер/регион (модуль 9). Промпты при этом могут вести себя по-разному — прогоняйте evals на fallback-модели тоже.

Калькулятор: модель × кэш × batch × routing

Месячная стоимость (30 дней) при ваших объёмах. Промахи кэша считаются как запись (1.25×). Роутинг отправляет долю трафика на Haiku 4.5, остальное — на выбранную модель.

Мультимодальность

Claude принимает изображения (image-блоки: base64, URL или file_id из Files API) и PDF (document-блоки). PDF обрабатывается и как текст, и как картинки страниц — поэтому модель видит таблицы, графики и сканы, но и платите вы за оба представления.

  • Стоимость картинки зависит от площади в пикселях, а не от «информативности»: порядка одного токена на патч 28×28 px. Изображение 1280×720 — около 1 200 токенов; большие картинки сервер уменьшает сам, но вы платите за передачу и ждёте. Даунскейльте на клиенте до того, что нужно задаче: для классификации фото товара хватит 512 px, для чтения мелкого текста на скриншоте — нет.
  • PDF: каждая страница стоит текст + изображение, то есть порядка тысяч токенов на страницу. Отчёт на 100 страниц — это сотни тысяч токенов. Для больших документов — извлечь текст сами, отправлять только нужные страницы, кэшировать документ (cache_control на document-блоке).
  • Порядок: изображения/документы ставьте до вопроса о них.
  • Режимы отказа: модель уверенно «читает» размытый текст (галлюцинация OCR), путает оси графиков, плохо считает объекты. Для критичных цифр — сверка с текстовым источником или structured output с полем уверенности.
pdf, err := os.ReadFile("invoice.pdf")
if err != nil {
	return err
}
msg := anthropic.NewUserMessage(
	anthropic.NewDocumentBlock(anthropic.Base64PDFSourceParam{Data: base64.StdEncoding.EncodeToString(pdf)}),
	anthropic.NewTextBlock("Извлеки номер счёта, дату и итоговую сумму."),
)
// Картинки — аналогично image-блоком (base64/URL); для повторного использования — Files API.

Что сказать на собесеГлавная концептуальная разница — где живёт состояние. Stateless API проще масштабировать и аудировать, всё под вашим контролем, но вы платите за историю и сами её обрезаете. Серверное состояние (Responses) экономит трафик и код, но это vendor lock-in и вопросы к хранению данных. Для абстракции над провайдерами (LLM-gateway) внутренний формат обычно ближе к блокам Anthropic/items Responses, потому что плоская строка не выражает tool calls и мультимодальность.

КодТипРетраить?Что это

529overloaded_errorДа, backoff; думать о fallbackAPI перегружен целиком — это не ваш лимит, а общая нагрузка
  • 429 vs 529: 429 — ваша квота (смотрите заголовки retry-after и anthropic-ratelimit-*, сглаживайте трафик, client-side rate limiter). 529 — перегрузка провайдера: ретраи помогают, но при затяжной перегрузке нужен fallback на другую модель/регион.
  • SDK ретраит сам: по умолчанию 2 повтора с экспоненциальным backoff для 408/409/429/5xx. Если строите свой слой ретраев — отключите встроенный (option.WithMaxRetries(0)), иначе получите 3 × 3 = 9 попыток и retry storm.
  • Backoff с jitter: без случайного разброса все ваши воркеры ретраят синхронно и снова ловят 429. Full jitter: sleep = rand(0, min(cap, base·2^n)). Если есть retry-after — он главнее формулы.
  • Бюджет ретраев: ограничивайте общее время через context, а при массовых ошибках — circuit breaker, чтобы не добивать лежащий сервис.
  • Идемпотентность: сам вызов LLM «идемпотентен» (без побочных эффектов), но ретрай стоит денег, а ответ будет другим. Ретраить tool с побочным эффектом — только с ключом идемпотентности.
// Клиент без встроенных ретраев — политику задаём сами.
var client = anthropic.NewClient(option.WithMaxRetries(0))

func WithRetry[T any](ctx context.Context, attempts int, fn func(context.Context) (T, error)) (T, error) {
	var zero T
	for n := 0; ; n++ {
		v, err := fn(ctx)
		if err == nil {
			return v, nil
		}
		delay, retryable := classify(err, n)
		if !retryable || n+1 >= attempts {
			return zero, err
		}
		slog.WarnContext(ctx, "llm retry", "attempt", n+1, "delay", delay, "err", err)
		t := time.NewTimer(delay)
		select {
		case <-t.C:
		case <-ctx.Done():
			t.Stop()
			return zero, errors.Join(err, ctx.Err())
		}
	}
}

func classify(err error, n int) (time.Duration, bool) {
	backoff := min(30*time.Second, 500*time.Millisecond<<n)
	delay := rand.N(backoff) + 100*time.Millisecond // full jitter

	var apierr *anthropic.Error
	if errors.As(err, &apierr) {
		switch s := apierr.StatusCode; {
		case s == 408, s == 409, s == 429, s == 529, s >= 500:
			if apierr.Response != nil {
				if ra, err := strconv.Atoi(apierr.Response.Header.Get("retry-after")); err == nil {
					delay = time.Duration(ra) * time.Second // сервер знает лучше
				}
			}
			return delay, true
		default:
			return 0, false // 400/401/403/404/413 — повтор не поможет
		}
	}
	if errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
		return 0, false
	}
	var ne net.Error
	if errors.As(err, &ne) || errors.Is(err, io.ErrUnexpectedEOF) {
		return delay, true // сеть, обрыв стрима
	}
	return 0, false
}

Самопроверка

Почему 30-й ход диалога стоит дороже первого, и что с этим делать?

API stateless: на каждом ходу отправляется вся история, и вы платите за неё как за input. Суммарные входные токены растут квадратично по числу ходов. Лечится prompt caching (история читается за 0.1×), компакцией/суммаризацией старой части, обрезкой больших tool_result и выносом больших документов в кэшируемый префикс.

Поток закончился, текст выглядит законченным, но message_stop не пришёл. Что делать?

Считать ответ неполным: нет гарантии, что это конец, и нет stop_reason/финального usage. Возобновить стрим нельзя, prefill на новых моделях запрещён — повторить запрос целиком (с ретрай-политикой), частичный ответ пометить как оборванный.

Модель вернула три tool_use. Как правильно вернуть результаты?

Выполнить конкурентно, собрать три tool_result с соответствующими tool_use_id и отправить их одним user-сообщением сразу после assistant-сообщения с этими tool_use. Упавший инструмент — is_error: true с понятным текстом, а не исключение на весь цикл.

Structured outputs гарантируют валидный JSON. Зачем тогда валидация на клиенте?

Гарантирована форма, а не смысл: значения могут быть неправильными, бизнес-правила (формат id, диапазоны, существование в БД) схема не выражает — minLength, minimum и т.п. не поддерживаются. Плюс при max_tokens и refusal гарантия не действует.

В system prompt добавили строку «Текущее время: …». Что сломалось?

Prompt caching: system стоит в начале префикса, а время меняется каждый запрос — байты префикса не совпадают, и всё после tools перестаёт кэшироваться. Время надо перенести в user-сообщение (после последнего breakpoint) или округлить до дня, если это допустимо.

Когда 1-часовой TTL кэша выгоднее 5-минутного?

Запись 2× против 1.25×. 1h выгоден, когда запросы с тем же префиксом приходят реже раза в 5 минут, но чаще раза в час (иначе 5-минутный кэш каждый раз протухает и вы платите запись снова), например редкий трафик внутреннего инструмента или агент, который думает дольше 5 минут между ходами.

Чем 429 отличается от 529 с точки зрения реакции системы?

429 — вы превысили свои лимиты: сглаживать трафик, соблюдать retry-after, клиентский rate limiter, приоритезация. 529 — провайдер перегружен целиком: backoff помогает на коротких всплесках, при затяжных — fallback на другую модель или провайдера, деградация функциональности.

Результаты batch пришли в другом порядке. Как их сопоставить и как повторить упавшие?

По custom_id, который вы задали для каждого запроса. Делайте его детерминированным (id записи + версия промпта): тогда повторная отправка только упавших (errored/expired) идемпотентна и легко дедуплицируется.

Вопросы с собеседований

Спроектируйте слой интеграции с LLM API для продукта с 50 RPS. Что в нём будет?

Тонкая обёртка над SDK со следующими ответственностями: (1) единая модель запроса/ответа с блоками, версией промпта и маршрутом; (2) ретраи с jitter и учётом retry-after, встроенные ретраи SDK отключены; бюджет по времени через context; circuit breaker на провайдера; (3) клиентский rate limiter по RPM и TPM (токены оценивать заранее), очередь с приоритетами для фоновых задач; (4) fallback-цепочка моделей/провайдеров с отдельными evals; (5) prompt caching: стабильный префикс, мониторинг hit rate; (6) observability: трейс на вызов с моделью, версией промпта, токенами (input/output/cache), стоимостью, TTFT, stop_reason; (7) стриминг до клиента с отменой по context; (8) лимиты стоимости на пользователя/тенанта. Оценка: 50 RPS × 3K input токенов — это 9M input токенов в минуту, надо сразу смотреть на TPM-лимиты и кэш.

Как бы вы реализовали tool use с 3 параллельными вызовами, где один — медленный внешний API?

Конкурентное выполнение (errgroup с SetLimit), таймаут на каждый инструмент, общий дедлайн цикла. Упавший или просроченный инструмент возвращает tool_result с is_error: true и подсказкой — модель решит, что делать; остальные результаты не теряются. Все результаты — одним user-сообщением. Если медленный API частый — кэш результатов, асинхронный инструмент (запустил задачу, вернул id, отдельный инструмент для статуса) или предзагрузка. Побочные эффекты — с ключом идемпотентности, потому что модель может повторить вызов.

У вас стоимость LLM выросла втрое за месяц без роста трафика. Как будете искать причину?

Разложить стоимость по измерениям из телеметрии: маршрут/фича, модель, версия промпта, input vs output vs cache write vs cache read. Типичные причины: (1) упал cache hit rate — кто-то добавил динамику в system или поменял набор tools (сравнить payload двух соседних запросов); (2) выросла длина ответа — новая модель/промпт стали многословнее, или thinking/effort подняли; (3) растущие истории без компакции; (4) ретраи/зацикленные агенты — число вызовов на пользовательский запрос; (5) переключение fallback на дорогую модель. Лечить с метриками «стоимость на успешную задачу», а не на запрос.

JSON mode, tool use как экстрактор, structured outputs — что и когда выбрать?

Structured outputs (constrained decoding по схеме) — дефолт для извлечения данных: гарантирует синтаксис и соответствие схеме, не нужен парсер-чинильщик. Strict tools — когда модель должна выбирать действия и аргументы должны быть валидны. «Просто попросить JSON» — только для прототипа или провайдеров без поддержки, с устойчивым парсером и повтором. В любом варианте — бизнес-валидация, обработка max_tokens/refusal и повтор с текстом ошибки. Минусы constrained decoding: ограниченное подмножество JSON Schema, компиляция схемы на первом запросе.

Объясните prompt caching так, чтобы стало понятно, почему порядок блоков важен.

Сервер кэширует вычисленное внутреннее состояние модели (KV-cache) для префикса запроса. Префикс определён порядком tools → system → messages, ключ — точные байты до breakpoint'а. Трансформер обрабатывает токены слева направо, и состояние каждого зависит от всех предыдущих — поэтому изменение в середине делает невалидным всё справа, а изменение в конце — ничего. Значит: стабильное в начало (tools, политика, большие документы), изменчивое в конец. Экономика: чтение 0.1×, запись 1.25× (5 мин) или 2× (1 ч); плюс сильное снижение TTFT на длинных промптах. Мониторить cache_read_input_tokens.

Когда Batch API — плохая идея, даже если скидка 50%?

Когда нужен ответ пользователю в интерактиве; когда шаги зависят друг от друга (цепочка из 5 батчей = до 5 суток в худшем случае); когда SLA на обработку короче 24 часов и нет запасного синхронного пути; когда объём маленький и сложность оркестрации (опрос статуса, частичные сбои, повторы) дороже экономии. Хорошее применение — ночные переобработки, evals, разметка, обогащение каталога.

Стримим ответ пользователю, а посреди стрима пришёл overloaded_error. Как это обработать в продукте?

HTTP-статус уже 200, поэтому ошибка приходит событием error — его надо обрабатывать явно. Частичный ответ нельзя «докачать»: повторить запрос целиком с backoff, возможно на fallback-модели; в UI либо заменить частичный текст новым (с индикацией «перегенерируем»), либо показать ошибку с кнопкой повтора. Логировать как оборванный стрим, учитывать сгенерированные токены в стоимости. Если частые обрывы — смотреть на прокси/таймауты и на долю 529 по модели.

Как выбрать модель для новой фичи, не угадывая?

Собрать eval-набор 50–200 примеров с критериями, прогнать 2–3 модели (и 2–3 уровня effort) и построить фронт Парето: качество vs стоимость на задачу vs p95 латентности. Выбрать самую дешёвую, проходящую порог качества с запасом. Рассмотреть каскад (дешёвая модель + проверка + эскалация) и роутинг по сегментам. Пересматривать при выходе новых моделей — evals делают это часовой задачей, а не проектом.
