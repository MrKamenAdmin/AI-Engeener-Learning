Зачем Go-разработчику Python

Прод-сервис вокруг LLM вполне можно и стоит писать на Go: вызов API, стриминг, лимиты, очереди, RAG на pgvector — всё это Go делает отлично, и у Anthropic есть официальный Go SDK. Но часть работы живёт в Python, и притворяться, что её нет, дорого:

Модули и пакеты

В Go пакет = директория, модуль = go.mod. В Python модуль = файл .py, пакет = директория (исторически с __init__.py), а «проект» описывается pyproject.toml. Импорты разрешаются через sys.path, а не через путь модуля, поэтому классическая боль — «работает из корня, не работает из поддиректории». Лечится src-layout и установкой проекта в окружение в editable-режиме (uv делает это сам). Экспорт не по регистру, а по соглашению: _name — «приватное», но доступно всем.

Типы и dataclass vs struct

Python динамически типизирован, аннотации (def f(x: int) -> str) интерпретатор не проверяет. Проверку делает внешний тайпчекер (mypy, pyright), и в команде с Go-культурой его стоит включить в CI со строгим режимом. @dataclass — ближайший аналог struct: поля, конструктор, сравнение. Но он не валидирует значения: User(age="десять") создастся спокойно. Для данных с границы доверия (JSON от клиента, ответ модели) нужен pydantic.

Исключения vs error

Нет if err != nil, ошибки летят исключениями вверх по стеку, пока их не поймают. Для Go-разработчика это ощущается как паника, которую принято ловить. Правила хорошего тона: ловить конкретные классы (except anthropic.RateLimitError), а не голый except Exception; не глотать молча; оборачивать с сохранением причины: raise MyError("…") from e (аналог fmt.Errorf("…: %w", err), цепочка видна в traceback). Ресурсы закрывает with (context manager) — это defer, привязанный к блоку, а не к функции.

Окружение: uv, venv, pyproject

Главная боль Python для гоферов — окружения. В Go зависимости изолированы модулем и собираются в бинарь. В Python пакеты ставятся в интерпретатор, поэтому на каждый проект нужен venv (virtual environment — отдельная директория с копией/ссылкой на интерпретатор и своими site-packages). Исторический зоопарк: pip, virtualenv, pip-tools, poetry, pipenv, conda, pyenv. В 2026 году разумный дефолт один — uv от Astral: менеджер версий Python, venv, зависимостей и lock-файла в одном быстром бинаре (он написан на Rust).

async/await vs goroutines

Самое важное концептуальное различие. В Go конкурентность прозрачна: любая функция может быть запущена в горутине, рантайм сам переключает их на блокирующих вызовах, горутины реально работают параллельно на всех ядрах. В Python asyncio — кооперативная многозадачность в одном потоке:

  • Функция должна быть объявлена async def, и вызывать её нужно через await. Это «окрашивание функций»: async заражает весь стек вызовов вверх.
  • Переключение происходит только в точках await. Синхронный блокирующий вызов внутри корутины (requests.get, time.sleep, синхронный клиент БД, тяжёлый CPU-код) останавливает весь event loop: все остальные запросы сервиса ждут. Это самая частая прод-ошибка в FastAPI-сервисах.
  • Параллелизма на CPU нет из-за GIL (Global Interpreter Lock). Для I/O-bound LLM-вызовов это не важно: тысячи одновременных запросов в одном потоке — нормально. Для CPU-задач — процессы (ProcessPoolExecutor) или нативные библиотеки (numpy, pandas отпускают GIL внутри). Free-threaded сборка CPython без GIL существует с 3.13, но экосистема к ней ещё привыкает.
  • Каналов как примитива языка нет; есть asyncio.Queue. Отмена — не context, а task.cancel(), которое бросает CancelledError в точке await; таймаут — asyncio.timeout().
import asyncio
import anthropic

client = anthropic.AsyncAnthropic()  # у SDK есть sync и async клиенты — в async-коде только async

async def classify(ticket: str) -> str:
    resp = await client.messages.create(
        model="claude-haiku-4-5",
        max_tokens=16,
        system="Ответь одним словом: billing, tech, refund или other.",
        messages=[{"role": "user", "content": ticket}],
    )
    return resp.content[0].text.strip()

async def main(tickets: list[str]) -> list[str | BaseException]:
    sem = asyncio.Semaphore(10)

    async def guarded(t: str) -> str:
        async with sem:
            return await classify(t)

    # gather(return_exceptions=True) ≈ errgroup без fail-fast: ошибки возвращаются значениями
    return await asyncio.gather(*(guarded(t) for t in tickets), return_exceptions=True)

# Ошибка, которую ловят на ревью:
async def bad_handler() -> None:
    import time
    time.sleep(2)             # блокирует ВЕСЬ event loop на 2 с
    await asyncio.sleep(2)    # правильно: отдаёт управление другим задачам
    # синхронную библиотеку без async-версии — в поток:
    # result = await asyncio.to_thread(sync_call, arg)

if __name__ == "__main__":
    print(asyncio.run(main(["Не прошла оплата картой", "Приложение падает при входе"])))

// То же на Go: никакой «окраски» функций, блокирующий вызов блокирует только свою горутину.
func classifyAll(ctx context.Context, client *anthropic.Client, tickets []string) ([]string, []error) {
	out := make([]string, len(tickets))
	errs := make([]error, len(tickets))
	var g errgroup.Group
	g.SetLimit(10)
	for i, t := range tickets {
		g.Go(func() error {
			resp, err := client.Messages.New(ctx, anthropic.MessageNewParams{
				Model:     "claude-haiku-4-5",
				MaxTokens: 16,
				System:    []anthropic.TextBlockParam{{Text: "Ответь одним словом: billing, tech, refund или other."}},
				Messages:  []anthropic.MessageParam{anthropic.NewUserMessage(anthropic.NewTextBlock(t))},
			})
			if err != nil {
				errs[i] = err // без fail-fast, как gather(return_exceptions=True)
				return nil
			}
			for _, b := range resp.Content {
				if tb, ok := b.AsAny().(anthropic.TextBlock); ok {
					out[i] = strings.TrimSpace(tb.Text)
				}
			}
			return nil
		})
	}
	_ = g.Wait()
	return out, errs
}
Аналогии, которые работают

asyncio.TaskGroup (3.11+) ≈ errgroup.WithContext: первая ошибка отменяет остальные задачи, выход из блока ждёт всех. asyncio.gather(..., return_exceptions=True) ≈ errgroup, где горутины пишут ошибку в срез и возвращают nil. asyncio.Semaphore ≈ semaphore.Weighted с весом 1. asyncio.timeout(s) ≈ context.WithTimeout, только область действия — блок async with, а не переданный вниз объект.

Pydantic: типы на границе доверия

Pydantic — библиотека моделей данных с валидацией в рантайме. Для AI engineering это центральный инструмент: FastAPI строит на нём валидацию запросов и OpenAPI, а для LLM он делает три вещи — описывает схему ожидаемого ответа, генерирует из неё JSON Schema для structured outputs и валидирует то, что модель вернула. В Go ближайший аналог — struct с тегами json + validate плюс генерация схемы через invopop/jsonschema; в Python это одна библиотека.

from typing import Literal
import anthropic
from pydantic import BaseModel, Field, ValidationError

class TicketTriage(BaseModel):
    category: Literal["billing", "tech", "refund", "other"]
    urgency: int = Field(ge=1, le=5, description="1 — не срочно, 5 — всё горит")
    summary: str = Field(max_length=200)
    needs_human: bool

client = anthropic.Anthropic()

def triage(ticket: str) -> TicketTriage:
    resp = client.messages.create(
        model="claude-sonnet-5",
        max_tokens=1024,
        messages=[{"role": "user", "content": f"Разбери тикет поддержки:\n\n{ticket}"}],
        # structured outputs: модель обязана вернуть JSON по схеме.
        # В старых версиях SDK параметр передаётся через extra_body={"output_config": ...}
        output_config={"format": {"type": "json_schema", "schema": TicketTriage.model_json_schema()}},
    )
    if resp.stop_reason == "max_tokens":
        raise RuntimeError("ответ обрезан, JSON неполный")
    raw = "".join(b.text for b in resp.content if b.type == "text")
    try:
        # схему гарантирует API, но бизнес-ограничения (ge/le, max_length) проверяем сами
        return TicketTriage.model_validate_json(raw)
    except ValidationError as e:
        raise ValueError(f"модель вернула невалидный triage: {e.error_count()} ошибок") from e
Подвохи
  • Не все ограничения JSON Schema поддерживаются провайдером в structured outputs (часто не поддерживаются числовые границы, длины строк, сложные паттерны). Схему, которую сгенерировал pydantic, иногда надо упростить, а проверку ограничений оставить на валидацию после ответа.
  • description у полей уходит в схему и работает как часть промпта. Это полезно, но значит, что правка docstring меняет поведение модели — версионируйте модели данных, как промпты.
  • Pydantic v1 и v2 несовместимы по API (.dict() → .model_dump(), parse_raw → model_validate_json). В старых туториалах и библиотеках встречается v1.

Скрипты для экспериментов

Типичный скрипт AI engineer: прочитать набор примеров, прогнать через модель конкурентно, сохранить результаты с метаданными (версия промпта, модель, токены, латентность) для анализа в pandas. Пример ниже самодостаточен: зависимости в PEP 723-заголовке, запуск uv run run_eval.py --prompt v3 cases.jsonl.

# /// script
# requires-python = ">=3.12"
# dependencies = ["anthropic>=0.60", "pandas>=2.2", "pyarrow"]
# ///
import argparse, asyncio, json, time
from pathlib import Path
import anthropic
import pandas as pd

PROMPTS = {
    "v2": "Классифицируй тикет. Ответь одним словом: billing, tech, refund, smalltalk.",
    "v3": Path("prompts/classify_v3.txt").read_text() if Path("prompts/classify_v3.txt").exists() else "",
}
client = anthropic.AsyncAnthropic(max_retries=4)  # ретраи 429/5xx с backoff — встроены в SDK

async def run_case(sem: asyncio.Semaphore, version: str, case: dict) -> dict:
    async with sem:
        t0 = time.perf_counter()
        try:
            resp = await client.messages.create(
                model="claude-haiku-4-5", max_tokens=16, system=PROMPTS[version],
                messages=[{"role": "user", "content": case["text"]}],
            )
            got = resp.content[0].text.strip().lower()
            usage = (resp.usage.input_tokens, resp.usage.output_tokens)
            err = None
        except anthropic.APIError as e:  # не роняем весь прогон из-за одного примера
            got, usage, err = None, (0, 0), type(e).__name__
    return {
        "example_id": case["id"], "category": case["category"], "prompt_version": version,
        "expected": case["label"], "got": got, "passed": int(got == case["label"]),
        "latency_ms": round((time.perf_counter() - t0) * 1000),
        "input_tokens": usage[0], "output_tokens": usage[1], "error": err,
    }

async def main() -> None:
    ap = argparse.ArgumentParser()
    ap.add_argument("cases", type=Path)
    ap.add_argument("--prompt", required=True, choices=PROMPTS)
    ap.add_argument("--concurrency", type=int, default=8)
    args = ap.parse_args()
    cases = [json.loads(line) for line in args.cases.read_text().splitlines() if line.strip()]
    sem = asyncio.Semaphore(args.concurrency)
    rows = await asyncio.gather(*(run_case(sem, args.prompt, c) for c in cases))
    df = pd.DataFrame(rows)
    df.to_parquet(f"results_{args.prompt}_{int(time.time())}.parquet")
    ok = df[df.error.isna()]
    print(f"pass_rate={ok.passed.mean():.3f} n={len(ok)} errors={df.error.notna().sum()}")

if __name__ == "__main__":
    asyncio.run(main())

Обратите внимание: ошибки инфраструктуры (429 после всех ретраев) записываются отдельно и не считаются провалом модели. Смешать их — классическая ошибка, из-за которой «новый промпт стал хуже» в день, когда у провайдера была перегрузка.

FastAPI: сервис-обёртка над LLM

FastAPI — де-факто стандарт для Python-сервисов вокруг моделей: async из коробки, валидация через pydantic, автоматическая OpenAPI-документация. Для Go-разработчика: это net/http + роутер + encoding/json + валидатор + swagger-генератор в одном, с объявлением через аннотации типов. Запускается ASGI-сервером (uvicorn) — это аналог http.Server.

import json
import anthropic
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel, Field

app = FastAPI()
client = anthropic.AsyncAnthropic()  # один клиент на процесс: пул соединений переиспользуется

class AskRequest(BaseModel):
    question: str = Field(min_length=1, max_length=8000)  # граница доверия: режем заранее
    max_tokens: int = Field(default=1024, ge=1, le=4096)

def sse(event: str, data: dict) -> str:
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"

@app.post("/v1/ask/stream")
async def ask_stream(req: AskRequest, request: Request) -> StreamingResponse:
    async def events():
        try:
            async with client.messages.stream(
                model="claude-opus-5",
                max_tokens=req.max_tokens,
                system="Ты ассистент поддержки. Отвечай кратко.",
                messages=[{"role": "user", "content": req.question}],
            ) as stream:
                async for text in stream.text_stream:
                    if await request.is_disconnected():
                        return  # выход из async with закрывает соединение с провайдером
                    yield sse("delta", {"text": text})
                msg = await stream.get_final_message()
            yield sse("done", {
                "stop_reason": msg.stop_reason,
                "input_tokens": msg.usage.input_tokens,
                "output_tokens": msg.usage.output_tokens,
            })
        except anthropic.APIStatusError as e:  # в т.ч. ошибка, пришедшая посреди стрима
            yield sse("error", {"status": e.status_code})

    return StreamingResponse(events(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})

@app.get("/healthz")
async def healthz() -> dict:
    return {"ok": True}

# uv run uvicorn app:app --host 0.0.0.0 --port 8000 --workers 2
Как это ломается в проде
  • Синхронный вызов в async-хендлере. anthropic.Anthropic() (sync) внутри async def блокирует event loop: один медленный запрос — и весь воркер стоит. Либо async-клиент, либо хендлер объявить обычным def (FastAPI выполнит его в пуле потоков).
  • Воркеры. Один процесс uvicorn = один event loop = одно ядро. Для CPU-части (токенизация, парсинг) нужны несколько воркеров. Для чистого I/O одного процесса хватает на сотни одновременных стримов.
  • Ошибка после 200. Статус и заголовки уже отправлены, когда начался стрим. Ошибку можно передать только событием внутри потока — клиент должен это обрабатывать.
  • Клиент на каждый запрос. Создание AsyncAnthropic() в хендлере — новый пул соединений и TLS-рукопожатие каждый раз. Клиент — синглтон, как http.Client в Go.

pandas для анализа evals

pandas — таблицы в памяти (DataFrame) с векторными операциями. Для Go-разработчика это «SQL поверх слайса структур без циклов»: groupby — GROUP BY, merge — JOIN, pivot_table — сводная таблица, query — WHERE. Главная ментальная перестройка: не писать циклы по строкам (iterrows медленный и неидиоматичный), а оперировать колонками целиком.

Ниже — 72 результата eval-прогона классификатора тикетов: три версии промпта × четыре категории × 6 примеров. Сгруппируйте по-разному и посмотрите, как меняются выводы. Усы на графике pass rate — 95% доверительный интервал Уилсона.

Мини-анализ evals: как это выглядит в pandas

Выберите группировку и метрику. Справа внизу — эквивалентный pandas-код и то, что он напечатает.

Что стоит заметить на этих данных. По версиям v3 выглядит лучше всех, но в разрезе «версия × категория» видно, что v3 просела на billing (3 из 6 против 5 и 4 у v1 и v2) — при n = 6 на ячейку это может быть и шум, и реальная регрессия, интервалы огромные. v3 также медленнее и расходует больше выходных токенов. Решение «катим v3» требует больше данных по billing и оценки стоимости, а не одного числа в сводке. Именно это — работа AI engineer с evals.

import pandas as pd

df = pd.concat(pd.read_parquet(p) for p in ["results_v1.parquet", "results_v2.parquet", "results_v3.parquet"])
df = df[df.error.isna()]  # инфраструктурные ошибки — отдельно, не в качестве

# 1. Сводка по версиям: качество, латентность, стоимость
PRICE_IN, PRICE_OUT = 1 / 1e6, 5 / 1e6  # Haiku 4.5, $ за токен (на момент написания)
df["cost_usd"] = df.input_tokens * PRICE_IN + df.output_tokens * PRICE_OUT
summary = df.groupby("prompt_version").agg(
    pass_rate=("passed", "mean"),
    n=("passed", "size"),
    p50_ms=("latency_ms", "median"),
    p95_ms=("latency_ms", lambda s: s.quantile(0.95)),
    cost_per_1k=("cost_usd", lambda s: s.mean() * 1000),
)

# 2. Срезы: где именно выросло или упало
pivot = df.pivot_table(index="category", columns="prompt_version",
                       values="passed", aggfunc="mean").round(2)
pivot["delta_v3_v2"] = pivot["v3"] - pivot["v2"]

# 3. Парное сравнение на одних и тех же примерах: смотрим только расхождения
wide = df.pivot_table(index="example_id", columns="prompt_version", values="passed")
fixed = ((wide.v2 == 0) & (wide.v3 == 1)).sum()
broken = ((wide.v2 == 1) & (wide.v3 == 0)).sum()
print(f"v3 починил {fixed}, сломал {broken}")  # для McNemar важны только эти два числа

# 4. Провалы глазами: самое полезное действие в анализе evals
print(df.query("prompt_version == 'v3' and passed == 0")[["example_id", "category", "expected", "got"]])
SQL-аналогии

df.groupby("v").agg(...) = SELECT v, avg(passed), count(*) … GROUP BY v. df.merge(other, on="example_id", how="left") = LEFT JOIN … USING (example_id). pivot_table = GROUP BY category, version, развёрнутый в колонки. Если привычнее SQL, есть DuckDB: duckdb.sql("select … from df") работает прямо по DataFrame. Для больших данных (десятки миллионов строк) смотрят в сторону Polars — колоночный движок на Rust с ленивым API.

SDK провайдеров

Официальные SDK Anthropic и OpenAI генерируются из OpenAPI-спецификаций и устроены похоже: типизированные запросы и ответы, sync и async клиенты, встроенные ретраи (у Anthropic по умолчанию 2 повтора на 408/409/429/5xx), таймауты, стриминг, пагинация. Всегда используйте их вместо ручного HTTP — кроме случаев, когда нужно понять протокол или SDK нет для вашего языка.

OpenAI-совместимый API как lingua franca

Формат Chat Completions стал де-факто стандартом: его отдают vLLM, Ollama, многие облака и gateway'и. Соблазн — писать всё под него и менять только base_url. Цена — потеря специфичных возможностей (явный prompt caching, thinking-блоки, особенности tool use), а они часто и есть основная экономия. Разумный компромисс — собственный тонкий интерфейс в коде (Generate(ctx, req) (Resp, error)) с адаптером на каждого провайдера, а не «наименьший общий знаменатель» на уровне протокола.

LangChain, LlamaIndex, LangGraph

Фреймворки — самая спорная тема в прикладном AI. На собеседовании ждут не «я знаю LangChain», а взвешенного мнения: что он даёт, чем платите, когда брать.

LangChain

Общий слой абстракций: единый интерфейс chat-моделей разных провайдеров, шаблоны промптов, парсеры вывода, сотни интеграций (векторные БД, загрузчики документов, инструменты), композиция цепочек. Сильная сторона — скорость прототипа и интеграции. Слабая — много слоёв поверх простого HTTP-вызова.

LlamaIndex

Фокус на данных и RAG: коннекторы к источникам, парсинг документов, стратегии чанкинга, индексы, query engines, reranking, оценка retrieval. Хорош, чтобы за день собрать RAG над корпусом и сравнить стратегии. Прод-логику retrieval часто потом переписывают под свои данные.

LangGraph

Низкоуровневая библиотека для агентов как графа состояний: узлы — шаги, рёбра — переходы (в т.ч. условные), общее состояние, checkpointing (сохранение состояния между шагами), human-in-the-loop, возобновление после сбоя. Меньше «магии», чем LangChain; по сути — движок конечного автомата с персистентностью.

Чем платите — список, который стоит уметь назвать:

  • Скрытые промпты. Готовые цепочки и агенты содержат свои системные промпты и шаблоны. Вы не видите, что уходит в модель, пока не включите трейсинг. Anthropic в «Building effective agents» прямо советует начинать с прямых вызовов API: фреймворки добавляют слои, скрывающие реальные промпты и ответы, и провоцируют лишнюю сложность.
  • Отладка. Стектрейс на 40 фреймов через generic-обёртки, callbacks и runnable-протоколы. Ошибка формата ответа модели выглядит как исключение глубоко внутри парсера.
  • Версии. Экосистема быстро меняет API; мажорные переходы ломали импорты и паттерны, туториалы годичной давности часто не работают. Пинить версии и закладывать время на миграции.
  • Отставание от провайдера. Новая возможность API (новый параметр, тип блока, режим кэширования) появляется в SDK провайдера в день релиза, во фреймворке — позже, а в «универсальной» абстракции может не появиться вовсе.
  • Наименьший общий знаменатель. Абстракция «chat model» сглаживает различия провайдеров, в том числе полезные.
  • Зависимости. Десятки транзитивных пакетов, конфликты версий с вашим pydantic или numpy.

Фреймворк или свой код?

Эвристика, а не закон. Двигайте сложность оркестрации (сколько шагов, ветвлений, состояния) и требования к контролю (прод-нагрузка, аудит, стоимость, отладка). Тип задачи уточняет, какой именно фреймворк.

А в Go?

Экосистема меньше: есть langchaingo (порт LangChain от сообщества), Eino от CloudWeGo, Genkit с поддержкой Go. Но в Go культура «тонкие библиотеки + свой код» и так сильнее, и это совпадает с советом Anthropic: SDK провайдера, свой агентный цикл на 100–200 строк, pgvector, OpenTelemetry. Агентный цикл — это for с switch resp.StopReason; граф состояний — таблица переходов и состояние в Postgres. Фреймворк здесь чаще мешает, чем помогает.

Jupyter: для экспериментов, не для прода

Jupyter notebook — документ из ячеек кода и текста, которые выполняются в живом процессе (kernel) по одной. Для работы с LLM это идеальная лаборатория: поправил промпт, перезапустил одну ячейку, посмотрел пять ответов рядом, построил график по результатам evals, записал выводы тут же. Состояние (загруженный датасет, клиент) живёт между ячейками, не нужно перезапускать всё.

Ровно это же делает его непригодным для прода:

  • Скрытое состояние. Ячейки выполняются в любом порядке, переменная могла быть определена в удалённой ячейке. Ноутбук «работает у меня» и не воспроизводится после Restart & Run All.
  • Нет тестов, типов, ревью. Файл .ipynb — JSON с выводами и картинками в base64; диффы в git нечитаемы. Помогают nbstripout (очистка выводов), jupytext (парный .py), или marimo — реактивные ноутбуки, хранящиеся как обычный .py.
  • Утечки. Выводы ячеек сохраняются в файле: ответы модели с ПДн, случайно напечатанный ключ API уезжают в репозиторий.
  • Нет жизненного цикла сервиса: ни graceful shutdown, ни лимитов, ни наблюдаемости.

Нормальный путь: ноутбук → код, который доказал ценность, выносится в модуль с функциями → скрипт с аргументами (PEP 723) → тесты и CI → при необходимости сервис (FastAPI или Go). Ноутбук остаётся как отчёт об эксперименте, импортирующий этот модуль.

Самопроверка

Почему time.sleep(2) внутри async def-хендлера FastAPI — серьёзная ошибка, а в Go time.Sleep в хендлере — нет?

asyncio кооперативный и однопоточный: переключение задач происходит только на await. Синхронный sleep блокирует event loop, и все остальные запросы этого воркера ждут. В Go рантайм паркует только текущую горутину, остальные продолжают работать на других потоках.

Чем dataclass отличается от pydantic BaseModel и когда что брать?

dataclass — контейнер с генерацией конструктора, без валидации значений в рантайме. BaseModel валидирует и приводит типы, парсит JSON, генерирует JSON Schema. Для внутренних структур — dataclass (быстро, просто), для данных с границы доверия (HTTP-запросы, ответы модели, конфиги) — pydantic.

Какой аналог fmt.Errorf("…: %w", err) в Python?

raise NewError("…") from err. Исходное исключение сохраняется в __cause__ и печатается в traceback. Проверка типа в цепочке делается через except по классу, аналога errors.Is по всей цепочке из коробки нет — обычно ловят на нужном уровне.

Зачем нужен venv и почему uv его не отменяет?

Python ставит пакеты в окружение интерпретатора, и без изоляции проекты конфликтуют версиями зависимостей. venv — отдельное окружение на проект. uv не отменяет venv, а управляет им: создаёт .venv, синхронизирует с lock-файлом, ставит нужную версию Python.

Что делает df.pivot_table(index="category", columns="prompt_version", values="passed", aggfunc="mean")?

Группирует по паре (категория, версия), считает среднее passed (то есть pass rate) и раскладывает версии по колонкам: строки — категории, колонки — версии, в ячейках — pass rate. Аналог GROUP BY по двум полям с последующим разворотом.

Почему при сравнении двух промптов на одном наборе полезно смотреть на «починенные» и «сломанные» примеры, а не только на разницу pass rate?

Одинаковая разница может получиться из «починил 5, сломал 0» и из «починил 25, сломал 20». Второй случай — нестабильный промпт, который меняет поведение на половине набора. Парный тест McNemar использует только эти два числа и чувствительнее сравнения двух независимых долей.

Назовите три конкретных минуса LangChain в проде.

Скрытые промпты и шаблоны внутри цепочек, которые влияют на поведение и стоимость; тяжёлая отладка через многослойные абстракции; нестабильность API между версиями и отставание от новых возможностей провайдеров. Плюс транзитивные зависимости и «наименьший общий знаменатель» в абстракции моделей.

Что не так с ноутбуком, который «работает у меня»?

Ячейки могли выполняться не по порядку, а часть состояния — прийти из удалённых ячеек. Проверка: Restart & Run All. Для воспроизводимости код выносится в модули, ноутбук только импортирует и визуализирует.

Вопросы с собеседований

Вы бы взяли LangChain для нового продукта?

Зависит от стадии и формы задачи, и я бы так и ответил, с критериями. Для прототипа или внутреннего инструмента с кучей интеграций — возможно, это ускоряет первую неделю. Для прод-системы с жёсткими требованиями к стоимости, латентности и отладке я начну с SDK провайдера и тонкого своего слоя: агентный цикл и RAG-пайплайн — это сотни строк, зато я вижу каждый промпт, могу использовать prompt caching и новые возможности API в день релиза, а трейсинг и evals настраиваю под себя. Для агента со сложным состоянием, human-in-the-loop и долгими сессиями рассмотрю LangGraph как движок персистентного графа, а не как набор готовых агентов. Главный аргумент против «всё на фреймворке» — скрытые промпты и отладка; главный аргумент «за» — не писать двадцатый загрузчик PDF. Совет Anthropic в «Building effective agents»: начинать с прямых вызовов API.

Почему FastAPI-сервис с LLM под нагрузкой отвечает всё медленнее, хотя провайдер отвечает стабильно?

Первое, что проверю: блокирующие вызовы в async-хендлерах — синхронный клиент LLM или БД, requests, тяжёлый CPU (токенизация, парсинг JSON мегабайтных ответов). Они блокируют event loop, и латентность всех запросов воркера растёт. Диагностика — debug-режим asyncio (предупреждения о медленных колбэках), py-spy. Второе: клиент создаётся на каждый запрос — нет переиспользования соединений. Третье: лимиты пула соединений HTTP-клиента меньше, чем одновременных стримов. Четвёртое: один воркер на CPU-bound работе. Лечение: async-клиенты везде, asyncio.to_thread для синхронных библиотек, пул процессов для CPU, несколько воркеров uvicorn, синглтон клиента с настроенным пулом.

Как вы анализируете результаты eval-прогона? Покажите на pandas.

Загружаю результаты в DataFrame, отделяю инфраструктурные ошибки. Сводка по версиям через groupby().agg(): pass rate, n, p50/p95 латентности, стоимость. Срезы через pivot_table по категории и версии — ищу, где регрессия прячется за общим ростом. Парное сравнение по example_id: сколько починено и сколько сломано, McNemar для значимости. Доверительные интервалы (Уилсон или bootstrap), решение по нижней границе. И обязательно глазами смотрю на провалы — df.query("passed == 0") — потому что метрика говорит «сколько», а не «почему». Ошибки judge-модели тоже проверяю выборочно.

Сервис на Go или на Python? Как бы вы выбрали для LLM-продукта?

Сервисный слой — на том, на чём сильна команда и инфраструктура: вызов API, стриминг, лимиты, очереди — это I/O, и Go здесь даёт простую конкурентность, предсказуемую память, один бинарь и строгую типизацию. Python нужен там, где экосистема: evals, анализ, fine-tuning, локальные модели, сложный парсинг документов. Частая здравая архитектура — Go-сервисы плюс Python-воркеры или офлайн-пайплайны, связь через очередь или HTTP. Против Python-сервиса по умолчанию: GIL и async-подвохи, упаковка и зависимости. За: скорость итерации, если команда — ML/DS. Выбор фиксирую в ADR, а не спорю о вкусах.

Зачем абстрагировать провайдера LLM и как не переусердствовать?

Нужно для fallback между моделями и провайдерами, A/B-тестов, тестов с фейковым клиентом и защиты от vendor lock-in. Переусердствовать — значит свести всё к наименьшему общему знаменателю и потерять prompt caching, thinking, особенности tool use, которые дают основную экономию и качество. Решение: узкий интерфейс под задачи продукта (генерация, стриминг, tool-цикл) с явными опциями, которые адаптер провайдера поддерживает или игнорирует; провайдер-специфичные возможности доступны через расширения. И evals на каждого провайдера — переключение без них опасно, промпты не переносятся один в один.

Чем asyncio отличается от горутин, и что вы бы сказали, если бы вас спросили, «что лучше для LLM-сервиса»?

asyncio — кооперативная многозадачность в одном потоке, переключение только в await, функции «окрашены» (async заражает стек), CPU-параллелизма нет из-за GIL. Горутины — вытесняющий планировщик M:N на всех ядрах, любая функция может быть конкурентной, блокирующий вызов не мешает другим. Для I/O-bound нагрузки LLM-сервиса оба справляются с тысячами одновременных запросов. Разница в надёжности: в Python одна синхронная библиотека способна положить воркер, и это надо контролировать ревью и линтерами; в Go такой класс ошибок отсутствует. Для CPU-частей (токенизация, обработка документов) у Go преимущество без дополнительных процессов.

Как вы используете Jupyter в работе и как код из ноутбука попадает в прод?

Ноутбук — для исследований: итерации над промптами на небольших выборках, анализ evals, графики, разбор провалов. Правила: выводы очищаются перед коммитом (nbstripout) или используется jupytext/marimo, секреты только из окружения, данные с ПДн не сохраняются в выводах. Как только код нужен повторно, он переезжает в модуль с тестами, ноутбук его импортирует. Прод-код — модули, скрипты с CLI и сервисы, с CI, типами и наблюдаемостью. Ноутбук никогда не запускается «по крону».
