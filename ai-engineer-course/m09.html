Продакшн: надёжность, стоимость, латентность

LLM-провайдер ведёт себя как ненадёжная, медленная и дорогая внешняя зависимость с жёсткими квотами. В этом модуле собираем вокруг неё то же, что вы строили вокруг любого внешнего API: ретраи, таймауты, circuit breaker, лимиты, кэши, трейсинг и guardrails. Отдельно разбираем, когда стоит поднимать собственный инференс.

Большая часть модуля знакома любому Go-бэкендеру: backoff, context, middleware, circuit breaker, token bucket, OpenTelemetry. У LLM есть три особенности, из-за которых привычные приёмы приходится донастраивать.

  • Длинные и сильно разбросанные по длительности запросы. Ответ идёт от 300 мс до нескольких минут, и время зависит от числа токенов на выходе. Один общий таймаут на 30 секунд либо оборвёт длинные ответы, либо будет ждать полминуты вместо того, чтобы вовремя переключиться на fallback.
  • Лимиты считаются в токенах. Помимо RPM провайдер ограничивает input и output tokens в минуту. Один запрос с документом на 200K токенов расходует квоту сотни обычных.
  • Стоимость каждого вызова заметна. Retry storm здесь бьёт не только по доступности, но и по счёту: каждая повторная попытка оплачивается заново.

Ретраи и таймауты

Начинать стоит с классификации ошибок. Ретрай имеет смысл, если следующая попытка может закончиться иначе. На 400 «messages: roles must alternate» повтор всегда даст тот же ответ, и вы просто потратите время пользователя.

Экспоненциальный backoff с jitter

Задержка перед попыткой n равна min(cap, base·2ⁿ). Без jitter все клиенты, получившие ошибку в одну и ту же секунду, придут повторно тоже одновременно. Так возникает thundering herd: пики нагрузки повторяются через 200 мс, 400 мс, 800 мс, и каждый пик снова упирается в лимит. Full jitter (sleep = rand(0, min(cap, base·2ⁿ))) из статьи AWS размазывает повторы по интервалу, и пики исчезают.

Симулятор ретраев: thundering herd и retry budget

400 клиентов шлют запрос в одни и те же 100 мс (например, после восстановления сети или рестарта зависимого сервиса). Сервис обрабатывает 30 запросов за 100 мс, остальные получают 429/529, и каждый отказ тоже немного расходует ёмкость. Сначала сравните столбики с jitter и без. Потом поставьте частоту ошибок на 100% («провайдер лежит») и включите retry budget.

Что видно в симуляторе:

  • Без jitter повторные попытки приходят волнами, и каждая волна снова больше ёмкости. Success rate упирается в число ретраев, а p99 растёт экспоненциально.
  • С jitter та же нагрузка растягивается по времени и помещается в ёмкость. Доля успешных запросов растёт, хотя попыток становится не больше.
  • Retry budget ограничивает долю повторов, например 20% сверху к обычному трафику. Когда провайдер лежит целиком (100% ошибок), без бюджета вы увеличиваете нагрузку в 1 + max_retries раз, а с бюджетом только в ~1.2 раза, и ошибка или fallback срабатывают быстро. У бюджета есть цена: при коротком всплеске на здоровом сервисе он отсекает ретраи, которые могли бы пройти. Поэтому бюджет считают по скользящему окну на реальном трафике, а не по одной вспышке.
Retry storm: ретраи на нескольких слоях

SDK Anthropic по умолчанию делает 2 ретрая. Вокруг него ваша middleware делает ещё 3. Выше API-gateway ретраит 5xx ещё 3 раза, а мобильный клиент добавляет свои 2. В худшем случае это 3·4·4·3 = 144 вызова на одно нажатие кнопки, и каждый из них оплачивается. Правило простое: ретраи живут на одном слое, как правило ближайшем к провайдеру, а остальные слои ретраи выключают. В Go SDK это option.WithMaxRetries(0), если ретраи у вас свои.

Идемпотентность

Сам вызов POST /v1/messages побочных эффектов не имеет, поэтому повторять его безопасно, хотя и платно. Опасно повторять шаг выше:

  • Агент с инструментами. Если упал вызов модели после того, как create_refund уже выполнился, при повторе всего шага деньги вернутся дважды. Инструментам с побочными эффектами нужны idempotency key (например, hash(conversation_id, tool_use_id)) и дедупликация на стороне исполнителя, как в платёжных API.
  • Стриминг. Если пользователь уже видел половину ответа, повтор вернёт другой текст: генерация недетерминирована. UI должен явно перезапустить сообщение, склеивать куски нельзя.
  • Batch и фоновые пайплайны. Нужны custom_id и upsert результата, чтобы повторная обработка не создавала дубликаты.

Таймауты и дедлайны

Задача таймаута в том, чтобы вовремя признать попытку неудачной, пока остаётся время на ретрай или fallback. Одного общего значения на LLM-вызов не хватает, нужно несколько:

Главная идея: при стриминге TTFT и полное время ограничиваются раздельно. Без стриминга есть только total. Если его выставить в 60 с, то при зависшем провайдере вы узнаете об этом через минуту. Со стримингом через 8 секунд без первого токена можно отменить попытку и уйти на fallback, а длинная генерация по-прежнему может идти хоть 5 минут.

// Стриминг с раздельными дедлайнами: TTFT, простой между чанками, общий.
var (
	ErrTTFT = errors.New("llm: no first token before deadline")
	ErrIdle = errors.New("llm: stream stalled")
)

func StreamWithDeadlines(ctx context.Context, c anthropic.Client, p anthropic.MessageNewParams,
	ttft, idle, total time.Duration, onText func(string)) error {

	ctx, cancelTotal := context.WithTimeout(ctx, total)
	defer cancelTotal()
	ctx, cancel := context.WithCancelCause(ctx)
	defer cancel(nil)

	var started atomic.Bool
	watchdog := time.AfterFunc(ttft, func() {
		if started.Load() {
			cancel(ErrIdle)
		} else {
			cancel(ErrTTFT)
		}
	})
	defer watchdog.Stop()

	stream := c.Messages.NewStreaming(ctx, p)
	defer stream.Close()
	for stream.Next() {
		watchdog.Reset(idle) // любое событие, включая ping, продлевает жизнь
		ev := stream.Current()
		d, ok := ev.AsAny().(anthropic.ContentBlockDeltaEvent)
		if !ok {
			continue
		}
		if t, ok := d.Delta.AsAny().(anthropic.TextDelta); ok {
			started.Store(true)
			onText(t.Text)
		}
	}
	if err := stream.Err(); err != nil {
		if cause := context.Cause(ctx); cause != nil {
			return cause // ErrTTFT / ErrIdle / DeadlineExceeded: понятно, что именно сработало
		}
		return err
	}
	return nil
}
Режим отказа: дедлайн меньше, чем нужно ответу

Total deadline 30 с при max_tokens: 8000 и скорости около 60 tok/s. Ответы длиннее примерно 1700 токенов будут стабильно отваливаться по таймауту, ретраиться и снова отваливаться. Вы платите за три обрезанные генерации и не получаете ни одного ответа. Дедлайн должен соответствовать max_tokens, или наоборот. Ещё лучше стримить и проверять stop_reason: "max_tokens".

Перед каждым ретраем стоит проверить остаток родительского дедлайна: if dl, ok := ctx.Deadline(); ok && time.Until(dl) < backoff+minAttempt { return err }. Пятисекундный backoff при оставшихся двух секундах бюджета бессмысленен. Лучше сразу вернуть ошибку или быстрый fallback.

Fallback и circuit breaker

Ретраи спасают от кратких сбоев, но не от минутных инцидентов у провайдера. На этот случай нужна цепочка fallback, например: основная модель, модель поменьше у того же провайдера, модель другого провайдера или того же через другое облако (Bedrock, Vertex), self-hosted модель и, наконец, деградированный ответ вроде «сервис перегружен, вот ссылки на FAQ».

Circuit breaker перед каждым звеном нужен, чтобы не тратить на заведомо лежащего провайдера TTFT-таймаут в каждом запросе. После N ошибок подряд breaker переходит в open, и запросы сразу идут к следующему звену. Через cooldown он становится half-open и пропускает один пробный запрос: при успехе возвращается в closed, при ошибке снова в open.

Маршрут запроса через цепочку fallback

Выберите состояние провайдеров и отправьте поток запросов. Breaker открывается после 3 ошибок подряд и через 8 с (модельного времени) становится half-open. На 429 breaker не срабатывает: это ваша квота, а не авария, поэтому звено пропускается на время retry-after.

Fallback-модель — не бесплатная копия основной

  • Промпты под модель. Промпт, отточенный под Opus 5, на Haiku или open-source модели часто работает хуже: другие привычки форматирования, другое следование инструкциям, другой формат tool calling. Храните промпт на каждое звено, prompts/answer@v12/{opus,haiku,qwen}.md, и адаптируйте запрос в роутере.
  • Различия API. У одной модели temperature запрещён (новые Claude), у другой он обязателен для детерминизма. Structured outputs, strict tools, размер контекста (1M против 200K у Haiku 4.5), vision: запрос на 400K токенов fallback на Haiku физически не примет. Роутер должен уметь сказать «это звено не подходит» до отправки.
  • Evals на каждое звено. Прогоняйте тот же golden set из модуля 8 по всей цепочке и знайте разницу в качестве, например «B на 4 п.п. хуже по faithfulness». Это продуктовое решение: иногда честный отказ лучше плохого ответа.
  • Fallback, которым не пользуются, со временем ломается. Если путь срабатывает раз в квартал, к моменту инцидента там окажется протухший ключ или удалённая модель. Пропускайте через него 1% трафика постоянно или устраивайте регулярные game day.
  • Стоимость. Fallback на более дорогую модель (Sonnet → Opus при 529) во время инцидента может утроить счёт. Лимиты расходов действуют и для fallback.
Refusal — это не ошибка для fallback

stop_reason: "refusal" означает, что модель сознательно отказалась отвечать. Автоматически переотправлять такой запрос «более сговорчивой» модели — плохая идея: это обход политики безопасности, и для compliance такой отказ всё равно считается ответом вашего продукта. Refusal стоит обрабатывать как продуктовый исход: понятное сообщение пользователю, лог, метрика доли отказов. Если отказов много на легитимных запросах (over-refusal), чините промпт и evals, а не роутинг.

Rate limits и бюджеты токенов

У провайдеров лимиты заданы на организацию или workspace и на модель, в нескольких измерениях сразу:

  • RPM — запросов в минуту;
  • ITPM — input tokens в минуту. У Anthropic для большинства актуальных моделей cache_read_input_tokens в ITPM не входят, так что prompt caching фактически увеличивает пропускную способность (проверьте для своей модели в доке);
  • OTPM — output tokens в минуту. Оценивается по max_tokens в начале запроса и корректируется по факту, поэтому завышенный max_tokens заранее «занимает» квоту.

Anthropic описывает свои лимиты как token bucket, который пополняется непрерывно, а не сбрасывается раз в минуту. Остаток видно в заголовках ответа anthropic-ratelimit-requests-remaining, anthropic-ratelimit-input-tokens-remaining, …-output-tokens-remaining и в retry-after на 429. У OpenAI это RPM/TPM с заголовками x-ratelimit-remaining-*.

Клиентский лимитер, очередь, приоритеты

Упираться в лимит провайдера и потом ретраить 429 — плохая стратегия: вы тратите попытки, увеличиваете латентность и конкурируете со своими же сервисами. Лучше держать свой token bucket чуть ниже провайдерского (90%) в трёх измерениях и ждать на нём:

  • golang.org/x/time/rate: rate.NewLimiter(rate.Limit(itpm/60.0), burst) и WaitN(ctx, estTokens). Если дедлайн контекста не дождётся токенов, WaitN сразу вернёт ошибку, и вы получаете load shedding без дополнительного кода.
  • Оценку input tokens даёт /v1/messages/count_tokens или эвристика «символы / 3.5» с запасом. OTPM резервируется по max_tokens.
  • Несколько инстансов сервиса делят один лимит организации. Локальный лимитер делит квоту поровну (limit / replicas), а распределённый хранит состояние в Redis (GCRA, скрипт на Lua). Второй честнее, но добавляет сетевой hop и точку отказа.
  • Приоритеты. Интерактивный чат важнее фоновой суммаризации. Держите две очереди с раздельными лимитерами или взвешенную очередь. Фоновые задачи лучше отправлять в Batch API: −50% к цене и отдельная ёмкость.
  • Fairness между тенантами. Один клиент, запустивший импорт на 10 000 документов, не должен съесть квоту остальных. Решение — per-tenant лимитер перед общим.

Цифры для оценки

Агент на Opus 5 ($5 / $25 за 1M): 20 итераций, контекст растёт до 60K токенов, в среднем около 35K input и 800 output на итерацию. Без кэша это 20·(35K·$5 + 0.8K·$25)/1M ≈ $3.9 за задачу. Латентность и кэши

Латентность LLM-вызова раскладывается так: T ≈ очередь + TTFT(prefill ~ input tokens) + output_tokens / скорость генерации. На практике почти всегда доминирует второе слагаемое. 1000 токенов вывода при 70 tok/s занимают 14 с, а prefill 20K токенов — порядка секунды. Отсюда порядок рычагов по силе:

  1. Сократить вывод. Структурированный короткий ответ, «без преамбулы», JSON вместо прозы, ограничение max_tokens. Эффект линейный и бесплатный.
  2. Стриминг. Полное время не уменьшается, но воспринимаемая латентность сокращается до TTFT. Для чата это главный UX-рычаг.
  3. Модель поменьше или ниже effort. Haiku-класс генерирует в разы быстрее и дешевле. Для новых Claude output_config.effort: "low" сокращает thinking. Маршрутизируйте по сложности: простое на маленькую модель, сложное на большую.
  4. Параллелизм. Retrieval из нескольких источников, независимые подзадачи, input guardrail параллельно с основным вызовом — это errgroup.
  5. Кэши. Точный и семантический кэш убирают вызов целиком. Prompt caching сокращает TTFT на длинном префиксе (по заявлению Anthropic до ~85% для длинных промптов) и снижает стоимость input до 0.1×.

Водопад латентности RAG-запроса

Типичный путь: guardrail → embedding → vector search + BM25 → rerank → LLM → проверка вывода. Включайте оптимизации и следите за двумя маркерами: когда пользователь видит первый текст и когда ответ готов целиком. Длительности — правдоподобный порядок величин, не бенчмарк.

Аналогия из Go

Retrieval из pgvector и BM25 из Elasticsearch — это errgroup.WithContext с двумя горутинами. Input guardrail работает как спекулятивное выполнение: запускаете классификатор и основной вызов одновременно, и если классификатор сказал «нет», отменяете ctx основного. Guardrail при этом не добавляет латентности, но в худшем случае вы заплатите за отменённый вызов (обычно за prefill).

Семантический кэш: где он ломается

Идея: если новый вопрос по embedding похож на уже отвеченный (cosine ≥ порога), вернуть сохранённый ответ. Проблема в том, что embedding-модели плохо различают отрицание, числа, даты и сущности. «Как отменить заказ?» и «Как оформить заказ?», «тариф Pro» и «тариф Team», «доставка в Москву» и «в Казань» оказываются рядом в пространстве, а правильные ответы у них разные.

Семантический кэш: порог сходства против ложных попаданий

Квадраты — ответы в кэше с кругом радиуса «1 − порог». Точки — новые запросы, цвет показывает исход. Похожие намерения (отмена и оформление заказа и т.п.) лежат рядом. Двигайте порог и смотрите, как hit rate растёт вместе с долей ложных попаданий.

верное попаданиеложное попаданиепромах (идём в LLM)запись в кэше
  • Порог калибруется, а не угадывается. Соберите 300–500 размеченных пар «один и тот же вопрос / разные вопросы» из реального трафика, постройте precision от порога и выберите порог под допустимую долю ложных попаданий, например ≤ 0.5%. Типичные значения 0.90–0.97, но они сильно зависят от embedding-модели.
  • Scope ключа. Тенант, язык, модель, версия промпта и хэш system и tools. Для RAG добавьте права пользователя: иначе ответ, собранный из документов HR, достанется человеку без доступа. Это уже утечка данных, а не просто ошибка кэша.
  • Инвалидация. TTL (часы или дни); смена версии промпта или модели меняет scope, и кэш «сбрасывается» сам. Для RAG храните id документов, на которых основан ответ, и удаляйте записи при их изменении.
  • Что не кэшировать. Персонализированные ответы, ответы с stop_reason != "end_turn", refusal, диалоги с историей (кэшировать стоит только первый вопрос), всё, что зависит от времени.
  • Дополнительная проверка. Для чувствительных доменов попадание можно перепроверить дешёвой моделью: «отвечает ли этот ответ на этот вопрос? да/нет». Вызов Haiku всё равно дешевле и быстрее генерации.

Prompt caching на практике

Коротко (подробно в модуле 2). Порядок: tools → system → messages. Ставьте cache_control на конец стабильной части, всего до 4 breakpoint'ов. Любой байт, изменившийся раньше breakpoint'а, инвалидирует всё после него. Классические ошибки: time.Now() в system prompt, недетерминированный порядок tools (ключи map в Go!), id запроса в начале сообщения. Проверяйте кэш метрикой cache_read_input_tokens / (input + cache_read + cache_write) в дашборде. Если она внезапно упала до нуля, значит, кто-то поменял префикс.

Observability

Классических RED-метрик (rate, errors, duration) для LLM мало. Вам нужны токены, стоимость, TTFT, stop reasons, cache hit rate, а для отладки ещё и содержимое промптов и ответов, что сразу упирается в PII.

PII в логах

  • Маскирование до записи. Регэкспы для email, телефонов, карт и паспортов плюс NER (Microsoft Presidio) для имён и адресов. Маскируйте в приложении или процессором в OTel Collector, но до того, как данные покинут периметр.
  • Сэмплирование содержимого. Метаданные (токены, латентность, модель) пишите для 100% запросов, полный текст для 1–5% и для всех ошибок. Это и дешевле, и безопаснее.
  • Retention и доступ. Сырые промпты 14–30 дней в отдельном хранилище с отдельными правами; агрегаты храните дольше. Нужны процедура удаления по запросу пользователя (GDPR) и аудит доступа.
  • Идентификаторы. user_id пишите через HMAC, а не открытым текстом. Ключ HMAC ротируется.
// Грубое маскирование PII перед логированием. Регэкспы ловят «структурные» PII;
// имена и адреса ловит NER (Presidio). Маскировать надо до того, как текст уйдёт в логи.
var piiPatterns = []struct {
	re   *regexp.Regexp
	mask string
}{
	{regexp.MustCompile(`[\w.+-]+@[\w-]+\.[\w.-]+`), "<EMAIL>"},
	{regexp.MustCompile(`\b(?:\d[ -]?){13,19}\b`), "<CARD>"},
	{regexp.MustCompile(`\+?\d[\d\s()-]{9,}\d`), "<PHONE>"},
}

func MaskPII(s string) string {
	for _, p := range piiPatterns {
		s = p.re.ReplaceAllString(s, p.mask)
	}
	return s
}

Guardrails и модерация

Guardrails — проверки вокруг вызова модели, которые не зависят от её доброй воли. Системный промпт «не обсуждай конкурентов» считается пожеланием, а не гарантией.

На входе

  • Лимиты размера и частоты
  • Детектор prompt injection / jailbreak: классификатор или маленькая модель
  • Тематический фильтр («вопрос по нашему продукту?»)
  • Редакция PII, если провайдеру её отдавать нельзя
  • Модерация токсичного и незаконного контента

На выходе

  • Валидация структуры: structured outputs / strict tools плюс проверка бизнес-правил (сумма ≥ 0, id существует)
  • Утечка PII и секретов, system prompt в ответе
  • Groundedness для RAG: есть ли утверждения, которых нет в источниках
  • Политика: юридические или медицинские советы, обещания от имени компании

Вокруг инструментов

  • Allowlist инструментов на роль или тенант
  • Валидация аргументов как недоверенного ввода
  • Human-in-the-loop для необратимых действий
  • Лимиты: сумма возврата, число писем
  • Чем проверять. Регэкспы и правила быстрые, дешёвые и предсказуемые. Специализированные классификаторы — Llama Guard, модерационные эндпоинты провайдеров, свой fine-tuned маленький классификатор (модуль 10). LLM-as-judge на Haiku-классе гибкий, но добавляет 200–500 мс и стоит денег. На практике их комбинируют: сначала дешёвое, дорогое только при сомнении.
  • Метрики guardrails. У каждого есть precision и recall. False positive — это легитимный пользователь, которому отказали, и такие ошибки убивают продукт так же, как пропуски. Держите размеченный набор и считайте обе ошибки.
  • Fail-open или fail-closed. Если классификатор недоступен, пропускаем или блокируем? Для модерации детского контента ответ «блокируем», для тематического фильтра внутреннего инструмента — «пропускаем и логируем». Это решение надо принять явно, а не получить случайно из-за if err != nil { return true }.
  • Стриминг и выходные проверки конфликтуют. Нельзя проверить ответ, пока он не сгенерирован. Варианты: проверять по предложениям с буфером в 1–2 предложения, стримить и «отзывать» сообщение (плохой UX), или не стримить там, где риск высокий.
  • Политика отказов. Единый тон и формат отказа, объяснение («не могу помочь с X, могу с Y»), метрика доли отказов по причинам. Отказ должен быть продуктовым сценарием, а не исключением.
// Input guardrail параллельно с основным вызовом: латентность не растёт,
// при блокировке основной вызов отменяется через общий ctx.
var ErrBlocked = errors.New("guardrail: input blocked")

func GuardedComplete(ctx context.Context, llm LLM, req Request,
	guard func(context.Context, string) (allowed bool, err error)) (*Response, error) {

	g, gctx := errgroup.WithContext(ctx)
	var resp *Response
	g.Go(func() error {
		ok, err := guard(gctx, lastUserText(req))
		switch {
		case err != nil:
			return fmt.Errorf("guardrail unavailable: %w", err) // fail-closed: осознанный выбор
		case !ok:
			return ErrBlocked
		}
		return nil
	})
	g.Go(func() (err error) {
		resp, err = llm.Complete(gctx, req)
		return err
	})
	if err := g.Wait(); err != nil {
		return nil, err
	}
	return resp, nil
}

Self-hosted инференс

Свой инференс поднимают по четырём причинам: приватность (данные не должны покидать периметр), стоимость на большом стабильном объёме, контроль (своя fine-tuned модель, фиксированная версия, предсказуемая латентность) и офлайн или edge. Платите вы за это GPU, людьми и дежурствами.

Почему vLLM быстрый

  • PagedAttention. KV-cache (модуль 1) хранится не одним непрерывным куском на максимальную длину последовательности, а блоками по 16 токенов, как страницы виртуальной памяти в ОС. Блоки выделяются по мере роста последовательности, почти без фрагментации, и могут разделяться между запросами с общим префиксом (copy-on-write). В одну и ту же память GPU помещается в разы больше одновременных последовательностей, а по пейперу пропускная способность выросла в 2–4 раза относительно предыдущих систем.
  • Continuous batching (iteration-level scheduling). Статический батч ждёт, пока закончится самая длинная последовательность. В continuous batching на каждом шаге декодирования завершённые запросы уходят, а новые встают на их место. GPU загружен постоянно, и короткие запросы не ждут длинные.
  • Prefix caching. Общий system prompt считается один раз. Это аналог prompt caching у провайдера, только бесплатный.
Цифры: память

Веса: число параметров × байты. 8B в bf16 занимает 16 ГБ, 70B в bf16 — 140 ГБ (минимум 2×H100 80 ГБ, на практике 4 ради KV-cache), 70B в FP8 — ~70 ГБ. KV-cache на токен равен 2 × layers × kv_heads × head_dim × bytes. Для Llama-3-8B (32 слоя, 8 KV-голов, head_dim 128, bf16) это 128 КБ на токен, так что одна последовательность на 32K токенов занимает 4 ГБ. Именно KV-cache, а не веса, ограничивает конкурентность.

GPU-экономика

Сравнивать надо не «цену GPU-часа», а стоимость миллиона токенов при вашей реальной утилизации: $/1M = GPU $/ч ÷ (tok/s × утилизация × 3600) × 10⁶. GPU, который ночью простаивает, стоит столько же, сколько днём, а API ночью не стоит ничего. Отсюда правило: self-hosted выгоден при большом и ровном объёме, когда модели поменьше хватает по качеству.

Калькулятор: self-hosted против API

Оси логарифмические. Линия API растёт линейно с объёмом. Self-hosted — ступеньки: GPU покупается целиком, плюс фиксированные расходы на людей. Пропускная способность — суммарная (с батчингом) на один GPU для вашей модели; её надо измерять, дефолты взяты для порядка величин. Цены на момент написания, проверьте актуальный прайс.

# 1) Запуск OpenAI-совместимого сервера (GPU с 24+ ГБ для 8B в bf16):
#    pip install vllm
#    vllm serve Qwen/Qwen3-8B \
#      --max-model-len 32768 \          # верхняя граница контекста: определяет бюджет KV-cache
#      --gpu-memory-utilization 0.90 \  # доля VRAM под веса + KV-cache
#      --max-num-seqs 128 \             # максимум одновременных последовательностей в батче
#      --enable-prefix-caching \        # в свежих версиях включено по умолчанию
#      --api-key "$VLLM_API_KEY"
#
# 2) Клиент — обычный OpenAI SDK. В vLLM temperature/top_p работают (в отличие от новых Claude).
import asyncio, os, time
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key=os.environ["VLLM_API_KEY"])

async def one(i: int) -> tuple[float, float, int]:
    t0 = time.perf_counter(); ttft = None; n = 0
    stream = await client.chat.completions.create(
        model="Qwen/Qwen3-8B",
        messages=[{"role": "user", "content": f"Кратко: что такое continuous batching? #{i}"}],
        max_tokens=300, temperature=0.2, stream=True,
    )
    async for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            ttft = ttft or time.perf_counter() - t0
            n += 1  # чанк ≈ токен; для точности берите usage
    return ttft or 0.0, time.perf_counter() - t0, n

async def main(concurrency: int = 64) -> None:
    t0 = time.perf_counter()
    res = await asyncio.gather(*(one(i) for i in range(concurrency)))
    wall = time.perf_counter() - t0
    ttfts = sorted(r[0] for r in res)
    print(f"p50 TTFT {ttfts[len(ttfts)//2]:.2f}s  p99 {ttfts[int(len(ttfts)*.99)]:.2f}s")
    print(f"суммарно {sum(r[2] for r in res)/wall:.0f} tok/s при {concurrency} параллельных")

asyncio.run(main())
# Локально без GPU: `ollama pull qwen3:8b` и base_url="http://localhost:11434/v1" — тот же код.

Такой нагрузочный скрипт нужен, чтобы получить реальные tok/s для калькулятора выше. Поднимайте concurrency, пока суммарная пропускная способность растёт, а p99 TTFT укладывается в SLO. Эта точка и есть ёмкость одной реплики.

Сборка: middleware LLM-клиента на Go

Собираем всё в одну обёртку. Интерфейс один, реализаций-декораторов несколько, и порядок оборачивания задаёт семантику:

Traced → SemCache → Metered(квоты, $) → Fallback[ для каждого звена: Breaker → Retry → Limiter → клиент провайдера ]

Трейс снаружи видит всё, включая попадания в кэш. Кэш стоит до квот, потому что попадание квоту не тратит. Ретраи и лимитер живут внутри звена: у каждого провайдера свои лимиты, и ретраить A, когда есть B, долго не нужно.

// Retryable: повтор может закончиться иначе. Второе значение — retry-after от сервера.
func Retryable(err error) (bool, time.Duration) {
	var apierr *anthropic.Error
	if errors.As(err, &apierr) {
		switch s := apierr.StatusCode; {
		case s == 408, s == 409, s == 429, s >= 500: // 529 overloaded входит сюда
			return true, retryAfter(apierr.Response)
		default: // 400/401/403/404/413: повтор даст то же самое
			return false, 0
		}
	}
	var ne net.Error
	return errors.As(err, &ne) || errors.Is(err, context.DeadlineExceeded), 0 // таймаут попытки
}

func retryAfter(r *http.Response) time.Duration {
	if r == nil {
		return 0
	}
	sec, _ := strconv.Atoi(r.Header.Get("retry-after"))
	return time.Duration(sec) * time.Second
}

// Budget: ретраев не больше Ratio от числа запросов (как retry budget в Finagle/gRPC).
type Budget struct {
	mu            sync.Mutex
	tokens, Ratio float64
	Max           float64
}

func (b *Budget) onRequest() { b.mu.Lock(); b.tokens = min(b.Max, b.tokens+b.Ratio); b.mu.Unlock() }
func (b *Budget) tryRetry() bool {
	b.mu.Lock()
	defer b.mu.Unlock()
	if b.tokens < 1 {
		return false
	}
	b.tokens--
	return true
}

type Retry struct {
	Next       LLM
	MaxRetries int
	Base, Cap  time.Duration
	Budget     *Budget
}

func (r *Retry) Complete(ctx context.Context, req Request) (*Response, error) {
	r.Budget.onRequest()
	for attempt := 0; ; attempt++ {
		resp, err := r.Next.Complete(ctx, req)
		if err == nil || ctx.Err() != nil {
			return resp, err // родительский дедлайн истёк: не ретраим
		}
		ok, ra := Retryable(err)
		if !ok || attempt == r.MaxRetries || !r.Budget.tryRetry() {
			return nil, err
		}
		d := min(r.Cap, r.Base<<attempt)
		d = max(time.Duration(rand.Int64N(int64(d)+1)), ra) // full jitter, но не раньше retry-after
		if dl, ok := ctx.Deadline(); ok && time.Until(dl) < d {
			return nil, err // не успеем: пусть решает fallback выше
		}
		select {
		case <-ctx.Done():
			return nil, errors.Join(err, ctx.Err())
		case <-time.After(d):
		}
	}
}

// Breaker: closed → (Threshold ошибок подряд) → open → (Cooldown) → half-open (1 проба).
// В проде можно взять sony/gobreaker; логика та же.
type Breaker struct {
	mu        sync.Mutex
	fails     int
	openUntil time.Time
	probing   bool
	Threshold int
	Cooldown  time.Duration
}

func (b *Breaker) Allow() bool {
	b.mu.Lock()
	defer b.mu.Unlock()
	switch {
	case b.fails < b.Threshold:
		return true // closed
	case time.Now().Before(b.openUntil), b.probing:
		return false // open, или проба уже в полёте
	default:
		b.probing = true // half-open: пропускаем ровно один запрос
		return true
	}
}

func (b *Breaker) Report(failed bool) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.probing = false
	if !failed {
		b.fails = 0
		return
	}
	if b.fails++; b.fails >= b.Threshold {
		b.openUntil = time.Now().Add(b.Cooldown)
	}
}

type Route struct {
	Name, Model string
	LLM         LLM                   // уже обёрнут в Retry и Limiter
	Breaker     *Breaker
	Fits        func(Request) bool    // влезет ли контекст, есть ли нужные фичи
	Adapt       func(Request) Request // свой промпт и параметры под модель
}

type Fallback struct{ Routes []Route }

func (f *Fallback) Complete(ctx context.Context, req Request) (*Response, error) {
	var errs []error
	for _, rt := range f.Routes {
		if rt.Fits != nil && !rt.Fits(req) {
			continue
		}
		if !rt.Breaker.Allow() {
			errs = append(errs, fmt.Errorf("%s: circuit open", rt.Name))
			continue
		}
		r := req
		r.Model = rt.Model
		if rt.Adapt != nil {
			r = rt.Adapt(r)
		}
		resp, err := rt.LLM.Complete(ctx, r)
		retryable, _ := Retryable(err)
		rt.Breaker.Report(err != nil && retryable && !isRateLimit(err)) // 429 — наша квота, не авария
		if err == nil {
			resp.Route = rt.Name
			return resp, nil
		}
		if !retryable {
			return nil, err // 400 на A будет 400 и на B: не маскируем баг перебором
		}
		errs = append(errs, fmt.Errorf("%s: %w", rt.Name, err))
		if ctx.Err() != nil {
			break
		}
	}
	return nil, errors.Join(errs...)
}

// Limiter: три token bucket'а под RPM/ITPM/OTPM провайдера, выставленные на ~90% лимита.
type Limiter struct {
	Next            LLM
	RPM, ITPM, OTPM *rate.Limiter
}

func NewLimiter(next LLM, rpm, itpm, otpm float64) *Limiter {
	per := func(v float64) *rate.Limiter { return rate.NewLimiter(rate.Limit(v*0.9/60), int(v*0.9/6)) }
	return &Limiter{Next: next, RPM: per(rpm), ITPM: per(itpm), OTPM: per(otpm)}
}

func (l *Limiter) Complete(ctx context.Context, req Request) (*Response, error) {
	// WaitN сразу вернёт ошибку, если дедлайн ctx не дождётся токенов: бесплатный load shedding.
	if err := l.RPM.Wait(ctx); err != nil {
		return nil, err
	}
	if err := l.ITPM.WaitN(ctx, min(req.EstInputTokens, l.ITPM.Burst())); err != nil {
		return nil, err
	}
	if err := l.OTPM.WaitN(ctx, min(int(req.MaxTokens), l.OTPM.Burst())); err != nil {
		return nil, err
	}
	return l.Next.Complete(ctx, req)
}

// Цены $ за 1M токенов на момент написания (сентябрь 2026).
var prices = map[string]struct{ In, Out float64 }{
	"claude-opus-5":    {5, 25},
	"claude-sonnet-5":  {2, 10},
	"claude-haiku-4-5": {1, 5},
}

func CostUSD(r *Response) float64 {
	p, ok := prices[r.Model]
	if !ok {
		return 0 // неизвестная модель: алертим отдельно, а не падаем
	}
	in := float64(r.InputTokens) + 0.1*float64(r.CacheReadTokens) + 1.25*float64(r.CacheWriteTokens)
	return (in*p.In + float64(r.OutputTokens)*p.Out) / 1e6
}

var ErrQuota = errors.New("llm: tenant budget exceeded")

// Metered: проверка квоты тенанта до вызова и учёт фактической стоимости после.
type Metered struct {
	Next  LLM
	Spent func(ctx context.Context, tenant string) (usd float64, err error) // напр. Redis GET
	Add   func(ctx context.Context, tenant string, usd float64) error       // INCRBYFLOAT + EXPIRE
	Limit func(tenant string) float64
}

func (m *Metered) Complete(ctx context.Context, req Request) (*Response, error) {
	spent, err := m.Spent(ctx, req.Tenant)
	if err == nil && spent >= m.Limit(req.Tenant) {
		return nil, ErrQuota // при ошибке Redis — fail-open: квота мягкая, логируем
	}
	resp, err := m.Next.Complete(ctx, req)
	if err != nil {
		return nil, err
	}
	_ = m.Add(ctx, req.Tenant, CostUSD(resp))
	return resp, nil
}

type SemCache struct {
	Next      LLM
	DB        *pgxpool.Pool
	Embed     func(ctx context.Context, text string) ([]float32, error)
	Threshold float64       // cosine similarity; калибруется на размеченных парах
	TTL       time.Duration
}

func (c *SemCache) Complete(ctx context.Context, req Request) (*Response, error) {
	q := lastUserText(req)
	if q == "" || len(req.Messages) > 1 { // кэшируем только первый вопрос без истории
		return c.Next.Complete(ctx, req)
	}
	emb, err := c.Embed(ctx, q)
	if err != nil {
		return c.Next.Complete(ctx, req) // кэш — оптимизация, а не точка отказа
	}
	vec, scope := pgvector.NewVector(emb), scopeKey(req)

	var text string
	var sim float64
	err = c.DB.QueryRow(ctx, `
		SELECT response, 1 - (embedding <=> $1) FROM llm_cache
		WHERE scope = $2 AND created_at > now() - make_interval(secs => $3)
		ORDER BY embedding <=> $1 LIMIT 1`, vec, scope, c.TTL.Seconds()).Scan(&text, &sim)
	switch {
	case err == nil && sim >= c.Threshold:
		return &Response{Text: text, Model: req.Model, StopReason: "end_turn", Route: "semcache"}, nil
	case err != nil && !errors.Is(err, pgx.ErrNoRows):
		slog.WarnContext(ctx, "semcache lookup", "err", err)
	}

	resp, err := c.Next.Complete(ctx, req)
	if err != nil {
		return nil, err
	}
	if resp.StopReason == "end_turn" { // не кэшируем обрезанные ответы и refusal
		if _, err := c.DB.Exec(ctx, `INSERT INTO llm_cache (scope, query, embedding, response)
			VALUES ($1, $2, $3, $4)`, scope, q, vec, resp.Text); err != nil {
			slog.WarnContext(ctx, "semcache store", "err", err)
		}
	}
	return resp, nil
}

func scopeKey(r Request) string {
	h := sha256.Sum256([]byte(r.Tenant + "\x00" + r.Model + "\x00" + r.System))
	return hex.EncodeToString(h[:])
}

// Anthropic — нижний слой. Ретраи SDK выключены: они живут в нашем Retry.
func Anthropic() LLM {
	c := anthropic.NewClient(option.WithMaxRetries(0))
	return Func(func(ctx context.Context, req Request) (*Response, error) {
		msg, err := c.Messages.New(ctx, anthropic.MessageNewParams{
			Model:     anthropic.Model(req.Model),
			MaxTokens: req.MaxTokens,
			System:    []anthropic.TextBlockParam{{Text: req.System}},
			Messages:  req.Messages,
		})
		if err != nil {
			return nil, err
		}
		out := &Response{
			Model: string(msg.Model), StopReason: string(msg.StopReason),
			InputTokens: msg.Usage.InputTokens, OutputTokens: msg.Usage.OutputTokens,
			CacheReadTokens:  msg.Usage.CacheReadInputTokens,
			CacheWriteTokens: msg.Usage.CacheCreationInputTokens,
		}
		for _, b := range msg.Content {
			if t, ok := b.AsAny().(anthropic.TextBlock); ok {
				out.Text += t.Text
			}
		}
		return out, nil
	})
}

Самопроверка

Почему jitter важнее, чем точное значение base delay?

Без jitter все клиенты, получившие ошибку одновременно, повторяют запрос тоже одновременно: t + base·2ⁿ одинаково у всех. Каждая волна повторов снова превышает ёмкость, и система не выходит из перегрузки. Jitter рассинхронизирует клиентов и превращает пики в ровный поток. Base delay лишь масштабирует картину, а синхронность от него не зависит.

Какие ответы API не надо ретраить и почему 404 — особый случай?

400, 401, 402, 403, 404, 413: запрос или доступ некорректен, и повтор даст то же самое. 404 у Anthropic означает неверный id модели или модель, недоступную организации. Ретрай бесполезен, но fallback на другую модель поможет, поэтому в роутере 404 разумно трактовать как «звено непригодно», а не как фатальную ошибку запроса. Заодно нужен алерт: скорее всего, модель сняли с поддержки.

Зачем при стриминге отдельный TTFT-таймаут, если есть общий?

Общий таймаут должен покрывать самую длинную легитимную генерацию, то есть минуты. Если ждать его при зависшем провайдере, вы потеряете минуты вместо секунд. TTFT-дедлайн ловит «провайдер не начал отвечать» за 5–20 секунд и оставляет время на fallback. Idle timeout ловит обрыв посреди стрима.

Почему 429 не должен открывать circuit breaker, а 529 должен?

429 значит, что вы превысили свою квоту. Провайдер здоров, и через retry-after всё заработает, так что уместны ожидание или временный пропуск звена. 529 или 5xx означают проблему на стороне провайдера. Breaker защищает и вас (не ждать таймауты), и провайдера (не добивать). Если открывать breaker на 429, короткий всплеск трафика надолго уведёт весь трафик на fallback.

Как prompt caching влияет на rate limits у Anthropic?

Для большинства актуальных моделей cache_read_input_tokens не учитываются в ITPM. При длинном стабильном префиксе эффективная пропускная способность по input растёт кратно, и одновременно input дешевеет до 0.1×. Проверять по документации конкретной модели.

Назовите три причины ложных попаданий в семантический кэш и три меры защиты.

Причины: embedding плохо различает отрицание («отменить» и «не отменять»), числа, даты и сущности («Pro» и «Team»); общий scope для разных тенантов или прав доступа; слишком низкий порог. Меры: калибровка порога на размеченных парах, scope с тенантом, версией промпта и правами, верификация попадания дешёвой моделью, исключение персонализированных и временных запросов, TTL и инвалидация по документам.

Какой рычаг латентности обычно самый сильный и почему?

Сокращение числа выходных токенов, потому что генерация идёт последовательно (десятки или сотни tok/s), и 1000 токенов вывода стоят больше, чем prefill 20K токенов input. Для воспринимаемой латентности — стриминг. Следом идут модель поменьше или низкий effort и кэши.

Что такое PagedAttention и continuous batching простыми словами?

PagedAttention хранит KV-cache страницами фиксированного размера, выделяемыми по требованию, как виртуальная память. Не нужно резервировать память под максимальную длину, фрагментация почти нулевая, а общие префиксы можно разделять, поэтому в GPU помещается больше одновременных запросов. Continuous batching собирает батч заново на каждом шаге декодирования: завершившиеся запросы уходят, новые встают на их место, и GPU не простаивает в ожидании самой длинной последовательности.

Когда self-hosted экономически проигрывает, даже при большом объёме?

При неровной нагрузке (пики днём, простой ночью), когда утилизация ниже 20–30%; когда нужна модель уровня frontier, которую сами не поднять; когда учтены инженерное время и HA-реплики; когда API-цены падают быстрее, чем окупается резерв GPU. И если self-hosted модель хуже по evals, экономия фиктивная.

Вопросы с собеседований

Провайдер LLM лёг на 20 минут. Что происходит с вашим сервисом и что вы спроектировали заранее?

Детекция. Circuit breaker на звене открывается после N ошибок 5xx или 529 либо TTFT-таймаутов. Алерт срабатывает по error rate и доле трафика на fallback.

Деградация по ступеням. Цепочка fallback: другая модель того же провайдера (часто перегрузка касается одной модели), тот же провайдер через другое облако (Bedrock или Vertex, отдельная ёмкость), другой провайдер с адаптированным промптом, кэш, деградированный ответ. На каждое звено прогнан eval, и известно, насколько оно хуже.

Защита от самоповреждения. Ретраи только на одном слое, с jitter и retry budget, чтобы при восстановлении не устроить thundering herd. Лимиты расходов действуют и на fallback. Фоновые задачи ставятся на паузу или уходят в очередь или Batch API, интерактивный трафик приоритетен.

Регулярная проверка. Fallback-путь получает 1% трафика постоянно, а раз в квартал проводится game day.

Чего не говорить: «SDK сам ретраит». Два ретрая SDK от 20-минутного инцидента не спасут и только добавят нагрузки.

Как вы спроектируете rate limiting для мультитенантного LLM-сервиса поверх провайдера с лимитами RPM/ITPM/OTPM?

Два уровня. Нижний — защита квоты провайдера: token bucket по трём измерениям на модель, выставленный на ~90% лимита. Input оценивается через count_tokens или эвристику, output резервируется по max_tokens. При нескольких репликах лимит либо делится поровну, либо хранится в Redis (GCRA), и я объясню компромисс: точность против лишнего hop и точки отказа.

Верхний — справедливость: per-tenant лимиты по тарифу, взвешенная очередь (WFQ), приоритет интерактивного трафика над фоновым, бюджеты в долларах на тенанта.

Перегрузка обрабатывается ожиданием с дедлайном (WaitN с ctx), а при невозможности уложиться — быстрым 429 со своим retry-after клиенту. Мониторинг: заголовки anthropic-ratelimit-*-remaining и доля 429 от провайдера, которая при правильном лимитере близка к нулю. Отдельно упомяну, что prompt caching снижает давление на ITPM, а Batch API уводит офлайн-нагрузку из общей ёмкости.

Латентность RAG-чата p50 = 9 секунд. Как будете ускорять?

Сначала измерить: трейс с разбивкой по этапам и отдельно TTFT и общее время. Почти всегда окажется, что LLM-генерация занимает 70–90%.

Дальше по силе эффекта: (1) стриминг, и воспринимаемая латентность падает до TTFT; (2) короче вывод: формат, max_tokens, «без повтора вопроса»; (3) модель поменьше или ниже effort для простых вопросов, с роутингом по сложности и проверкой evals; (4) prompt caching стабильного префикса (system, инструкции) снижает TTFT и стоимость; (5) параллельный retrieval и guardrail параллельно с генерацией; (6) меньше контекста: top-k после rerank 5 вместо 20, так что prefill короче и качество часто выше; (7) семантический кэш для FAQ-нагрузки.

Отдельно назову метрики: p50 и p99 TTFT, время до полного ответа, и сравнение A/B по качеству, чтобы ускорение не стало деградацией.

Нужен ли вам семантический кэш? Какие у него риски?

Нужен, только если в трафике много повторяющихся намерений и ответ не персонализирован: FAQ поддержки, справка по продукту. В B2B-копилоте с уникальными запросами hit rate будет 2–5% при заметном риске. Сначала я бы посчитал потенциальный hit rate на логах.

Риски: ложные попадания (отрицания, числа, сущности), из-за которых пользователь получает уверенный неправильный ответ; утечка между тенантами или правами доступа при плохом scope; устаревание после изменения документов или промпта. Защита: калибровка порога на размеченных парах под целевую долю ложных попаданий, scope ключа, верификация попадания дешёвой моделью, TTL и инвалидация по документам, метрики hit rate и «отзывов» ответов.

Для большинства продуктов prompt caching даёт больше при нулевом риске, и начинать стоит с него.

Какую observability вы строите для LLM-приложения? Что пишете в логи?

OpenTelemetry с GenAI semantic conventions: спан на каждый LLM-вызов с gen_ai.request.model, gen_ai.usage.*, finish_reasons, response.id, вложенные спаны retrieve, rerank, execute_tool, для агентов — invoke_agent. Метрики: токены, стоимость по tenant и feature, TTFT, cache hit rate, доля max_tokens и refusal, доля трафика по звеньям fallback.

Бэкенды через OTel Collector: SRE-стек (Tempo, Prometheus) и Langfuse для AI-команды: разбор диалогов, датасеты для evals, онлайн-оценки.

Содержимое промптов и ответов пишется по opt-in, с маскированием PII в коллекторе, сэмплированием (100% метаданных, 1–5% текста и все ошибки), retention 30 дней, отдельными правами доступа и процедурой удаления. user_id хэшируется через HMAC.

Как вы строите guardrails и как понимаете, что они работают?

Слои: вход (размер, injection или jailbreak-классификатор, тематический фильтр, PII), выход (structured outputs плюс проверка бизнес-правил, утечки, groundedness для RAG), инструменты (allowlist, валидация аргументов, human-in-the-loop на необратимое). Сначала дешёвые проверки (правила), дорогие LLM-судьи только по сигналу. Input guardrail запускается параллельно с основным вызовом с отменой через ctx.

«Работают» — это измеряемо: у каждого guardrail есть размеченный набор и precision и recall, а в проде отслеживаются доля срабатываний и выборочная ручная проверка. False positive считается продуктовой ошибкой, over-refusal убивает конверсию. Для каждого guardrail явно выбран fail-open или fail-closed при недоступности. И я говорю, что system prompt — не guardrail: гарантии дают только проверки вне модели.

Когда вы бы предложили self-hosted модель вместо API? Посчитайте на примере.

Критерии: требования к данным (данные не могут уходить третьей стороне, резидентность), большой и ровный объём, достаточность модели 8–70B по evals (извлечение, классификация, суммаризация, а не сложный reasoning), потребность в своей fine-tuned модели, контроль латентности.

Расчёт: 2 млрд токенов в день; API по смешанной цене $2 за 1M обходится в ~$120K в месяц. GPU за $3 в час с 2500 tok/s при утилизации 40% даёт ~86M токенов в день на GPU, то есть нужно 24 GPU, или ~$52K в месяц, плюс люди ~$10–20K. Выигрыш есть, но он чувствителен к утилизации: при 20% GPU нужно вдвое больше, и преимущество почти исчезает. Реальные tok/s надо измерить нагрузочным тестом на своей длине запросов.

Упомяну скрытые затраты (пики, HA, дежурства, обновления) и гибрид: self-hosted для массовой простой нагрузки, API для сложного и как fallback.

Агент в проде иногда тратит $40 на одну задачу. Что делать?

Немедленно: жёсткие лимиты на задачу по итерациям, токенам и долларам с остановкой и частичным результатом, плюс алерт на выбросы.

Диагностика по трейсам: где растёт контекст (tool results на десятки тысяч токенов, которые можно усечь или суммаризировать), есть ли зацикливание (одинаковые tool calls подряд, детектится по хэшу аргументов), работает ли prompt caching (cache_read около нуля означает, что префикс меняется на каждой итерации).

Лечение: компактизация истории, усечение результатов инструментов, кэширование стабильного префикса, маленькая модель для подшагов и роутинг, более явные критерии остановки в промпте. После исправлений — eval на наборе «дорогих» задач, чтобы убедиться, что качество не упало.
