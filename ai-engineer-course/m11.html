Кодинг с LLM-интеграцией: типовые задачи

Задачи этого раунда почти всегда вариации пяти тем. Если вы можете написать каждую за 20–30 минут без документации, раунд пройден.

  1. Вызвать модель, распарсить ответ, обработать 429/5xx с экспоненциальным backoff и jitter, уважать retry-after.
  2. Стриминг: прочитать SSE, собрать текст из content_block_delta, корректно обработать обрыв и отмену через context.
  3. Цикл tool use: выполнить инструменты (параллельно, если их несколько), вернуть все tool_result одним сообщением, ограничить число шагов.
  4. Мини-RAG в памяти: чанкинг, эмбеддинги (или заглушка), косинусная близость, top-k, промпт с цитатами.
  5. Извлечение структуры: JSON Schema, валидация, повтор при невалидном ответе, eval на 10 примерах.
// Классика раунда: вызов с ретраями. Интервьюер смотрит на context, jitter, retry-after и типы ошибок.
func callWithRetry(ctx context.Context, do func(context.Context) (*http.Response, error)) (*http.Response, error) {
	const maxAttempts = 4
	backoff := 500 * time.Millisecond
	for attempt := 1; ; attempt++ {
		resp, err := do(ctx)
		if err == nil && resp.StatusCode < 300 {
			return resp, nil
		}
		retryable := err != nil // сетевые ошибки ретраим
		wait := backoff + time.Duration(rand.Int63n(int64(backoff))) // full jitter поверх базы
		if resp != nil {
			switch resp.StatusCode {
			case 408, 409, 429, 500, 502, 503, 504, 529:
				retryable = true
				if s, perr := strconv.Atoi(resp.Header.Get("retry-after")); perr == nil {
					wait = time.Duration(s) * time.Second
				}
			}
			resp.Body.Close()
		}
		if !retryable || attempt == maxAttempts {
			if err == nil {
				err = fmt.Errorf("status %d after %d attempts", resp.StatusCode, attempt)
			}
			return nil, err
		}
		select {
		case <-time.After(wait):
			backoff *= 2
		case <-ctx.Done():
			return nil, ctx.Err()
		}
	}
}

В продакшене это делает SDK (по умолчанию 2 ретрая на 408/409/429/5xx), но на интервью просят написать самому и объяснить, почему нельзя ретраить 400 и почему без jitter получится синхронный шторм.

Частые концептуальные вопросы

32 вопроса, которые встречаются чаще всего на скрининге, в начале system design и на deep dive. Ответы здесь — эталон уровня сеньора: суть, компромиссы, цифры. Не заучивайте дословно: научитесь воспроизводить структуру ответа своими словами за 60–90 секунд. Все вопросы доступны ниже в режиме флеш-карточек.

LLM-основы

Что такое токен и почему инженеру важно о нём думать?

Токен — единица, на которую токенизатор (обычно BPE) режет текст; модель видит и генерирует токены, а не символы. От числа токенов зависят стоимость (цена за 1M вход/выход), латентность (генерация идёт по токену), лимиты (контекстное окно, max_tokens, ITPM/OTPM). Для английского ≈ 4 символа на токен, для русского и кода токенов больше, поэтому одна и та же фича на русском стоит дороже. Токенизация объясняет и странности: модели плохо считают буквы в слове, потому что не видят букв.

Как работают temperature и top_p, и как управлять поведением на новых моделях Claude?

Модель выдаёт распределение над словарём; temperature делит логиты перед softmax (меньше — распределение острее, ближе к greedy), top_p оставляет минимальный набор токенов с суммарной вероятностью p. На open-source моделях (vLLM, Ollama) и у ряда провайдеров это основные ручки. На новейших моделях Anthropic (Opus 4.7+, Sonnet 5, Fable) temperature и top_p удалены из API (запрос с ними вернёт 400); поведение управляется промптом, effort (output_config.effort) и structured outputs. Важно понимать: даже temperature=0 не даёт полного детерминизма из-за батчинга и численных эффектов на GPU, поэтому тесты строятся на evals, а не на точном совпадении.

Контекстное окно 1M токенов — почему бы не класть туда всё?

Потому что это дорого, медленно и не всегда качественно. 500K токенов входа на Sonnet 5 стоят $1 за запрос, TTFT растёт с длиной промпта, а качество поиска нужного факта в середине длинного контекста ниже, чем в начале и конце (эффект lost in the middle, у новых моделей слабее, но есть). Длинный контекст хорош для разовых задач над одним большим документом, особенно с prompt caching. Для частых запросов к большой базе RAG дешевле на порядки и даёт цитаты.

Что такое эмбеддинг и чем эмбеддинг-модель отличается от генеративной?

Эмбеддинг — вектор фиксированной длины (768–3072 чисел), в котором семантически близкие тексты находятся близко по косинусной мере. Эмбеддинг-модель (обычно энкодер) обучена contrastive-задаче: сближать пары «запрос — релевантный документ». Генеративная модель предсказывает следующий токен. Эмбеддинги дешевле на порядки и используются для поиска, кластеризации, дедупликации, классификации. Важно: векторы разных моделей несравнимы, смена модели означает полную переиндексацию.

Почему LLM галлюцинирует и как это снижать в продукте?

Модель обучена порождать правдоподобное продолжение, а не проверять истинность; когда знания нет или оно размыто, правдоподобный текст всё равно генерируется. Снижение: заземление (RAG с требованием цитат и разрешением сказать «не знаю»), порог по retrieval-скору, чтобы не генерировать без источников, structured output с полями-цитатами и программной проверкой, проверка утверждений отдельным вызовом, более сильная модель на критичных шагах, человек в контуре при высокой цене ошибки. И измерение: faithfulness-метрика на golden set, а не ощущения.

Чем KV-cache отличается от prompt caching?

KV-cache — механизм внутри одного запроса: при генерации каждого нового токена ключи и значения attention для предыдущих токенов не пересчитываются. Он делает генерацию линейной по длине вместо квадратичной и занимает много памяти GPU. Prompt caching — сохранение KV-cache префикса между запросами на стороне провайдера: если следующий запрос начинается с тех же байт (tools → system → messages), префикс не пересчитывается. У Anthropic чтение кэша ≈ 0.1× цены входа, запись 1.25× (TTL 5 мин) или 2× (1 ч), до 4 breakpoint'ов. Любое изменение в префиксе (timestamp в system prompt) инвалидирует всё после него; проверка — usage.cache_read_input_tokens.

RAG

Опишите RAG-пайплайн end to end.

Офлайн: загрузка источников → парсинг (PDF, HTML, таблицы) → чанкинг с учётом структуры → эмбеддинги → запись в индекс вместе с метаданными (источник, дата, ACL). Онлайн: (опционально) переписывание запроса → эмбеддинг → гибридный поиск (вектор + BM25) с фильтром по правам → слияние (RRF) → rerank → сборка контекста с идентификаторами → генерация с требованием цитат → проверка цитат. Вокруг: evals на каждом шаге (retrieval отдельно от генерации), инкрементальный ingest, трейсинг. На интервью важно сказать, что большинство проблем RAG — это проблемы retrieval, а не генерации.

Как выбрать размер чанка?

Компромисс: маленькие чанки (200–300 токенов) точнее матчатся с запросом, но теряют контекст; большие (800–1500) несут контекст, но размывают эмбеддинг и тратят окно. Стартовая точка 400–600 токенов с перекрытием 10–15%, разбиение по структуре документа (заголовки, абзацы, функции в коде), а не по символам. Приёмы: small-to-big (ищем по мелким, отдаём родительский раздел), добавление заголовка документа и раздела в чанк (contextual chunking). Окончательно — по eval: recall@k на golden set для 2–3 вариантов.

Зачем гибридный поиск и что такое RRF?

Векторный поиск хорош в синонимах и перефразах, но плохо находит точные строки: коды ошибок, артикулы, имена функций, редкие термины. BM25 наоборот. Гибрид запускает оба и сливает результаты. RRF (Reciprocal Rank Fusion) складывает 1/(k + rank) по каждому списку (k ≈ 60): не требует калибровки скоров разной природы и устойчив. На практике гибрид даёт заметный прирост recall почти всегда, когда в корпусе есть идентификаторы.

Bi-encoder и cross-encoder: в чём разница и зачем rerank?

Bi-encoder кодирует запрос и документ независимо, документы можно закодировать заранее — это и есть эмбеддинги для ANN; быстро, но документ сжат в один вектор без знания запроса. Cross-encoder получает пару (запрос, документ) целиком и выдаёт скор релевантности — точнее, но надо прогонять каждую пару в момент запроса. Поэтому двухстадийно: ANN достаёт top-50..100, cross-encoder переранжирует до top-5..10. Цена — 50–200 мс и GPU или вызов rerank-API; выигрыш — обычно несколько пунктов nDCG и меньше мусора в контексте.

RAG дал плохой ответ. Как вы будете отлаживать?

По трейсу, послойно. (1) Был ли нужный документ в индексе вообще (ingest, парсинг, права)? (2) Попал ли он в top-k retrieval? Если нет — проблема запроса (переписывание), чанкинга, эмбеддингов или фильтров. (3) Попал, но rerank его опустил? (4) Был в контексте, но модель его не использовала или исказила — промпт, порядок, длина контекста, модель. Каждую найденную причину превращаю в кейс golden set, чтобы регрессия ловилась в CI. Отдельные метрики retrieval (recall@k) и генерации (faithfulness) позволяют не гадать.

RAG, fine-tuning или длинный контекст: как выбрать?

RAG — для знаний, которые меняются, большие по объёму, требуют прав доступа и цитат. Длинный контекст — для разовой работы с конкретными документами целиком, особенно с prompt caching, и для небольших стабильных баз. Fine-tuning — не для знаний, а для поведения: формат, стиль, узкая задача (классификация, извлечение), где нужно снизить цену и латентность, перейдя на маленькую модель. Они комбинируются: fine-tuned маленькая модель как reranker или классификатор внутри RAG.

Агенты и MCP

Чем workflow отличается от агента, и что вы выберете по умолчанию?

По определению Anthropic, workflow — LLM и инструменты оркестрируются по заранее заданным путям в коде (цепочки, роутинг, параллелизация, orchestrator-workers, evaluator-optimizer). Агент — модель сама решает, какие шаги делать и когда остановиться, в цикле с инструментами. По умолчанию workflow: он дешевле, быстрее, предсказуемее и тестируется как обычный код. Агент оправдан, когда путь решения нельзя предсказать заранее (исследование кодовой базы, отладка, открытые задачи), и стоит лимитов на шаги, бюджет и чёткой среды с обратной связью.

Как работает tool use на уровне API?

В запросе передаются описания инструментов (имя, описание, JSON Schema входа). Модель отвечает блоком tool_use с id и аргументами, stop_reason: "tool_use". Код исполняет инструмент и отправляет следующее user-сообщение с блоком tool_result (tool_use_id, содержимое, is_error: true при ошибке). Если модель запросила несколько инструментов в одном ответе, их выполняют конкурентно и возвращают все результаты одним сообщением. Цикл продолжается до end_turn или лимита шагов. Модель ничего не исполняет сама — все побочные эффекты и права в вашем коде.

Что такое MCP и какую проблему он решает?

Model Context Protocol — открытый протокол (JSON-RPC 2.0) для подключения инструментов и данных к LLM-приложениям. Сервер предоставляет tools, resources и prompts; клиент (Claude Code, Claude Desktop, IDE, ваш агент) их обнаруживает и вызывает. Транспорты: stdio для локальных серверов и Streamable HTTP для удалённых. Решает проблему M×N интеграций: вместо того чтобы каждое приложение писало свой коннектор к каждой системе, система публикует один MCP-сервер. Для Go есть официальный SDK github.com/modelcontextprotocol/go-sdk. Риски: сторонний сервер — это чужой код и чужие описания инструментов в вашем контексте (tool poisoning), поэтому allowlist и ревью.

Как ограничить агента, чтобы он не натворил дел?

Бюджеты: максимум шагов, токенов, времени и денег на задачу. Права: least privilege у каждого инструмента, отдельные креды на агента, read-only по умолчанию, песочница для исполнения кода (контейнер без сети или с egress allowlist). Подтверждение человеком для необратимых действий (отправка, удаление, платежи). Валидация аргументов инструментов в коде. Аудит всех вызовов. Детектор зацикливания. И evals на траекториях, а не только на финальном ответе.

Что такое «lethal trifecta» и как с ней жить?

Термин Саймона Уиллисона: агент опасен, когда одновременно (1) имеет доступ к приватным данным, (2) обрабатывает недоверенный контент (веб, письма, документы, issue), (3) может передавать данные наружу (HTTP-запросы, отправка писем, даже markdown-картинки с URL). Prompt injection в недоверенном контенте тогда может увести данные. Надёжного детектора инъекций нет, поэтому защита архитектурная: разорвать одну из трёх ног для конкретного сценария — например, убрать внешние запросы или разделить агента на читающего недоверенное без доступа к секретам и действующего без доступа к недоверенному.

Evals

Как построить golden set с нуля?

Начать с реальных данных: логи запросов, тикеты, вопросы пользователей; если продукта ещё нет — вопросы от экспертов домена и синтетика, сгенерированная по документам и отфильтрованная людьми. Стратифицировать по типам запросов и сложности, обязательно включить edge cases: нет ответа в базе, неоднозначные, adversarial. Для каждого — ожидаемый результат в проверяемой форме (правильные документы, ключевые факты, эталонный SQL). 50–100 примеров для старта, 300–500 для уверенных сравнений. Версионировать как код, пополнять из прод-ошибок. Главное — посмотреть глазами на 100+ реальных ответов до того, как придумывать метрики (error analysis).

LLM-as-a-judge: какие проблемы и как их решать?

Проблемы: позиционный bias (в попарном сравнении предпочитает первый вариант), bias к длинным ответам, self-preference (любит ответы своей модели), нестабильность шкал 1–10. Решения: бинарные или узкие критерии («каждое утверждение подкреплено контекстом: да/нет») вместо общей оценки; попарное сравнение с перестановкой порядка; рассуждение перед вердиктом; судья сильнее или другого семейства, чем генератор. И калибровка: 100–200 примеров размечают люди, считаем согласие судьи с людьми (accuracy, Cohen's kappa), итерируем промпт судьи, пока согласие не станет сопоставимым с согласием между людьми.

Offline и online evals: зачем оба?

Offline — на фиксированном наборе до релиза: быстро, воспроизводимо, гейт в CI, но набор отстаёт от реальности. Online — на реальном трафике: явный фидбек, неявные сигналы (переформулировки, эскалации, копирование ответа), judge на выборке, A/B. Ловит дрейф входов и то, чего нет в наборе. Цикл: online находит новые классы ошибок → они попадают в offline-набор → регрессия больше не пройдёт незамеченной.

Какие метрики retrieval вы знаете и когда какую использовать?

Recall@k — доля релевантных документов, попавших в top-k; главная для RAG, потому что генератор не увидит то, что не нашли. Precision@k — доля релевантных среди top-k; важна, когда контекст дорог или шум путает модель. MRR — средний 1/ранг первого релевантного; для сценариев «нужен один правильный ответ». nDCG@k — учитывает градации релевантности и позицию; стандарт для поиска с ранжированием. Плюс ANN-recall — насколько приближённый поиск совпадает с точным, это метрика инфраструктуры.

Как встроить evals в CI и не получить flaky-тесты?

Не требовать 100% прохождения отдельных кейсов: гейт по агрегированной метрике с порогом и допуском (например, faithfulness не ниже baseline − 2 п.п.). Детерминированные проверки (схема, наличие цитат, запрещённые строки) — жёсткие, как unit-тесты. Кэшировать ответы модели по хэшу (промпт, модель, вход), чтобы повторные прогоны без изменений были бесплатными и стабильными. Быстрый smoke-набор (30–50 кейсов) на каждый PR, полный — ночью или перед релизом. Отчёт с диффом по кейсам, а не только числом.

Продакшн

Как вы обрабатываете 429, 5xx и 529 от провайдера?

429 (rate limit) — ретрай с экспоненциальным backoff и jitter, с учётом retry-after; на уровне системы — собственный rate limiter перед провайдером, чтобы не упираться в лимит, и приоритизация трафика. 5xx и 529 (overloaded) — ретрай с backoff, circuit breaker на модель/провайдера, fallback на другую модель или регион. 400 не ретраить: это ошибка запроса. Общий бюджет ретраев, чтобы не устроить шторм, и согласование ретраев на разных уровнях (SDK, gateway, клиент), иначе они перемножаются. Для стрима — ретрай возможен только до первого отданного пользователю токена.

Зачем стриминг и какие у него сложности?

Стриминг сокращает воспринимаемую латентность: пользователь видит первые слова через TTFT (сотни мс) вместо полного ответа через 5–15 с; для длинных выводов он ещё и нужен, чтобы не упереться в HTTP-таймауты. Сложности: прокси и балансировщики буферизуют ответ (нужно отключать буферизацию), таймауты на idle-соединения (события ping), обрыв посередине (что показать, как учесть токены), модерация и валидация вывода, который уже ушёл пользователю, парсинг частичного JSON для tool use (input_json_delta), отмена генерации при уходе клиента через context.

Как гарантировать, что модель вернёт валидный JSON?

Использовать structured outputs: у Anthropic — output_config.format с JSON Schema или strict: true у tools; декодирование ограничено схемой, и невалидный по синтаксису JSON не возвращается. Инструкция «ответь JSON» без этого даёт битый вывод в доле процента, что на миллионах запросов превращается в тысячи ошибок. Prefill ответа на новых моделях Claude не поддерживается (400). Но валидность по схеме не равна правильности значений: семантическая проверка (диапазоны, существование id, согласованность полей) остаётся в коде.

Что должно быть в observability LLM-системы?

Трейс на запрос (OpenTelemetry с атрибутами gen_ai.*): спаны retrieval, rerank, каждого вызова модели и инструмента; модель, версия промпта, токены (вход, выход, cache read/write), стоимость, stop_reason, латентность и TTFT, id найденных документов. Метрики: p50/p95/p99, ошибки по типам, $ по фичам, доля cache hit. Качество: фидбек, онлайн-judge, эскалации. Хранилище промптов и ответов с контролем доступа из-за PII. Инструменты: Langfuse, Arize Phoenix, LangSmith или своё на OTel + ClickHouse + Grafana.

Какие виды кэширования есть в LLM-системах?

(1) Prompt caching провайдера — повторное использование префикса, 0.1× цены входа, почти всегда включать для стабильных системных промптов и инструментов. (2) Точный кэш ответов — хэш от модели, параметров и сообщений; безопасен, но хит-рейт низкий, кроме FAQ-подобных сценариев. (3) Семантический кэш — ответ на «похожий» запрос по близости эмбеддингов; высокий хит-рейт, но риск неверного ответа на похожий по форме, но другой по смыслу вопрос и утечки между пользователями — только с высоким порогом и там, где ответ не персональный. (4) Кэш эмбеддингов и результатов retrieval.

Стоимость

Как быстро оценить стоимость LLM-фичи?

Запросов в месяц × (токены входа × цена входа + токены выхода × цена выхода) / 1M, с поправками: доля кэшированного префикса по 0.1×, число вызовов модели на запрос (агенты), доля хитов кэша ответов, −50% для batch. Пример: 1M запросов, 4K вход, 400 выход на Sonnet 5 ($2/$10): $8K + $4K = $12K/мес. Дальше сравнить с ценностью: выручка на пользователя, сэкономленное время сотрудников, стоимость живого оператора.

Как снизить стоимость в 5 раз без потери качества?

По порядку эффекта: (1) роутинг — простые запросы на маленькую модель (Haiku 4.5 в 2–5 раз дешевле Sonnet/Opus), решает классификатор или каскад с эскалацией по уверенности; (2) prompt caching стабильного префикса — вход дешевеет до 10 раз на кэшированной части; (3) сокращение контекста — rerank и меньше чанков, обрезка истории; (4) короче вывод — structured output, лимиты; (5) batch для всего, что не интерактивно (−50%); (6) кэш ответов для повторяющихся запросов. Каждый шаг проверяется eval-набором: «без потери качества» — это измеряемое утверждение, а не надежда.

Когда self-hosted модель выгоднее API?

Когда загрузка GPU высокая и стабильная (амортизация железа), задача узкая и маленькая модель (7–30B, после fine-tuning) достигает нужного качества, или есть требования к данным и латентности. TCO включает GPU (часы или покупку), инференс-сервер (vLLM, TGI), инженеров, мониторинг, обновления моделей, резервирование. Типичная ошибка — сравнивать цену GPU-часа с ценой токенов при 100% загрузке, хотя реальная загрузка 20–40%. Для большинства продуктов API выгоднее до очень большого объёма.

Когда использовать Batch API?

Для любых задач, где результат не нужен сразу: ночная обработка документов, суммаризация звонков, генерация описаний, прогон evals, разметка данных, бэкфилл эмбеддингов. Скидка 50%, асинхронно, результат до 24 часов (обычно быстрее), не конкурирует с синхронными лимитами. Нюансы: результаты приходят в произвольном порядке — матчить по custom_id; часть запросов может завершиться с ошибкой или истечь — нужен повтор; prompt caching тоже работает внутри батча.

Почему агенты так дорого стоят и что с этим делать?

Каждый шаг агента заново отправляет всю историю: системный промпт, описания инструментов, все прошлые вызовы и результаты. Суммарный вход растёт примерно квадратично по числу шагов, а результаты инструментов бывают огромными (листинг файлов, ответ API). Меры: prompt caching (префикс и история кэшируются), обрезка и суммаризация результатов инструментов, компактизация истории, лимиты шагов, субагенты с чистым контекстом для подзадач, дешёвая модель для рутинных шагов и сильная для планирования.

Пример: RAG по документации на Go

Задача. У платформенной команды ≈ 3 000 страниц в Confluence и 400 README в репозиториях; 300 инженеров задавали одни и те же вопросы в Slack, дежурный тратил около 15 часов в неделю на ответы.

Решение. Я спроектировал и написал сервис на Go: ingest из Confluence и Git по webhook, чанкинг по заголовкам (≈ 500 токенов, код-блоки не режутся), эмбеддинги в Postgres с pgvector (HNSW), гибридный поиск с tsvector и RRF, rerank top-30, генерация на Sonnet со стримингом через SSE и обязательными цитатами; поверх — Slack-бот. pgvector выбрал вместо отдельной векторной БД: 60K чанков, фильтр по правам в том же SQL-запросе, одна база в эксплуатации. Отдельную векторную БД рассматривал, но на таком объёме она давала только операционную сложность.

Метрики. Собрал golden set из 120 реальных вопросов из истории Slack с правильными страницами. Recall@5 вырос с 0.62 до 0.87 за счёт гибрида и rerank; faithfulness 0.91 по LLM-судье, откалиброванному на 100 ответах, размеченных мной и коллегой (согласие 88%). p95 TTFT 1.2 с, стоимость ≈ $0.004 за вопрос, ≈ $180 в месяц. Повторяющиеся вопросы в канале поддержки сократились на 40% за два месяца.

Ошибки. Сначала резал текст по 1 000 символов — ломались таблицы и примеры кода, recall был 0.48; переход на структурный чанкинг дал самый большой прирост. Второе: бот цитировал страницы из закрытых пространств — нашли на ревью; добавил фильтр по группам пользователя прямо в SQL и тест на утечку в CI.

Улучшения. Переписывание коротких запросов, кэш ответов на топ-50 вопросов, evals на каждый PR вместо ночного прогона, contextual chunking (добавить в чанк заголовок документа и раздела).

Обратите внимание, что в примере нет ни одного прилагательного-оценки («отличный», «эффективный»): только решения, цифры и причины. Конструктор ниже помогает собрать такой рассказ о своём проекте и показывает, где не хватает конкретики.

    Типичное задание: «за 4–8 часов сделайте сервис, который отвечает на вопросы по этим документам / извлекает поля из этих писем / классифицирует тикеты». Почти все присылают работающий код. Выделяются те, кто присылает измеренный работающий код с честным описанием компромиссов.

    Как запустить одной командой (make run / docker compose up), архитектура в 5 строках или схеме, ключевые решения и альтернативы, результаты evals таблицей, стоимость и латентность, известные ограничения, что бы сделали за следующую неделю.

    Компромиссы явно

    «Выбрал X, потому что Y; при объёме Z перешёл бы на W». Интервьюер ищет понимание границ решения, а не максимальную сложность.

    Стоимость

    Сколько стоил прогон evals, сколько будет стоить 1 000 запросов в день, какой рычаг экономии следующий. Одна таблица — и вы выглядите как человек, который уже запускал такое в прод.

    Инженерная гигиена

    Ключи из env, таймауты и ретраи, обработка ошибок, пара тестов на детерминированные части (чанкер, парсер), линтер. Структура репозитория, понятная за минуту.

    Не переусердствовать

    Если лимит 6 часов, не тратьте 30: это видно и считается сигналом плохой приоритизации. Лучше честный раздел «не успел, сделал бы так».

    Вопросы работодателю

    Ваши вопросы — тоже часть оценки, и одновременно способ понять, будет ли вам там хорошо. Для AI-ролей особенно важно понять, насколько зрелая у команды практика.

    • Продакшн: «Какие LLM-фичи уже в проде и какой у них трафик? Что было последним инцидентом, связанным с моделью?»
    • Стоимость: «Кто отвечает за бюджет на LLM и как его отслеживают? Были ли решения, принятые из-за стоимости?»
    • Роль: «Как делится работа между AI engineer, ML engineer и бэкендом? Кто владеет данными для evals?»
    • Модели: «Как вы выбираете провайдера и модель? Как часто переезжаете на новые версии?»
    • Данные: «Какие ограничения по данным: можно ли отправлять провайдерам, есть ли PII?»
    • Успех: «Как будет выглядеть успех в этой роли через 6 месяцев? Какая метрика?»
    • Команда: «Что в текущей AI-архитектуре вы бы переделали, если бы начинали заново?»

    Кольцо показывает общий процент, внутренние дуги — категории. Клик по дуге прокручивает к категории.

    План последних двух недель

    Предполагается, что основные модули курса и хотя бы два сквозных проекта готовы. Две недели — не для новых знаний, а для скорости воспроизведения и уверенности.

    Практика

    Задание 1: два проекта в формате рассказа

    Соберите в конструкторе рассказы о двух проектах (сквозные проекты курса подходят). Проговорите каждый вслух с таймером, запишите на диктофон, послушайте.

    Критерии готовности: конструктор не показывает красных предупреждений; рассказ укладывается в 2–3 минуты; в метриках минимум три числа с «было → стало»; на вопрос «почему не X?» есть ответ для каждого ключевого решения.

    Задание 2: флеш-карточки до 90%

    Пройдите все карточки, затем режим «незнакомые» до тех пор, пока «знал» не станет ≥ 90%. Для каждого «не знал» вернитесь в соответствующий модуль курса.

    Задание 3: take-home на время

    За 5 часов: сервис на Go, который извлекает из писем клиентов (возьмите 50 публичных или синтетических) поля «продукт, проблема, срочность» через structured output; eval на 30 размеченных письмах (точность по полям), сравнение двух моделей, README по структуре выше со стоимостью.

    Задание 4: поведенческие истории

    Шесть историй в формате STAR: конфликт по техническому решению, провал и выводы, решение при неполных данных, влияние без полномочий, самый сложный баг в проде, как учили других. Каждая — до 2 минут, с результатом в цифрах, где это возможно.

    Самопроверка

    Из каких пяти этапов обычно состоит процесс найма AI engineer?

    Скрининг, кодинг (часто обычный + раунд с LLM-интеграцией), AI system design, deep dive по проектам, поведенческое интервью. Порядок и названия варьируются.

    Какие пять блоков в рассказе о проекте и какой из них чаще всего пропускают?

    Задача, решение, метрики, ошибки, улучшения. Чаще всего пропускают метрики (или заменяют их прилагательными) и ошибки.

    Что в take-home выделяет кандидата сильнее всего?

    Evals с таблицей результатов для нескольких вариантов и README с явными компромиссами, стоимостью и ограничениями. Работающий код присылают почти все.

    Почему в рассказе важно говорить «я», а не «мы»?

    Интервьюер оценивает вас, а не команду. «Мы» не позволяет понять, что сделали лично вы. Правильно: «команда из четырёх человек; я отвечал за retrieval и evals, решил…».

    Какой вопрос работодателю лучше всего показывает зрелость AI-практики в команде?

    «Как вы понимаете, что новая версия промпта или модели не хуже старой?» — наличие или отсутствие evals сразу видно по ответу.

    Что делать в последние два дня перед собеседованием?

    Лёгкий прогон (незнакомые карточки, рассказы вслух), проверка техники и окружения, отдых. Новые темы не учить: это повышает тревожность и почти не добавляет результата.

    Вопросы с собеседований

    Концептуальные вопросы собраны выше. Здесь — мета-вопросы и поведенческие вопросы, специфичные для AI-ролей.

    Почему вы переходите из бэкенда в AI engineering?

    Честная и конкретная история на 60 секунд: что вы уже построили с LLM (проект с цифрами), что увидели — что узкое место AI-продуктов не в моделях, а в инженерии вокруг них (надёжность, evals, стоимость, данные), и почему ваш бэкенд-опыт прямо в это переносится. Не говорить «потому что это хайп» и не принижать бэкенд.

    Расскажите о случае, когда LLM-фича не сработала так, как ожидалось.

    STAR с акцентом на то, как обнаружили (метрика, фидбек, инцидент), как нашли корневую причину (трейсы, разбор ошибок по категориям), что изменили (не только промпт, но и процесс: добавили кейсы в golden set, гейт в CI) и какой был результат в цифрах. Сильный ответ показывает, что вы превращаете инциденты в тесты.

    Как вы объясните продакт-менеджеру, почему модель иногда ошибается и это нельзя «просто починить»?

    Без жаргона: модель статистическая, у неё есть доля ошибок, как у поиска или у человека-оператора; задача — не ноль ошибок, а приемлемая доля при приемлемой цене и понятное поведение при ошибке. Предложить язык метрик: «сейчас 92% ответов корректны на наборе из 300 реальных вопросов; до 96% можно дойти за счёт X за Y недель и Z $/мес; для оставшихся делаем эскалацию на человека». Перевести разговор от «почини» к «какой уровень качества нужен и сколько он стоит».

    Как вы решаете, нужна ли LLM для задачи вообще?

    Проверяю: есть ли детерминированное решение (правила, регулярки, SQL, классический классификатор), которое даёт нужное качество; какова цена ошибки; какой объём и нужна ли латентность в миллисекундах; есть ли данные для evals. LLM оправдана, когда вход неструктурированный и разнообразный, правила не масштабируются, а ошибка допустима или ловится. Часто лучший ответ — гибрид: правила для 80% простых случаев и LLM для хвоста.

    Как вы следите за изменениями в области, которая меняется каждый месяц?

    Конкретика вместо «читаю Twitter»: документация и changelog провайдеров, инженерные блоги (Anthropic engineering, блоги практиков вроде Simon Willison, Hamel Husain, Eugene Yan), выборочно пейперы по своей теме. И главное — собственный eval-набор: новая модель или техника проверяется на нём за час, а не по отзывам в соцсетях.

    Вы не согласны с решением команды использовать мультиагентную архитектуру. Что сделаете?

    Сформулирую несогласие через измеримое: предложу сравнить на общем eval-наборе мультиагентный вариант и простой workflow по качеству, стоимости и латентности; сделаю прототип простого варианта за день-два. Если данные показывают, что сложный вариант лучше — поддерживаю его. Показать, что решение принимается по данным, а не по статусу, и что после решения вы в команде, а не в оппозиции.

    Что вы сделаете в первые 90 дней на этой позиции?

    30 дней: разобраться в продукте и текущих AI-фичах, прочитать трейсы и 100+ реальных ответов, понять, как сейчас измеряется качество и сколько всё стоит. 60 дней: собрать или улучшить golden set и evals в CI для главной фичи, закрыть самую очевидную проблему (часто это retrieval или отсутствие fallback). 90 дней: измеримое улучшение ключевой метрики или стоимости и план на следующий квартал. Упомянуть, что начнёте с вопросов, а не с переписывания.

    Какой ваш самый большой технический компромисс в LLM-проекте?

    Выбрать реальный пример с цифрами: например, отказ от более сильной модели ради латентности и стоимости с компенсацией через rerank и лучший контекст, или отказ от семантического кэша из-за риска неверных ответов. Описать, какие варианты рассматривали, как измеряли, чем пожертвовали и как бы пересмотрели решение при изменении условий.
