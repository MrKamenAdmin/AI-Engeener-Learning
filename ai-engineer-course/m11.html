Ingestion: от PDF до чанка с метаданными

Ingestion (загрузка и подготовка данных) — всё, что происходит с документом до попадания его чанков в индекс. Многие «галлюцинации RAG» из модуля 5 начинаются здесь: таблица превратилась в кашу из чисел, скан стал пустой страницей, футер «Конфиденциально, стр. 3 из 40» попал в каждый чанк, старая версия политики лежит рядом с новой. Модель честно отвечает по тому, что ей дали.

Пайплайн: сбор (коннекторы к Confluence, Drive, S3, тикетам) → парсинг (текстовый слой, OCR или VLM) → нормализация в структуру (markdown или JSON с заголовками, таблицами, списками и порядком чтения) → очистка → PII-редакция → дедупликация → чанкинг по структуре → метаданные и ACL → эмбеддинги и индекс (модуль 5) → отчёт о качестве. Каждый шаг идемпотентен: повторный запуск на тех же байтах ничего не меняет.

Почему PDF — худший формат для RAG

PDF описывает страницу, а не документ: это глифы по координатам, без абзацев, порядка чтения и таблиц. Типовые поломки:

  • Порядок чтения: две колонки читаются построчно поперёк, сноски вклиниваются в абзац.
  • Таблицы: ячейки склеиваются в строку «План Срок Комиссия Месяц 3 дня 0%», связь «значение ↔ колонка» теряется, и вопрос «какая комиссия на годовом плане» уже не решается никаким промптом.
  • Сканы: текстового слоя нет, парсер возвращает пустую строку, документ молча выпадает из индекса.
  • Битые шрифты: без корректной таблицы ToUnicode извлекается мусор вроде «Ïîëèòèêà», хотя визуально PDF идеален.
  • Колонтитулы и переносы: «стр. 3 из 40» в каждом чанке, «воз-\nврат» вместо «возврат» ломает и BM25, и эмбеддинги.

def parse(path: Path) -> tuple[str, dict]:
    from docling.document_converter import DocumentConverter

    t0 = time.perf_counter()
    res = DocumentConverter().convert(path)  # OCR растровых областей включён по умолчанию
    doc = res.document
    md = doc.export_to_markdown()
    pages = doc.num_pages()
    report = {
        "file": path.name,
        "sha256": hashlib.sha256(path.read_bytes()).hexdigest()[:16],  # версия источника
        "status": str(res.status),
        "pages": pages,
        "chars_per_page": round(len(md) / max(pages, 1)),
        "headings": [t.text for t in doc.texts if t.label == "section_header"],
        "tables": [t.export_to_dataframe(doc=doc).to_dict(orient="records") for t in doc.tables],
        "seconds": round(time.perf_counter() - t0, 1),
    }
    # Дешёвые проверки качества: пустой текст почти всегда значит скан без OCR или битые шрифты.
    report["warnings"] = [w for w, bad in [

        ("нет заголовков: структура потеряна, чанкинг по секциям не сработает", not report["headings"]),
    ] if bad]
    return md, report

Чанкинг по структуре

Стратегии чанкинга и подбор размера по recall@k — в модуле 5, там же ChunkSection для прозы. Здесь недостающий кусок для проекта A: нарезать markdown после парсера по заголовкам так, чтобы путь заголовков ехал с каждым чанком, а код-блоки и таблицы не резались. Только стандартная библиотека.

/** Markdown-сплиттер модуля 11: секции по заголовкам, блоки не режутся. */
public final class MdSplit {
    private MdSplit() {}

    /**
     * Кусок markdown с путём заголовков. Эмбеддим heading + "\n\n" + text:
     * путь заголовков даёт чанку контекст, которого нет в самом тексте.
     */
    public record Chunk(String heading, String text) {}

    /**
     * Режет markdown по ATX-заголовкам (# … ######), затем пакует блоки секции (абзацы,
     * списки, таблицы, код) в чанки до maxChars символов. Блок не режется никогда:
     * код-блок и таблица уходят целиком, даже если длиннее maxChars.
     * ponytail: блок длиннее maxChars остаётся одним чанком; прозу дорезайте chunkSection из модуля 5.
     */
    public static List<Chunk> splitMarkdown(String md, int maxChars) {
        return new Splitter(maxChars).run(md);
    }

    private static final class Splitter {
        final int max;
        final List<Chunk> out = new ArrayList<>();
        final List<String> path = new ArrayList<>();   // текущий путь заголовков по уровням
        final List<String> blocks = new ArrayList<>(); // блоки текущей секции
        final List<String> cur = new ArrayList<>();    // строки текущего блока
        String fence = "";                             // открытый ``` или ~~~

        Splitter(int max) { this.max = max; }

        void endBlock() {
            String t = String.join("\n", cur).strip();
            if (!t.isEmpty()) blocks.add(t);
            cur.clear();
        }

        void endSection() {
            endBlock();
            String heading = String.join(" › ", path.stream().filter(s -> !s.isEmpty()).toList());
            List<String> buf = new ArrayList<>();
            int size = 0;
            for (String b : blocks) {
                int n = b.codePointCount(0, b.length());
                if (size > 0 && size + n > max) {
                    out.add(new Chunk(heading, String.join("\n\n", buf)));
                    buf.clear();
                    size = 0;
                }
                buf.add(b);
                size += n;
            }
            if (!buf.isEmpty()) out.add(new Chunk(heading, String.join("\n\n", buf)));
            blocks.clear();
        }

        List<Chunk> run(String md) {
            for (String line : md.split("\n", -1)) {
                String trim = line.strip();
                int lvl;
                if (!fence.isEmpty()) { // внутри код-блока: ни заголовков, ни разрывов
                    cur.add(line);
                    if (trim.startsWith(fence)) {
                        fence = "";
                        endBlock();
                    }
                } else if (trim.startsWith("```") || trim.startsWith("~~~")) {
                    endBlock();
                    fence = trim.substring(0, 3);
                    cur.add(line);
                } else if ((lvl = headingLevel(trim)) > 0) {
                    endSection();
                    while (path.size() < lvl) path.add("");
                    path.subList(lvl - 1, path.size()).clear();
                    path.add(trim.substring(lvl).strip());
                } else if (trim.isEmpty()) {
                    endBlock();
                } else {
                    cur.add(line);
                }
            }
            endSection();
            return out;
        }
    }

    /** "## Title" → 2; "#hashtag" и "####### x" — не заголовки. */
    static int headingLevel(String s) {
        int n = 0;
        while (n < s.length() && s.charAt(n) == '#') n++;
        if (n == 0 || n > 6 || (n < s.length() && s.charAt(n) != ' ')) return 0;
        return n;
    }
}
// Chunk — кусок markdown с путём заголовков. Эмбеддим Heading + "\n\n" + Text:
// путь заголовков даёт чанку контекст, которого нет в самом тексте.
type Chunk struct {
	Heading string // "Тарифы › Возвраты › Сроки"
	Text    string
}

// SplitMarkdown режет markdown по ATX-заголовкам (# … ######), затем пакует блоки
// секции (абзацы, списки, таблицы, код) в чанки до maxRunes. Блок не режется никогда:
// код-блок и таблица уходят целиком, даже если длиннее maxRunes.
// ponytail: блок длиннее maxRunes остаётся одним чанком; прозу дорезайте ChunkSection из модуля 5.
func SplitMarkdown(md string, maxRunes int) []Chunk {
	var (
		out    []Chunk
		path   []string // текущий путь заголовков по уровням
		blocks []string // блоки текущей секции
		cur    []string // строки текущего блока
		fence  string   // открытый ``` или ~~~
	)
	endBlock := func() {
		if t := strings.TrimSpace(strings.Join(cur, "\n")); t != "" {
			blocks = append(blocks, t)
		}
		cur = nil
	}
	endSection := func() {
		endBlock()
		heading := strings.Join(nonEmpty(path), " › ")
		var buf []string
		size := 0
		for _, b := range blocks {
			n := utf8.RuneCountInString(b)
			if size > 0 && size+n > maxRunes {
				out = append(out, Chunk{heading, strings.Join(buf, "\n\n")})
				buf, size = nil, 0
			}
			buf = append(buf, b)
			size += n
		}
		if len(buf) > 0 {
			out = append(out, Chunk{heading, strings.Join(buf, "\n\n")})
		}
		blocks = nil
	}
	for _, line := range strings.Split(md, "\n") {
		trim := strings.TrimSpace(line)
		switch {
		case fence != "": // внутри код-блока: ни заголовков, ни разрывов
			cur = append(cur, line)
			if strings.HasPrefix(trim, fence) {
				fence = ""
				endBlock()
			}
		case strings.HasPrefix(trim, "```") || strings.HasPrefix(trim, "~~~"):
			endBlock()
			fence = trim[:3]
			cur = append(cur, line)
		case headingLevel(trim) > 0:
			endSection()
			lvl := headingLevel(trim)
			for len(path) < lvl {
				path = append(path, "")
			}
			path = append(path[:lvl-1], strings.TrimSpace(trim[lvl:]))
		case trim == "":
			endBlock()
		default:
			cur = append(cur, line)
		}
	}
	endSection()
	return out
}

// headingLevel: "## Title" → 2; "#hashtag" и "####### x" — не заголовки.
func headingLevel(s string) int {
	n := 0
	for n < len(s) && s[n] == '#' {
		n++
	}
	if n == 0 || n > 6 || (n < len(s) && s[n] != ' ') {
		return 0
	}
	return n
}

func nonEmpty(ss []string) []string {
	var out []string
	for _, s := range ss {
		if s != "" {
			out = append(out, s)
		}
	}
	return out
}

Чанк без метаданных нельзя отфильтровать, обновить, удалить по запросу и процитировать. Минимум поверх таблицы chunks из модуля 5 (там уже есть tenant_id, acl, embed_model):

Как это ломается в продеТихие поломки ingestion не видны в логах ошибок: скан дал 0 чанков, таблица стала строкой чисел, документ со сменившимися правами остался виден старой группе. Защита — отчёт парсинга на каждый документ (страницы, символов на страницу, доля OCR, число таблиц и заголовков) с алертами на аномалии и по 2–3 вопроса golden set (проект B) на каждый тип документа: если после смены парсера упал recall@5 на «табличных» вопросах, вы узнаете это раньше пользователей.

Качество данных и дедупликация

Дубли в RAG-индексе занимают места в top-k (пять копий абзаца вытесняют четыре полезных чанка), смещают ответ к версии, у которой больше копий (часто к старой), и стоят денег на эмбеддинги. В датасетах для evals и обучения дубли дают утечку теста в трейн — это и групповое разбиение разобраны в модуле 10. Здесь фокус на корпусе для RAG.

SimHash (Charikar, 2002): каждый шингл хэшируется в 64 бита, по каждому биту голосуют все шинглы (+1 за единицу, −1 за ноль), знак суммы даёт бит отпечатка. У похожих текстов почти все шинглы общие, и голосование почти совпадает. Чтобы не сравнивать документ со всем корпусом, Manku и соавторы (Google, 2007) режут отпечаток на блоки: при расстоянии ≤ 3 хотя бы один из четырёх 16-битных блоков совпадает целиком, поэтому сравниваем только с кандидатами из тех же корзин. В их работе на 8 млрд веб-страниц разумными оказались 64 бита и k = 3.

/**
 * Ищет точные (sha256 нормализованного текста) и почти-дубли (SimHash ≤ maxDist бит).
 * Индекс — 4 таблицы по 16-битным блокам отпечатка: при расстоянии ≤ 3 хотя бы один блок
 * совпадает целиком (принцип Дирихле), поэтому сравниваем только с кандидатами из корзин,
 * а не со всем корпусом (Manku et al., 2007).
 */
public final class Dedup {
    /** Найденный дубль: id и расстояние Хэмминга (0 — точная копия). */
    public record Match(String dupOf, int dist) {}

    private record Entry(String id, long hash) {}

    private final int maxDist; // 3 для 64 бит — значение из статьи Manku et al.; подбирайте на своей разметке
    private final Map<String, String> exact = new HashMap<>();
    @SuppressWarnings("unchecked")
    private final Map<Integer, List<Entry>>[] bands = new Map[4];

    public Dedup(int maxDist) {
        this.maxDist = maxDist;
        for (int i = 0; i < bands.length; i++) bands[i] = new HashMap<>();
    }

    /**
     * Общий шаг для точных и нечётких дублей: нижний регистр, только буквы и цифры,
     * пробелы схлопнуты. Даты, id и подписи вырезайте до этого.
     */
    public static List<String> normalize(String s) {
        List<String> out = new ArrayList<>();
        StringBuilder w = new StringBuilder();
        s.toLowerCase(Locale.ROOT).codePoints().forEach(cp -> {
            if (Character.isLetter(cp) || Character.isDigit(cp)) {
                w.appendCodePoint(cp);
            } else if (!w.isEmpty()) {
                out.add(w.toString());
                w.setLength(0);
            }
        });
        if (!w.isEmpty()) out.add(w.toString());
        return out;
    }

    /** 64-битный отпечаток по шинглам из 3 слов (Charikar, 2002). */
    public static long simHash(List<String> words) {
        final int k = 3;
        int[] acc = new int[64];
        List<String> shingles = new ArrayList<>();
        if (words.size() < k) shingles.add(String.join(" ", words));
        for (int i = 0; i + k <= words.size(); i++) shingles.add(String.join(" ", words.subList(i, i + k)));
        for (String sh : shingles) {
            long x = fnv64a(sh.getBytes(StandardCharsets.UTF_8));
            for (int i = 0; i < 64; i++) acc[i] += ((x >>> i) & 1) != 0 ? 1 : -1;
        }
        long out = 0;
        for (int i = 0; i < 64; i++) if (acc[i] > 0) out |= 1L << i;
        return out;
    }

    public static int hamming(long a, long b) { return Long.bitCount(a ^ b); }

    /**
     * Возвращает найденный дубль или null; если дубля нет, документ добавляется в индекс.
     * ponytail: корректно только для maxDist ≤ 3 (4 блока); для большего порога — больше таблиц с перестановками битов.
     */
    public Match add(String id, String text) {
        List<String> words = normalize(text);
        String key = sha256Hex(String.join(" ", words));
        String prev = exact.get(key);
        if (prev != null) return new Match(prev, 0);
        long h = simHash(words);
        for (int i = 0; i < bands.length; i++) {
            for (Entry e : bands[i].getOrDefault(band(h, i), List.of())) {
                int dist = hamming(h, e.hash());
                if (dist <= maxDist) return new Match(e.id(), dist);
            }
        }
        exact.put(key, id);
        for (int i = 0; i < bands.length; i++) {
            bands[i].computeIfAbsent(band(h, i), b -> new ArrayList<>()).add(new Entry(id, h));
        }
        return null;
    }

    private static int band(long h, int i) { return (int) ((h >>> (16 * i)) & 0xFFFF); }

    private static long fnv64a(byte[] data) {
        long h = 0xcbf29ce484222325L;
        for (byte b : data) {
            h ^= b & 0xff;
            h *= 0x100000001b3L;
        }
        return h;
    }

    private static String sha256Hex(String s) {
        try {
            return HexFormat.of().formatHex(MessageDigest.getInstance("SHA-256").digest(s.getBytes(StandardCharsets.UTF_8)));
        } catch (NoSuchAlgorithmException e) {
            throw new IllegalStateException(e);
        }
    }
}
// Normalize — общий шаг для точных и нечётких дублей: нижний регистр,
// только буквы и цифры, пробелы схлопнуты. Даты, id и подписи вырезайте до этого.
func Normalize(s string) []string {
	return strings.FieldsFunc(strings.ToLower(s), func(r rune) bool {
		return !unicode.IsLetter(r) && !unicode.IsDigit(r)
	})
}

// SimHash — 64-битный отпечаток по шинглам из 3 слов (Charikar, 2002).
// Похожие тексты дают отпечатки с малым расстоянием Хэмминга.
func SimHash(words []string) uint64 {
	const k = 3
	var acc [64]int
	add := func(shingle string) {
		h := fnv.New64a()
		h.Write([]byte(shingle))
		x := h.Sum64()
		for i := 0; i < 64; i++ {
			if x&(1<<i) != 0 {
				acc[i]++
			} else {
				acc[i]--
			}
		}
	}
	if len(words) < k {
		add(strings.Join(words, " "))
	}
	for i := 0; i+k <= len(words); i++ {
		add(strings.Join(words[i:i+k], " "))
	}
	var out uint64
	for i, v := range acc {
		if v > 0 {
			out |= 1 << i
		}
	}
	return out
}

func Hamming(a, b uint64) int { return bits.OnesCount64(a ^ b) }

// Dedup ищет точные (sha256 нормализованного текста) и почти-дубли (SimHash ≤ MaxDist бит).
// Индекс — 4 таблицы по 16-битным блокам отпечатка: при расстоянии ≤ 3 хотя бы один блок
// совпадает целиком (принцип Дирихле), поэтому сравниваем только с кандидатами из корзин,
// а не со всем корпусом (Manku et al., 2007).
type Dedup struct {
	MaxDist int // 3 для 64 бит — значение из статьи Manku et al.; подбирайте на своей разметке
	exact   map[[32]byte]string
	bands   [4]map[uint16][]entry
}

type entry struct {
	id   string
	hash uint64
}

func NewDedup(maxDist int) *Dedup {
	d := &Dedup{MaxDist: maxDist, exact: map[[32]byte]string{}}
	for i := range d.bands {
		d.bands[i] = map[uint16][]entry{}
	}
	return d
}

// Add возвращает id найденного дубля и расстояние (0 — точная копия).
// Если дубля нет, документ добавляется в индекс и возвращается "".
// ponytail: корректно только для MaxDist ≤ 3 (4 блока); для большего порога — больше таблиц с перестановками битов.
func (d *Dedup) Add(id, text string) (dupOf string, dist int) {
	words := Normalize(text)
	key := sha256.Sum256([]byte(strings.Join(words, " ")))
	if prev, ok := d.exact[key]; ok {
		return prev, 0
	}
	h := SimHash(words)
	for i := range d.bands {
		for _, e := range d.bands[i][uint16(h>>(16*i))] {
			if dist := Hamming(h, e.hash); dist <= d.MaxDist {
				return e.id, dist
			}
		}
	}
	d.exact[key] = id
	for i := range d.bands {
		b := uint16(h >> (16 * i))
		d.bands[i][b] = append(d.bands[i][b], entry{id, h})
	}
	return "", 0
}

Шум, языки, устаревшие версии

  • Boilerplate (колонтитулы, меню и cookie-баннеры из HTML, подписи писем) лучше всего находится по частоте: строка, которая встречается на 30% страниц документа или в 1000 писем, — шаблон. Удаляйте до чанкинга. Мусорные чанки (слишком короткие, без букв, mojibake) отсекаются простыми эвристиками.
  • Язык чанка (fastText lid.176, lingua) пишите в метаданные вместе с уверенностью: от него зависят конфигурация полнотекстового поиска ('russian' или 'english'), выбор эмбеддинг-модели и фильтр по языку пользователя.
  • Устаревшие версии — главный источник ответов «по прошлогодней политике». Новая ревизия документа ставит старой is_current = false в той же транзакции; удалённый в источнике документ удаляется из индекса (tombstone), иначе данные, удалённые по требованию, продолжают жить в индексе; дата обновления едет в <source> промпта (модуль 3). Почти-дубли с разными id («копия политики в чужом пространстве») показывайте владельцу корпуса, а не удаляйте автоматически.

PII-редакция

PII (personally identifiable information, персональные данные) приходит в LLM-продукт тремя путями: в документах корпуса (HR-политики, договоры, тикеты), в сообщениях пользователей (в чат вставляют всё: номер карты, паспорт, переписку) и в ответах модели, которая пересказывает контекст. Редактировать нужно там, где данные пересекают границу: индекс, логи, внешний провайдер, разметчики, обучающий датасет.

  • Прямые идентификаторы: ФИО, телефон, email, карта, паспорт, СНИЛС, ИНН, адрес.
  • Косвенные: дата рождения, город, должность, «дочь учится в 5 «Б» школы № 1234». По отдельности безобидны, вместе указывают на человека: по работе Суини (2000), почтовый индекс, пол и дата рождения уникально определяют 87% жителей США.
  • Особые категории (здоровье, биометрия, убеждения) — по GDPR и 152-ФЗ под более жёсткими правилами.

Код: детекторы, контрольные суммы, псевдонимы

Пересечения решаются приоритетом: сначала то, что подтверждено контрольной суммой, потом форматные детекторы. Так СНИЛС без дефисов не станет «телефоном». Это развитие MaskPII из модуля 9, где регэксп карты маскирует любые 13–19 цифр подряд, включая номера заказов.

/** Найденный фрагмент PII: границы (индексы char) в исходном тексте. */
public record Finding(String kind, int start, int end, String value) {}

/** valid == null — проверки нет, только формат. */
private record Detector(String kind, Pattern re, Predicate<String> valid) {}

// Порядок = приоритет при пересечениях: сначала то, что подтверждено контрольной суммой.
private static final List<Detector> DETECTORS = List.of(
        new Detector("CARD", Pattern.compile("\\b(?:\\d{4}[ -]){3}\\d{4}\\b|\\b\\d{13,19}\\b"), Pii::luhn),
        new Detector("SNILS", Pattern.compile("\\b\\d{3}-?\\d{3}-?\\d{3}[ -]?\\d{2}\\b"), Pii::snils),
        new Detector("INN", Pattern.compile("\\b\\d{12}\\b|\\b\\d{10}\\b"), Pii::inn),
        new Detector("EMAIL", Pattern.compile("[\\w.+-]+@[\\w-]+(?:\\.[\\w-]+)+"), null),
        new Detector("PHONE", Pattern.compile("(?:\\+7|\\b8)[ (-]*\\d{3}[ )-]*\\d{3}[ -]?\\d{2}[ -]?\\d{2}\\b"), null),
        // Паспорт РФ: 4 цифры серии + 6 цифр номера. Контрольной суммы нет — без пробела
        // перед номером не ловим, иначе каждое 10-значное число станет «паспортом».
        new Detector("PASSPORT", Pattern.compile("\\b\\d{2} ?\\d{2} \\d{6}\\b"), null));

/** Непересекающиеся находки, отсортированные по позиции. */
public static List<Finding> find(String text) {
    List<Finding> all = new ArrayList<>();
    for (Detector d : DETECTORS) {
        Matcher m = d.re().matcher(text);
        while (m.find()) {
            String v = m.group();
            if (d.valid() != null && !d.valid().test(digitsOnly(v))) continue;
            all.add(new Finding(d.kind(), m.start(), m.end(), v));
        }
    }
    // all уже упорядочен по приоритету детектора; берём находку, если она не пересекается с принятыми.
    // ponytail: O(n²) по числу находок — для сообщений и документов хватает, для гигабайтных дампов нужен interval tree.
    List<Finding> out = new ArrayList<>();
    for (Finding f : all) {
        if (out.stream().noneMatch(o -> f.start() < o.end() && o.start() < f.end())) out.add(f);
    }
    out.sort(Comparator.comparingInt(Finding::start));
    return out;
}
// Finding — найденный фрагмент PII: байтовые границы в исходном тексте.
type Finding struct {
	Kind       string // EMAIL, PHONE, CARD, INN, SNILS, PASSPORT
	Start, End int
	Value      string
}

type detector struct {
	kind  string
	re    *regexp.Regexp
	valid func(digits string) bool // nil — проверки нет, только формат
}

// Порядок = приоритет при пересечениях: сначала то, что подтверждено контрольной суммой.
var detectors = []detector{
	{"CARD", regexp.MustCompile(`\b(?:\d{4}[ -]){3}\d{4}\b|\b\d{13,19}\b`), luhn},
	{"SNILS", regexp.MustCompile(`\b\d{3}-?\d{3}-?\d{3}[ -]?\d{2}\b`), snils},
	{"INN", regexp.MustCompile(`\b\d{12}\b|\b\d{10}\b`), inn},
	{"EMAIL", regexp.MustCompile(`[\w.+-]+@[\w-]+(?:\.[\w-]+)+`), nil},
	{"PHONE", regexp.MustCompile(`(?:\+7|\b8)[ (-]*\d{3}[ )-]*\d{3}[ -]?\d{2}[ -]?\d{2}\b`), nil},
	// Паспорт РФ: 4 цифры серии + 6 цифр номера. Контрольной суммы нет — без пробела
	// перед номером не ловим, иначе каждое 10-значное число станет «паспортом».
	{"PASSPORT", regexp.MustCompile(`\b\d{2} ?\d{2} \d{6}\b`), nil},
}

// Find возвращает непересекающиеся находки, отсортированные по позиции.
func Find(text string) []Finding {
	var all []Finding
	for _, d := range detectors {
		for _, m := range d.re.FindAllStringIndex(text, -1) {
			v := text[m[0]:m[1]]
			if d.valid != nil && !d.valid(digitsOnly(v)) {
				continue
			}
			all = append(all, Finding{Kind: d.kind, Start: m[0], End: m[1], Value: v})
		}
	}
	// all уже упорядочен по приоритету детектора; берём находку, если она не пересекается с принятыми.
	// ponytail: O(n²) по числу находок — для сообщений и документов хватает, для гигабайтных дампов нужен interval tree.
	var out []Finding
	for _, f := range all {
		overlap := false
		for _, o := range out {
			if f.Start < o.End && o.Start < f.End {
				overlap = true
				break
			}
		}
		if !overlap {
			out = append(out, f)
		}
	}
	sort.Slice(out, func(i, j int) bool { return out[i].Start < out[j].Start })
	return out
}
static String digitsOnly(String s) {
    StringBuilder b = new StringBuilder();
    for (char c : s.toCharArray()) if (c >= '0' && c <= '9') b.append(c);
    return b.toString();
}

/** Контрольная сумма номеров карт (ISO/IEC 7812). */
static boolean luhn(String d) {
    int sum = 0;
    for (int i = d.length() - 1; i >= 0; i--) {
        int n = d.charAt(i) - '0';
        if ((d.length() - 1 - i) % 2 == 1) {
            n *= 2;
            if (n > 9) n -= 9;
        }
        sum += n;
    }
    return sum % 10 == 0;
}

/** Контрольные цифры ИНН: 10 знаков (организация) или 12 (физлицо, ИП). */
static boolean inn(String d) {
    return switch (d.length()) {
        case 10 -> innCheck(d, 2, 4, 10, 3, 5, 9, 4, 6, 8) == d.charAt(9) - '0';
        case 12 -> innCheck(d, 7, 2, 4, 10, 3, 5, 9, 4, 6, 8) == d.charAt(10) - '0'
                && innCheck(d, 3, 7, 2, 4, 10, 3, 5, 9, 4, 6, 8) == d.charAt(11) - '0';
        default -> false;
    };
}

private static int innCheck(String d, int... w) {
    int s = 0;
    for (int i = 0; i < w.length; i++) s += w[i] * (d.charAt(i) - '0');
    return s % 11 % 10;
}

/**
 * Контрольное число СНИЛС: веса 9…1 по первым 9 цифрам, затем mod 101 (100 и 101 → 00).
 * Номера не больше 001-001-998 не проверяются — для детектора считаем их невалидными.
 */
static boolean snils(String d) {
    if (d.length() != 11 || d.substring(0, 9).compareTo("001001998") <= 0) return false;
    int s = 0;
    for (int i = 0; i < 9; i++) s += (d.charAt(i) - '0') * (9 - i);
    s %= 101;
    if (s == 100) s = 0;
    return s == (d.charAt(9) - '0') * 10 + (d.charAt(10) - '0');
}
func digitsOnly(s string) string {
	return strings.Map(func(r rune) rune {
		if r >= '0' && r <= '9' {
			return r
		}
		return -1
	}, s)
}

// luhn — контрольная сумма номеров карт (ISO/IEC 7812).
func luhn(d string) bool {
	sum := 0
	for i := len(d) - 1; i >= 0; i-- {
		n := int(d[i] - '0')
		if (len(d)-1-i)%2 == 1 {
			n *= 2
			if n > 9 {
				n -= 9
			}
		}
		sum += n
	}
	return sum%10 == 0
}

// inn — контрольные цифры ИНН: 10 знаков (организация) или 12 (физлицо, ИП).
func inn(d string) bool {
	check := func(w []int) int {
		s := 0
		for i, k := range w {
			s += k * int(d[i]-'0')
		}
		return s % 11 % 10
	}
	switch len(d) {
	case 10:
		return check([]int{2, 4, 10, 3, 5, 9, 4, 6, 8}) == int(d[9]-'0')
	case 12:
		return check([]int{7, 2, 4, 10, 3, 5, 9, 4, 6, 8}) == int(d[10]-'0') &&
			check([]int{3, 7, 2, 4, 10, 3, 5, 9, 4, 6, 8}) == int(d[11]-'0')
	}
	return false
}

// snils — контрольное число СНИЛС: веса 9…1 по первым 9 цифрам, затем mod 101 (100 и 101 → 00).
// Номера не больше 001-001-998 не проверяются — для детектора считаем их невалидными.
func snils(d string) bool {
	if len(d) != 11 || d[:9] <= "001001998" {
		return false
	}
	s := 0
	for i := 0; i < 9; i++ {
		s += int(d[i]-'0') * (9 - i)
	}
	s %= 101
	if s == 100 {
		s = 0
	}
	return s == int(d[9]-'0')*10+int(d[10]-'0')
}
/** Текст без PII и словарь токен → исходное значение. */
public record Redacted(String text, Map<String, String> vault) {}

/**
 * Заменяет PII. key == null — маскирование ([CARD]); иначе — псевдонимизация:
 * [CARD:3f9a1c2b] = HMAC(key, тип+нормализованное значение). Одно и то же значение даёт
 * один и тот же токен во всех документах — можно считать, джойнить и искать по нему, не видя PII.
 * Словарь (vault) нужен только для обратной подстановки: храните его отдельно,
 * с отдельными правами и сроком жизни, или не храните вовсе, если восстановление не нужно.
 */
public record Redactor(byte[] key) {
    public Redacted redact(String text) {
        StringBuilder b = new StringBuilder();
        Map<String, String> vault = new HashMap<>();
        int last = 0;
        for (Finding f : find(text)) {
            b.append(text, last, f.start());
            String tok = "[" + f.kind() + "]";
            if (key != null) {
                tok = "[" + f.kind() + ":" + pseudonym(f) + "]";
                vault.put(tok, f.value());
            }
            b.append(tok);
            last = f.end();
        }
        b.append(text.substring(last));
        return new Redacted(b.toString(), vault);
    }

    private String pseudonym(Finding f) {
        String norm = f.value().toLowerCase(Locale.ROOT);
        if (!f.kind().equals("EMAIL")) {
            norm = digitsOnly(f.value());
            if (f.kind().equals("PHONE") && norm.startsWith("8")) {
                norm = "7" + norm.substring(1); // 8 912… и +7 912… — один и тот же номер
            }
        }
        try {
            Mac mac = Mac.getInstance("HmacSHA256");
            mac.init(new SecretKeySpec(key, "HmacSHA256"));
            byte[] sum = mac.doFinal((f.kind() + ":" + norm).getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(sum, 0, 4); // 32 бита: читаемо; для больших баз берите 8+ байт
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException(e);
        }
    }
}

/** Обратная подстановка, например в ответе модели перед показом пользователю. */
public static String restore(String text, Map<String, String> vault) {
    for (var e : vault.entrySet()) text = text.replace(e.getKey(), e.getValue());
    return text;
}
// Redactor заменяет PII. Key == nil — маскирование ([CARD]); иначе — псевдонимизация:
// [CARD:3f9a1c2b] = HMAC(key, тип+нормализованное значение). Одно и то же значение даёт
// один и тот же токен во всех документах — можно считать, джойнить и искать по нему, не видя PII.
type Redactor struct {
	Key []byte
}

// Redact возвращает текст без PII и словарь токен → исходное значение.
// Словарь (vault) нужен только для обратной подстановки: храните его отдельно,
// с отдельными правами и сроком жизни, или не храните вовсе, если восстановление не нужно.
func (r Redactor) Redact(text string) (string, map[string]string) {
	var b strings.Builder
	vault := map[string]string{}
	last := 0
	for _, f := range Find(text) {
		b.WriteString(text[last:f.Start])
		tok := "[" + f.Kind + "]"
		if r.Key != nil {
			tok = "[" + f.Kind + ":" + r.pseudonym(f) + "]"
			vault[tok] = f.Value
		}
		b.WriteString(tok)
		last = f.End
	}
	b.WriteString(text[last:])
	return b.String(), vault
}

func (r Redactor) pseudonym(f Finding) string {
	norm := strings.ToLower(f.Value)
	if f.Kind != "EMAIL" {
		norm = digitsOnly(f.Value)
		if f.Kind == "PHONE" && strings.HasPrefix(norm, "8") {
			norm = "7" + norm[1:] // 8 912… и +7 912… — один и тот же номер
		}
	}
	m := hmac.New(sha256.New, r.Key)
	m.Write([]byte(f.Kind + ":" + norm))
	return hex.EncodeToString(m.Sum(nil)[:4]) // 32 бита: читаемо; для больших баз берите 8+ байт
}

// Restore — обратная подстановка, например в ответе модели перед показом пользователю.
func Restore(text string, vault map[string]string) string {
	pairs := make([]string, 0, 2*len(vault))
	for tok, v := range vault {
		pairs = append(pairs, tok, v)
	}
	return strings.NewReplacer(pairs...).Replace(text)
}

Разметка: гайдлайн важнее инструмента

Согласие разметчиков (Cohen's κ) и error analysis разобраны в модуле 8. Низкое согласие почти всегда означает плохой гайдлайн, а не плохих разметчиков. В гайдлайне должны быть: задача и что будет с меткой дальше; метки с определениями и примерами «да» и «нет»; дерево решений для пограничных случаев («ответ верный, но без цитаты → FAIL»; «по устаревшей версии документа → FAIL, тег stale»); выход «не могу оценить»; версия и changelog — изменили определение, перечитайте затронутые метки.

  • Контроль качества: контрольные задания с известным ответом вперемешку с обычными, перекрёстная разметка 10–20% и арбитраж эксперта.
  • Инструменты (по состоянию на октябрь 2026): Label Studio (Apache-2.0) активно развивается; Argilla (Apache-2.0) после перехода в Hugging Face в 2024 году находится в режиме поддержки: только исправления ошибок, без новых функций; doccano (MIT) развивается медленно. Для старта хватает внутренней страницы с трассой целиком и горячими клавишами PASS/FAIL.
  • PII и доступ: редакция до разметки, роли, договор с подрядчиком, запрет выгрузки.

Active learning: что размечать первым

Active learning — выбирать для разметки примеры, которые сильнее всего улучшат систему. Для LLM-продукта это неуверенные случаи (низкий скор retrieval, judge и эвристики разошлись, разные прогоны дали разные ответы), новые кластеры запросов, которых нет в golden set, высокая цена ошибки (деньги, право, безопасность) и сигналы из прода. Активная выборка смещена к трудным случаям, поэтому для честной оценки держите отдельную случайную выборку.

Фидбек и data flywheel

Data flywheel (маховик данных) — замкнутый цикл: прод поставляет примеры ошибок, из них получаются кейсы для evals и данные для улучшений, улучшения через eval-гейт возвращаются в прод. Без маховика golden set застывает на дне запуска, а прод уходит вперёд.

  • Явный фидбек (👍/👎, комментарий, исправление оператором) точный, но редкий (обычно меньше процента ответов) и смещённый: его чаще оставляют недовольные.
  • Неявный (регенерация, переформулирование, эскалация, копирование, правка черновика) — подробно в модуле 8.
  • Привязка к трассе: фидбек без trace_id бесполезен — нужны запрос, найденные чанки и версии.

Путь сигнала: отбор (все 👎 и эскалации, случайная выборка 0.5–2% трафика, активная выборка) → PII-редакция → разбор (error analysis: сломались retrieval, документ, промпт, модель или ожидания) → исход (кейс в golden set, задача владельцу документа, правка промпта, пример для обучения в модуле 10, «не баг») → релиз через eval-гейт, где новый кейс сначала падает, потом проходит. Брать логи пользователей для evals и обучения можно не всегда: нужны правовое основание и совместимость с целью сбора (следующий урок), а также условия договора с провайдером.

Метрики маховика: время цикла от 👎 до кейса в CI (медиана в днях — самая честная метрика того, учится ли система); доля разобранных сигналов и бэклог; прирост golden set и покрытие прод-кластеров; доля повторяющихся ошибок (высокая — фиксы не доезжают или кейс не ловит регрессию); тренд качества по релизам на фиксированном срезе; стоимость размеченного кейса.

Маховик данных: где узкое место

Двигайте трафик, долю фидбека, выборку и бюджет разметки. Схема считает недельный поток и подсвечивает узкое место: мало сигналов, не хватает разметки или разобранное не становится кейсами. Модель упрощённая: она показывает баланс, а не прогнозирует ваши цифры.

Логи диалогов: что хранить, сколько и кому показывать

Логи диалогов нужны для отладки, evals, маховика данных и расследования инцидентов. Это же самое опасное хранилище PII в системе: тексты, которые пользователи писали, не думая, где они окажутся. Удаление по запросу

Нужен реестр мест хранения с ключом поиска по пользователю: прод-БД, логи, трейсы и фидбек (по HMAC); векторный индекс, если индексируется пользовательский контент (по owner_id чанка); golden set, очереди разметки и выгрузки подрядчикам (по ссылке на трассу); кэши ответов; бэкапы — через crypto-shredding (данные пользователя шифруются его ключом, удаление ключа делает недоступными и копии); провайдер — по договору. Дообученную модель «разучить» человека нельзя, поэтому сырые персональные данные в обучение не берут. Удаление — скрипт с тестом на синтетическом пользователе и отчётом о выполнении, а не инструкция в wiki.

EU AI Act

EU AI Act (Regulation (EU) 2024/1689) регулирует ИИ по уровням риска и действует экстерриториально: на всех, кто выводит AI-системы на рынок ЕС, и на провайдеров и эксплуатантов из третьих стран, если результат работы системы используется в ЕС (ст. 2). Российская компания с клиентами в ЕС может под него попасть. Ниже — что закон требует и как это меняет архитектуру. Применимость к конкретной системе определяет юрист, урок не является юридической консультацией.

  • Провайдер GPAI-модели (general-purpose AI) — Anthropic, OpenAI, Mistral. Глава V: техническая документация, информация для интеграторов, политика по авторскому праву, публичное описание обучающих данных, для моделей с системным риском — оценка и снижение рисков. Вы становитесь провайдером GPAI, только если выпускаете свою модель общего назначения или значительно модифицируете чужую; по руководству Еврокомиссии обычный LoRA-тюнинг под узкую задачу к этому, как правило, не относится.
  • Провайдер AI-системы (provider) разрабатывает систему и выводит её на рынок под своим именем: чат-бот поддержки на Claude, который вы даёте клиентам, — ваша AI-система.
  • Эксплуатант (deployer) применяет систему под своей ответственностью: банк, внедривший чужой скоринг, или ваша компания со внутренним инструментом.

Как определить категорию своей фичи

  1. Сфера: есть ли пользователи или результаты работы системы в ЕС?
  2. Роль: провайдер системы, эксплуатант или провайдер GPAI-модели?
  3. Ст. 5: нет ли запрещённой практики в назначении или в разумно предсказуемом злоупотреблении?
  4. High-risk: относится ли назначение (intended purpose) к пункту приложения III или к приложению I? Если да — работает ли ст. 6(3), нет ли профилирования?
  5. Ст. 50: общение с людьми, генерация контента, эмоции, дипфейки?
  6. Запишите вывод со ссылками на статьи и отдайте юристу. Пересматривайте при смене назначения: «добавим скоринг кандидатов» делает HR-чат-бот high-risk.

    Самопроверка

    Почему документ-скан опасен для RAG, даже если парсер не выдал ошибку?

    Без текстового слоя парсер возвращает пустой текст, документ даёт 0 чанков и молча выпадает из индекса; ошибки в логах нет. Защита — OCR для страниц без текста и алерт отчёта парсинга на «мало символов на страницу».

    Как положить в индекс таблицу на 300 строк?

    Группами строк с шапкой в каждом чанке или построчно «колонка: значение». Справочник с точными значениями лучше положить в SQL и дать модели инструмент поиска.

    Чем SimHash отличается от MinHash и зачем SimHash режут на блоки?

    MinHash оценивает сходство Жаккара шинглов набором минимальных хэшей, кандидатов ищут LSH-корзинами. SimHash сжимает документ в 64-битный отпечаток, похожие тексты близки по Хэммингу. Блоки избавляют от полного перебора: при расстоянии ≤ 3 хотя бы один из четырёх 16-битных блоков совпадает.

    Почему дедупликацию нельзя делать глобально по всему индексу?

    Одинаковый текст у разных тенантов или групп доступа — это разные документы. Удалив «дубль», вы лишите второго тенанта документа, а склеив ACL — откроете ему чужие данные. Ключ дедупликации включает область доступа.

    Номер заказа из 10 цифр прошёл проверку ИНН. Это баг детектора?

    Нет, это ожидаемое свойство: у ИНН одна контрольная цифра, и случайное число проходит проверку примерно в одном случае из десяти. Контрольная сумма снижает ложные срабатывания, но не убирает их. Помогают контекстные слова («ИНН» рядом), знание формата ваших номеров заказов и измерение точности на размеченной выборке.

    Чем детерминированная псевдонимизация лучше маскирования и в чём её риск?

    Одно значение всегда даёт один токен, поэтому сохраняются связность и аналитика: можно посчитать обращения одного клиента, не видя его телефона. Риски: это всё ещё персональные данные (по GDPR псевдонимизированные данные остаются персональными), ключ HMAC — секрет, утечка которого позволяет перебором сопоставить токены с известными значениями, а ротация ключа рвёт связность.

    Где в LLM-системе нужно редактировать PII? Назовите минимум четыре точки.

    До индексации (или ACL и решение не индексировать), до логов и трейсов, до отправки внешнему провайдеру (минимизация; допустимость самой передачи оценивает юрист), до разметки и evals, до обучения, на выходе модели.

    Что должно входить в версию данных, по которой посчитана метрика RAG?

    Ревизии исходных документов, версия парсера, чанкер и его параметры, эмбеддинг-модель, версия golden set и гайдлайна разметки. Обновление парсера — это новая версия корпуса и повод прогнать evals.

    Почему golden set нельзя пополнять только из 👎?

    Явный фидбек редкий и смещённый: оценки оставляют недовольные и определённые сегменты пользователей. Набор только из жалоб завышает долю трудных случаев и не отражает реальное распределение. Нужна случайная выборка трафика для честной оценки и активная — для поиска ошибок.

    Какая метрика лучше всего показывает, что маховик данных работает?

    Время цикла: сколько дней проходит от 👎 в проде до регрессионного кейса в CI. Дополнительно — бэклог разметки, прирост и покрытие golden set по кластерам прод-запросов, доля повторяющихся ошибок.

    Что изменил Digital Omnibus on AI в датах для high-risk систем и каков его статус?

    Принят: Regulation (EU) 2026/1744 от 8 июля 2026 года, в силе с 27 июля 2026 года. Требования к high-risk системам из приложения III применяются со 2 декабря 2027 года, из приложения I — со 2 августа 2028 года. В принятом тексте даты фиксированные, без привязки к готовности стандартов, как было в предложении. Прозрачность по ст. 50 — со 2 августа 2026 года, для систем генерации, выпущенных раньше, 50(2) — до 2 декабря 2026 года.

    Какие нормы 152-ФЗ затрагивает отправка запросов российских пользователей в зарубежный LLM API?

    Локализация (ч. 5 ст. 18): первичная запись и хранение — в базе в России. Трансграничная передача (ст. 12): уведомление Роскомнадзора до начала передачи и ожидание, если страна не в перечне. Правовое основание и согласие (ст. 6, 9), поручение обработки иностранному лицу (ст. 6). Инженерно: минимизация и псевдонимизация до отправки, провайдер за интерфейсом с возможностью переключения. Окончательно применимость оценивает юрист.

    Вопросы с собеседований

    Спроектируйте ingestion для 2 млн корпоративных PDF: сканы, таблицы, права доступа, документы обновляются.

    Очередь и идемпотентные воркеры с ключом (doc_id, revision); неизменившийся по хэшу документ не обрабатывается повторно. Маршрутизация по страницам: текстовый слой → layout-парсер (self-hosted, если документы нельзя отдавать наружу), страницы без текста → OCR, сложные таблицы и графики → VLM только там, где важны цифры, со сверкой по текстовому слою. Выход — markdown или JSON со структурой, чанкинг по заголовкам, таблицы не режутся. Метаданные: источник, ревизия, страницы, язык, версия парсера, ACL из источника с отдельной частой синхронизацией и deny by default. PII-редакция и дедупликация внутри области доступа, старые версии is_current = false, удалённые в источнике — tombstone. Наблюдаемость: отчёт парсинга на документ, доля OCR, документы с нулём чанков, стоимость страницы; качество — golden-вопросы по типам документов и recall@k до и после смены парсера.

    На что смотрит интервьюер: маршрутизация по стоимости вместо «прогоним всё через самую сильную VLM», ACL и удаление как часть ingestion, наблюдаемость тихих поломок, инкрементальность.

    Банковский чат-бот на внешнем LLM API. Как организуете работу с PII?

    Сначала требования: что можно передавать провайдеру по договору и закону, регион, zero data retention. Детекторы на входе: регэкспы с контрольными суммами (карты, счета, ИНН, СНИЛС) и NER для имён и адресов. Для провайдера — обратимая псевдонимизация: модель видит токены, приложение подставляет значения в ответ, vault отдельно и с коротким сроком жизни. В логах — необратимое маскирование до выхода из периметра, HMAC вместо id. На выходе — детектор PII. Полноту детекторов меряю на синтетических диалогах в CI. Реквизиты для операций вообще не идут через LLM: инструмент берёт их из сессии, а не из промпта.

    На что смотрит интервьюер: различает маскирование и обратимую псевдонимизацию, меряет полноту, не шлёт PII провайдеру ради поиска PII, держит реквизиты вне промпта.

    Пользователь требует удалить все свои данные. Что это значит для LLM-системы?

    Нужен реестр мест хранения с ключом поиска: прод-БД, логи, трейсы и фидбек (HMAC), векторный индекс, если индексируется пользовательский контент (owner_id), кэши ответов, golden set и очереди разметки (ссылка на трассу), выгрузки подрядчикам, бэкапы (crypto-shredding), логи провайдера (договор). Дообученную модель точечно не почистить, поэтому сырые персональные данные в обучение не попадают — это решается заранее. Удаление — скрипт с тестом на синтетическом пользователе и отчётом; сроки задаёт закон, значит, процесс автоматизирован.

    На что смотрит интервьюер: неочевидные места (индекс, golden set, кэш, бэкапы, провайдер) и понимание, что модель нельзя «разучить».

    Как построить data flywheel для RAG-ассистента, который только что запустился?

    Инструментирование: трасса с версиями, найденные чанки, явный фидбек с комментарием и неявные сигналы. Отбор на разбор: все 👎 и эскалации, случайная выборка около 1% для честной оценки, активная — неуверенные ответы и новые кластеры. PII-редакция перед очередью. Еженедельный error analysis, у каждого исхода владелец: кейс в golden set, задача владельцу базы знаний, правка промпта. Релиз через eval-гейт, новый кейс сначала падает, потом проходит. Метрики: время цикла от 👎 до кейса в CI, бэклог, покрытие прод-кластеров, повторяемость ошибок. Узкое место почти всегда разметка: приоритизация по цене ошибки и первичная сортировка judge-моделью.

    На что смотрит интервьюер: замкнутость цикла, понимание смещения явного фидбека, метрика скорости, а не «собираем лайки».

    Как вы определите, подпадает ли фича под high-risk по EU AI Act, и что это изменит в архитектуре?

    Начинаю с назначения (intended purpose) и роли: провайдер системы или эксплуатант. Проверяю ст. 5, затем приложение III: важна не отрасль, а использование — отбор резюме (п. 4) да, FAQ-бот для кандидатов, скорее всего, нет. Если попадаем — исключение ст. 6(3) (узкая процедурная или подготовительная задача, без профилирования) с документированной оценкой. Параллельно ст. 50 с 2 августа 2026. High-risk из приложения III применяется со 2 декабря 2027 (Regulation (EU) 2026/1744). Архитектура: append-only журнал событий с версиями и решениями человека, хранение не меньше 6 месяцев; human oversight в UI (источники, отклонить, остановить); техническая документация; datasheet и проверка смещений; заявленная точность из evals и red-team; мониторинг и процесс уведомления об инцидентах. Окончательную классификацию подтверждает юрист.

    На что смотрит интервьюер: знает структуру закона и актуальные даты, разделяет роли, переводит статьи в компоненты системы, не выдаёт себя за юриста.

    Recall@5 упал с 0.86 до 0.79 после «обновления корпуса». Как найдёте причину?

    Проверяю сопоставимость: та же версия golden set, эмбеддинг-модель и код поиска. Затем дифф данных: какие документы добавились, исчезли, изменились; сменилась ли версия парсера; сколько документов дали 0 чанков; как изменились длины чанков и число таблиц. Срезы метрики: упали «табличные» вопросы — парсер или чанкинг таблиц; вопросы по конкретным документам — их выпадение или новые версии рядом со старыми; всё равномерно — эмбеддинги или дубли, вытесняющие полезное из top-k. По каждому упавшему кейсу смотрю, куда делся нужный чанк. Вывод для процесса: обновление корпуса — релиз с прогоном evals.

    На что смотрит интервьюер: версии и lineage данных как инструмент отладки, срезы, системный поиск причины вместо «поменяем размер чанка».

    Согласие разметчиков κ = 0.4. Что будете делать?

    На таких метках нельзя ни калибровать judge, ни обучать. Разбираю расхождения: где и почему спорят. Обычно виноват гайдлайн — размытое определение, нет правил для пограничных случаев, нет «не могу оценить». Переписываю с деревом решений и примерами, составной критерий дроблю на бинарные. Повторная перекрёстная разметка на 30–50 кейсах, арбитраж эксперта, контрольные задания в потоке. Гайдлайн версионирую и пересматриваю метки, затронутые изменением.

    На что смотрит интервьюер: лечит инструкцию, а не людей; знает, что judge не согласуется с людьми лучше, чем люди между собой (модуль 8).

    Российский продукт хочет перейти на зарубежный LLM API. Какие инженерные последствия по 152-ФЗ вы назовёте?

    Персональные данные в запросах — трансграничная передача (ст. 12): уведомление Роскомнадзора до начала, для стран вне перечня РКН — ожидание 10 рабочих дней, риск запрета. Локализация (ч. 5 ст. 18) — отдельное требование: первичная запись и хранение в базе в России, поэтому история диалогов и логи живут у нас, а провайдер получает только текущий запрос. Архитектурно: минимизация контекста и псевдонимизация перед отправкой, маршрутизация по классу данных (чувствительное — на self-hosted или российского провайдера), провайдер за интерфейсом шлюза для переключения конфигурацией, реестр мест хранения для уведомления по ст. 22 и удаления. Плюс проверить 243-ФЗ: не попадает ли продукт в сферы, где допустимы только российские модели. Правовую оценку делает юрист.

    На что смотрит интервьюер: различает локализацию и трансграничную передачу, предлагает переключаемого провайдера и минимизацию, а не «запретим всё» или «отправим как есть».
