Vision-модели и понимание документов

VLM (vision-language model, модель «зрение + язык») режет изображение на патчи, превращает их в визуальные токены и обрабатывает вместе с текстом тем же трансформером. Как отправить картинку или PDF в API и сколько это стоит, разобрано в модуле 2 (мультимодальность). Здесь vision — инженерная задача: что поручать модели, где она ошибается и как это ловить до того, как ошибка попадёт в базу.

Режимы отказа

  • Мелкий текст и уменьшение. Модель видит не ваш PNG, а копию в пределах своего лимита. У Claude изображение режется на патчи 28×28 px и стоит ⌈w/28⌉ × ⌈h/28⌉ визуальных токенов, а картинка больше лимита уменьшается: стандартный уровень — до 1568 px по длинной стороне, высокое разрешение (модели начиная с Claude 4.7) — до 2576 px, по документации на октябрь 2026. На стандартном уровне скриншот 4K уменьшается примерно в 2,6 раза: текст в 9 px становится пятнами в 3–4 px, и модель всё равно «прочитает» его. Режьте страницу на фрагменты (tiles) или кадрируйте нужную область.
  • Счёт объектов. Документация Anthropic прямо предупреждает: подсчёт приблизителен, особенно когда мелких объектов много. Вместо «сколько позиций в накладной» просите список позиций и считайте в коде.
  • Пространственные отношения. В BlindTest (Rahmanzadehgervi et al., 2024) четыре сильные на тот момент VLM в среднем решали 58% элементарных задач вроде «пересекаются ли два круга» и «сколько раз пересекаются линии». Лучший результат, 77,8%, показал Claude 3.5 Sonnet, а человек решает такие задачи безошибочно. Новые модели сильнее, но «что левее», «какая подпись к какой линии» по-прежнему проверяйте.
  • Галлюцинации чисел — самый дорогой отказ. Размытая 3 читается как 8, теряется разряд или минус, строка таблицы читается дважды, пустое поле заполняется правдоподобным значением. Модель не скажет «не вижу», если вы не дали ей такого выхода (модуль 3).
  • Плохой вход. По документации, на повёрнутых, низкокачественных и совсем маленьких (меньше 200 px) изображениях растёт доля ошибок. Сильное JPEG-сжатие портит мелкий текст, а повторное — ещё сильнее.
  • Недоверенный ввод. Текст на картинке — такой же канал prompt injection, как веб-страница: надпись «игнорируй инструкции» белым по белому модель прочтёт (модуль 7).
  • Политики. Называть людей по фото Claude отказывается; сложные медицинские снимки (КТ, МРТ) документация относит к задачам, для которых модель не предназначена.

Стоимость

Формула и порядок величин — в модуле 2. Две поправки на 2026 год. Первая: у моделей с высоким разрешением та же картинка может стоить до трёх раз больше визуальных токенов, чем на стандартном уровне. Вторая: число токенов на изображение ограничено сверху (1568 на стандартном уровне, 4784 на высоком), поэтому огромный скан стоит не дороже «потолка», зато и читается хуже. Пример из документации: изображение 1000×1000 — 1296 токенов, на Opus 5 ($5 за 1M входа) это около $6.5 за тысячу картинок. Главный рычаг — отправлять только нужное: кроп области, нужные страницы, разрешение, выбранное по eval, а не на глаз.

VLM или OCR-пайплайн

Классический пайплайн (модуль 11): OCR-движок → анализ разметки страницы (layout) → правила или модель для полей. VLM делает это за один вызов. Выбор — по точности, цене и контролю.

Гибрид — частый продакшн-вариант. OCR даёт текст и координаты, VLM получает изображение страницы вместе с OCR-текстом и извлекает поля, а расхождение между ними — повод отправить документ человеку. Ещё проще маршрутизация: цифровые PDF с текстовым слоем идут в обычный парсер, сканы и фото — в VLM.

Извлечение с проверкой

Выход VLM — недоверенный ввод. Structured outputs (модуль 2) гарантируют форму, а смысл проверяет код: суммы строк сходятся с итогом, даты разбираются, контрольные суммы реквизитов верны. Полезный приём — просить числа строкой «как напечатано» и разбирать их самим. Тогда модель только переписывает символы, а арифметика детерминирована и покрыта тестом (examples/m16-voice/invoice, функция Kopecks разбирает «12 345,67» в копейки без float).

// Invoice — ответ модели по JSON-схеме. Суммы — строкой «как напечатано»:
// модель только переписывает, а разбор числа детерминирован и тестируется.
type Invoice struct {
	Number string `json:"number"`
	Date   string `json:"date"` // YYYY-MM-DD
	Lines  []Line `json:"lines"`
	Total  string `json:"total"`
}

type Line struct {
	Name   string `json:"name"`
	Amount string `json:"amount"`
}

// Validate возвращает все найденные расхождения; nil — счёт сходится.
func (inv Invoice) Validate() error {
	var errs []error
	if strings.TrimSpace(inv.Number) == "" {
		errs = append(errs, errors.New("нет номера"))
	}
	if _, err := time.Parse(time.DateOnly, inv.Date); err != nil {
		errs = append(errs, fmt.Errorf("дата %q: %w", inv.Date, err))
	}
	var sum int64
	for i, l := range inv.Lines {
		k, err := Kopecks(l.Amount)
		if err != nil {
			errs = append(errs, fmt.Errorf("строка %d: %w", i+1, err))
		}
		sum += k
	}
	total, err := Kopecks(inv.Total)
	if err != nil {
		errs = append(errs, fmt.Errorf("итог: %w", err))
	} else if len(errs) == 0 && sum != total {
		// Классика VLM: перепутанные 3/8, потерянный разряд, строка прочитана дважды.
		errs = append(errs, fmt.Errorf("сумма строк %d ≠ итог %d (коп.)", sum, total))
	}
	return errors.Join(errs...)
}

Если проверка не прошла: повтор с кропом проблемной области в большем разрешении, затем другая модель, затем очередь на ручную проверку. Доля документов, ушедших к человеку, — полноценная метрика: это и стоимость, и ранний сигнал дрейфа входных данных.

Аналогия из GoVLM здесь — парсер с недокументированными багами. Вы же не поручаете json.Unmarshal проверку бизнес-инвариантов: после разбора идёт Validate(), и ошибка валидации — это 422, а не паника. JSON-схема играет роль типов, сходимость сумм — роль валидации.

Evals для vision

  • Набор из реальных входов: фото с телефона, кривые сканы, скриншоты в тёмной теме, а не чистые PDF, сгенерированные для теста. Стратифицируйте по качеству и типу документа и считайте метрики по слоям, иначе среднее спрячет провал на фото.
  • Метрики по полям: точное совпадение для номеров и дат, числовое — для сумм после нормализации, CER (character error rate, доля ошибочных символов) или ANLS (метрика DocVQA на основе расстояния Левенштейна) для свободного текста.
  • Метрика документа: доля документов без единой ошибки в критичных полях. Её понимает бизнес, и она жёстче: при 98% точности по каждому из 10 независимых полей без ошибок останется лишь около 82% документов.
  • Отказы: отдельные кейсы, где поля нет или фрагмент нечитаем. Правильный ответ — «нет данных», а не выдумка.
  • Разрешение как параметр: прогон одного набора на 2–3 разрешениях даёт кривую «качество / стоимость» и обоснованный выбор уменьшения.
  • Публичные бенчмарки (DocVQA, ChartQA, OCRBench) годятся для шорт-листа моделей. Решение принимается только по своему набору (модуль 8).

Голос: каскад или speech-to-speech

Голосовой агент — это диалог в реальном времени: пользователь говорит, агент понимает и отвечает голосом, а его можно перебить. Архитектур две.

Каскад STT → LLM → TTS

VAD (voice activity detection, детектор речи) и STT (speech-to-text, распознавание) превращают речь в текст. Текстовая LLM отвечает, используя RAG и инструменты, а TTS (text-to-speech, синтез) озвучивает ответ. Каждое звено — отдельный сервис, часто от разных вендоров.

Speech-to-speech (realtime)

Одна модель принимает аудио и сразу генерирует аудио. Конец реплики, перебивание и вызов инструментов обрабатываются внутри одной сессии у провайдера. Текст пользователя появляется только как побочная транскрипция, если её включить. Отдельная ветка — полнодуплексные модели, которые слушают и говорят одновременно (Moshi, Défossez et al., 2024).

Практическое правило на 2026 год: по наблюдению авторов primer'а, продакшн-агенты в основном каскадные. Speech-to-speech выбирают, когда естественность разговора важнее контроля (компаньоны, практика языка, демо) или когда смешанная речь — норма. Бывают и гибриды: S2S-модель ведёт разговор и вызывает «тяжёлую» текстовую модель как инструмент. Решение, как всегда, — по eval на своих сценариях, а не по демо.

Где здесь ClaudeВ Claude API на октябрь 2026 нет аудиовхода и аудиовыхода, поэтому Claude работает LLM-звеном каскада. Для каскада это типичная форма: то же звено, что в текстовом агенте проекта A, только с другим промптом и жёстким бюджетом латентности.

Бюджет латентности голосового хода

В чате пользователь видит, что ответ печатается. В голосе у него есть только тишина, а тишина в разговоре — сигнал: собеседник не понял, завис или связь оборвалась. Поэтому главная метрика голосового агента — voice-to-voice latency: время от момента, когда пользователь замолчал, до первого звука ответа в его динамике.

На что ориентироваться

  • Люди. В исследовании десяти языков (Stivers et al., 2009) самые частые паузы между репликами лежат в диапазоне от 0 до 200 мс, медиана по всем языкам около 100 мс. Levinson и Torreira (2015) отмечают парадокс: на подготовку даже короткой реплики нужно больше 600 мс, значит, люди предсказывают конец чужой фразы и начинают готовить ответ заранее. Каскаду до этого далеко: о конце реплики он узнаёт по тишине.
  • Продакшн-агенты. Авторы Voice AI primer (Daily, Pipecat) называют 1500 мс voice-to-voice важной целью: с агентами, которые в неё укладываются, людям нормально разговаривать. Хорошо настроенный каскад в их демо отвечал примерно за 500 мс. Для LLM-звена у них же практическое правило — TTFT не больше ~600 мс.
  • Сеть. По ITU-T G.114, при односторонней задержке до 150 мс большинство приложений не страдает, а 400 мс — граница, которую не стоит превышать при планировании сети. Телефонная связь добавляет к бюджету агента сотни миллисекунд.

Ориентиры задают порядок, а не норматив. Что приемлемо для вашего сценария, решают ваши данные: доля перебиваний, брошенных звонков, успешно решённых задач.

Endpointing — главный компромисс. Короткий порог тишины ускоряет ответ, но агент начинает перебивать человека, который задумался посреди фразы: «мой номер заказа… эээ… 4815». Длинный порог безопасен, но медленен. Для ориентира: Pipecat по умолчанию подтверждает конец речи после 0,2 с тишины по VAD и затем спрашивает модель Smart Turn, закончил ли человек мысль; в примере OpenAI для server_vad стоит 500 мс тишины. Поэтому и появились модели конца реплики, которые учитывают смысл и интонацию, а не только паузу: semantic_vad у OpenAI ждёт дольше после незаконченной фразы и отвечает быстрее после законченной, turn detector в LiveKit Agents, Smart Turn в Pipecat, Flux у Deepgram.

Приёмы

  • Стриминг на каждом шаге. STT отдаёт частичные гипотезы, LLM — токены, TTS принимает текст по фразам и отдаёт звук чанками. Без этого задержки этапов складываются целиком, и это первый рычаг по силе.
  • Спекулятивный старт. LLM запускается на ранней гипотезе конца реплики (EagerEndOfTurn у Deepgram Flux) и отменяется, если пользователь продолжил (TurnResumed). Выигрыш — часть endpointing; цена — лишние вызовы: Deepgram предупреждает, что ранний конец реплики может увеличить число вызовов LLM на 50–70%. Звук при этом не играет, пока конец реплики не подтверждён. В LiveKit Agents есть похожая настройка — preemptive generation.
  • Короткая первая фраза. Промпт требует, чтобы первая фраза была короткой и сразу по делу (см. VoiceSystem ниже). TTS стартует после первой фразы, и 6 токенов вместо 20 экономят сотни миллисекунд.
  • Филлер. «Секунду, смотрю заказ» из кэша TTS, пока работает инструмент или поиск. Он маскирует ожидание, но не сокращает его, а на каждом ходу раздражает. Включайте его по событию «ожидается долгий шаг».
  • Кэш TTS. Приветствие, подтверждения, филлеры и частые ответы синтезируются заранее. Ключ кэша — текст, голос и параметры синтеза.
  • Тёплые соединения. WebSocket к STT и TTS открыт на весь звонок. TLS-рукопожатие на каждом ходу — это лишние RTT.
  • Один регион. STT, LLM, TTS и оркестратор стоят рядом. Каждый межконтинентальный вызов внутри хода добавляет сотни миллисекунд.
  • Модель под голос. Отвечает быстрая модель, а сложный вопрос получает «дайте подумать» и вызов более сильной модели как инструмента.

Бюджет латентности голосового хода

От момента, когда пользователь замолчал, до первого звука ответа в его динамике. Двигайте длительности этапов, включайте приёмы и сравнивайте каскад со speech-to-speech. Длительности — порядок величин для экспериментов, а не бенчмарк; аудиостек клиента взят по таблице из Voice AI primer. Свои цифры берите из трейсов.

Как мерить

  • Спаны на каждый сегмент в трейсе хода (модуль 9): endpoint, stt.final, llm.first_token, tts.first_chunk, playback.start. Смотрите p50 и p95 каждого, а не среднее: в голосе заметен именно хвост.
  • Запись разговора. Серверные метки не видят аудиостек клиента и сеть. Настоящую voice-to-voice латентность меряют по стереозаписи (пользователь и агент на разных каналах): расстояние от конца речи пользователя до начала речи агента. 10–20 записанных звонков ловят то, чего не видно в трейсах.
  • Сегменты не всегда складываются. При спекулятивном старте и параллельном retrieval сумма длительностей больше итоговой задержки. Отчитывайтесь и по сегментам, и итогом.
Аналогия из GoБюджет хода устроен как SLO цепочки RPC в Go-сервисе: p95 суммы не равен сумме p95. Если пять сегментов независимо попадают в свой хвост в 5% случаев, хотя бы один хвост случится почти в каждом четвёртом ходе (1 − 0,95⁵ ≈ 23%). Поэтому бюджет задают на итог (p95 до первого звука), а по сегментам ищут, кто его съедает.

Barge-in: перебивание

Barge-in — пользователь начинает говорить, пока агент ещё отвечает. Люди делают это постоянно: уточняют, поправляют, говорят «нет-нет, мне другое». Агент, который не умеет замолкать, договаривает 15 секунд в пустоту, а пользователь повторяет громче. Задача распадается на пять шагов.

  1. Обнаружить речь пользователя во время собственного ответа: VAD на микрофоне работает и тогда, когда говорит агент.
  2. Подтвердить, что это перебивание, а не шум: минимальная длительность речи, минимальное число распознанных слов, классификатор «перехват хода или поддакивание».
  3. Отменить всё, что ещё в работе: генерацию LLM, синтез TTS и, главное, звук, уже лежащий в буферах.
  4. Обрезать историю до фактически произнесённого.
  5. Слушать новую реплику как обычный ход.

Что отменять: звук в буферах

К моменту перебивания LLM обычно уже дописала ответ, TTS синтезировала его быстрее реального времени, а сервер отправил клиенту звук на секунды вперёд. Остановить генерацию мало: пользователь продолжит слышать буфер. Звук нужно останавливать там, где он играет.

  • WebRTC и SIP: сервер знает, сколько проиграно. Realtime API OpenAI в этих режимах сам обрезает непроигранный звук при перебивании.
  • WebSocket: воспроизведением управляет клиент, поэтому он же должен остановить звук и сообщить, сколько успело прозвучать. У OpenAI это событие conversation.item.truncate с audio_end_ms: оно отрезает непроигранный звук и соответствующую часть транскрипта.
  • Телефония: в Twilio Media Streams сообщение clear сбрасывает буфер звука, а метки mark показывают, какие куски доиграли. После clear Twilio возвращает метки непроигранного, и вы точно знаете, что пользователь не услышал.

Точность обрезки ограничена выравниванием текста и звука. TTS с таймкодами слов позволяет резать по слову, без них — по чанку или приблизительно; OpenAI прямо пишет, что realtime-модель не может точно выровнять транскрипт и звук. Для истории точности до слова хватает.

Результаты инструментов остаются в истории независимо от обрезки речи: состояние мира и сказанное вслух — разные вещи. Для действий с побочными эффектами нужны подтверждение до вызова и ключи идемпотентности (модуль 6).

Ложные срабатывания

  • Эхо: голос агента из динамика возвращается в микрофон, и агент перебивает сам себя. Лечится acoustic echo cancellation (AEC, подавление акустического эха); в браузере это ограничение echoCancellation в getUserMedia. На громкой связи без AEC barge-in не работает в принципе.
  • Шум: кашель, хлопнувшая дверь, разговор в комнате. Помогают порог минимальной длительности речи и шумоподавление до VAD: документация Pipecat советует чистить вход фильтром, а не только поднимать пороги.
  • Поддакивание (backchannel): «угу», «да-да», «так» означают «продолжай», а не перехват хода. Помогают порог минимального числа слов (в LiveKit Agents — min_words) или классификатор.
  • Ложное перебивание: VAD сработал, а STT не вернул ни слова. В LiveKit Agents это отдельное событие, и по умолчанию агент продолжает говорить с того места, где остановился.

Компромисс тот же, что у endpointing. Строгие фильтры — и агент реагирует медленнее, иногда договаривая поверх человека. Мягкие — и он замолкает от каждого шороха. Удобный приём — двухступенчатая реакция: по сигналу VAD сразу приглушить звук или поставить его на паузу, а отменять ответ, только когда STT подтвердил слова.

Конвейер голосового хода на Go

Каскад естественно ложится на Go: этап — горутина, стрим — канал, отмена — context. Полный код с тестами лежит в examples/m16-voice. Внешние API не нужны: провайдеры заменены фейками с настраиваемыми задержками, а Claude-звено вынесено в отдельный адаптер.

  • Четыре этапа: пересылка аудио в STT с меткой конца речи; LLM → нарезка на фразы; фразы → TTS; воспроизведение. Буфер канала позволяет TTS синтезировать следующую фразу, пока звучит текущая.
  • Одна отмена на ход: context.WithCancelCause. Причина ErrBargeIn отличает перебивание от ухода клиента или ошибки TTS.
  • Правило дренажа: после отмены каждый этап всё равно дочитывает входной канал до закрытия. Поэтому к концу Turn все горутины гарантированно завершены, а метки времени читаются без гонок: закрытие канала — граница happens-before.
  • История получает только чанки, которые Player доиграл целиком.
type Transcript struct {
	Text  string
	Final bool // false — частичная гипотеза, ещё может измениться
}

// Chunk — кусок синтезированного звука и текст, который в нём звучит
// (выравнивание: многие TTS-API отдают таймкоды слов или символов).
type Chunk struct {
	Audio []byte
	Text  string
	Dur   time.Duration
}

// Контракт всех реализаций: выходной канал закрывается в конце и при отмене ctx,
// отправка в канал всегда через select с ctx.Done() — иначе отмена оставит висящие горутины.
// ponytail: ошибки посреди стрима не передаются, в проде — поле Err в событии.
type STT interface {
	Stream(ctx context.Context, audio <-chan []byte) (<-chan Transcript, error)
}

type LLM interface {
	Stream(ctx context.Context, history []Message) (<-chan string, error)
}

type TTS interface {
	Stream(ctx context.Context, text string) (<-chan Chunk, error)
}

// Player проигрывает чанк и возвращает nil, только если чанк прозвучал целиком.
type Player interface {
	Play(ctx context.Context, c Chunk) error
}

// Timings — латентность, отсчитанная от конца речи пользователя.
type Timings struct {
	STT         time.Duration // финальный транскрипт (endpointing + финализация)
	LLM         time.Duration // первый токен ответа
	TTS         time.Duration // первый чанк синтезированного звука
	Audio       time.Duration // начало воспроизведения: voice-to-voice без сети и аудиостека
	Interrupted bool
}
var (
	ErrBargeIn  = errors.New("voice: пользователь перебил")
	ErrNoSpeech = errors.New("voice: нет финального транскрипта")
)

type Agent struct {
	STT     STT
	LLM     LLM
	TTS     TTS
	Player  Player
	History []Message
}

// Turn проводит один ход. audio закрывается, когда пользователь замолчал (VAD);
// сигнал в bargeIn означает, что пользователь заговорил во время ответа.
func (a *Agent) Turn(ctx context.Context, audio <-chan []byte, bargeIn <-chan struct{}) (Timings, error) {
	var tm Timings
	ctx, cancel := context.WithCancelCause(ctx)
	defer cancel(nil)

	// Пересылаем аудио в STT и запоминаем момент конца речи — точку отсчёта бюджета.
	in, ended := make(chan []byte), make(chan time.Time, 1)
	go func() {
		defer close(in)
		for f := range audio {
			select {
			case in <- f:
			case <-ctx.Done():
				return
			}
		}
		ended <- time.Now()
	}()

	transcripts, err := a.STT.Stream(ctx, in)
	if err != nil {
		return tm, err
	}
	var user string
	for t := range transcripts {
		if t.Final {
			user = t.Text
			break
		}
	}
	sttAt := time.Now()
	if user == "" {
		return tm, errors.Join(ErrNoSpeech, context.Cause(ctx))
	}
	t0 := sttAt // финал пришёл раньше конца аудио (eager endpointing)
	select {
	case t0 = <-ended:
	default:
	}

	a.History = append(a.History, Message{Role: "user", Text: user})
	deltas, err := a.LLM.Stream(ctx, a.History)
	if err != nil {
		return tm, err
	}

	// Barge-in: одна отмена останавливает LLM, TTS и воспроизведение сразу.
	go func() {
		select {
		case <-bargeIn:
			cancel(ErrBargeIn)
		case <-ctx.Done():
		}
	}()

	// LLM → предложения: TTS стартует на первой фразе, а не на всём ответе.
	sentences := make(chan string, 4)
	var llmAt time.Time
	go func() {
		defer close(sentences)
		var buf string
		for d := range deltas {
			if llmAt.IsZero() {
				llmAt = time.Now()
			}
			buf += d
			if s, rest, ok := cutSentence(buf); ok {
				select {
				case sentences <- s:
				case <-ctx.Done():
					return
				}
				buf = rest
			}
		}
		if s := strings.TrimSpace(buf); s != "" && ctx.Err() == nil {
			sentences <- s
		}
	}()

	// Предложения → звук. Синтез идёт быстрее реального времени, буфер chunks
	// даёт TTS работать над следующей фразой, пока звучит текущая.
	chunks := make(chan Chunk, 8)
	var ttsAt time.Time
	go func() {
		defer close(chunks)
		for s := range sentences {
			if ctx.Err() != nil {
				continue // дочитываем канал, чтобы этап выше завершился
			}
			stream, err := a.TTS.Stream(ctx, s)
			if err != nil {
				cancel(err)
				continue
			}
			for c := range stream {
				if ttsAt.IsZero() {
					ttsAt = time.Now()
				}
				select {
				case chunks <- c:
				case <-ctx.Done():
				}
			}
		}
	}()

	// Воспроизведение. Канал дочитывается до закрытия даже после отмены:
	// так все горутины гарантированно завершились до чтения llmAt и ttsAt.
	var spoken []string
	var audioAt time.Time
	cut := false // часть ответа не прозвучала
	for c := range chunks {
		if ctx.Err() != nil {
			cut = true
			continue
		}
		if audioAt.IsZero() {
			audioAt = time.Now()
		}
		if a.Player.Play(ctx, c) != nil { // недоигранный чанк в историю не попадает
			cut = true
			continue
		}
		spoken = append(spoken, strings.TrimSpace(c.Text))
	}

	// В историю — только произнесённое: модель не должна «помнить», что сказала то,
	// чего пользователь не услышал.
	tm.Interrupted = errors.Is(context.Cause(ctx), ErrBargeIn)
	if text := strings.Join(spoken, " "); text != "" {
		if cut {
			text += "…"
		}
		a.History = append(a.History, Message{Role: "assistant", Text: text, Interrupted: cut})
	}
	since := func(t time.Time) time.Duration {
		if t.IsZero() {
			return 0
		}
		return t.Sub(t0)
	}
	tm.STT, tm.LLM, tm.TTS, tm.Audio = since(sttAt), since(llmAt), since(ttsAt), since(audioAt)
	if err := context.Cause(ctx); err != nil && !tm.Interrupted {
		return tm, err
	}
	return tm, nil
}
// bargePlayer доигрывает after чанков, а на следующем «слышит» пользователя и ждёт отмены.
type bargePlayer struct {
	after, n int
	bargeIn  chan struct{}
}

func (p *bargePlayer) Play(ctx context.Context, c Chunk) error {
	if p.n == p.after {
		close(p.bargeIn)
		<-ctx.Done()
		return context.Cause(ctx)
	}
	p.n++
	return nil
}

// Claude — LLM-звено каскада поверх стримингового Messages API.
type Claude struct {
	Client anthropic.Client
	Model  string // в голосе важнее TTFT: маленькая модель, например "claude-haiku-4-5"
}

func (c Claude) Stream(ctx context.Context, history []Message) (<-chan string, error) {
	msgs := make([]anthropic.MessageParam, 0, len(history))
	for _, m := range history {
		b := anthropic.NewTextBlock(m.Text)
		if m.Role == "assistant" {
			msgs = append(msgs, anthropic.NewAssistantMessage(b))
		} else {
			msgs = append(msgs, anthropic.NewUserMessage(b)) // подряд идущие user-сообщения API склеит
		}
	}
	stream := c.Client.Messages.NewStreaming(ctx, anthropic.MessageNewParams{
		Model:     c.Model,
		MaxTokens: 300,
		System:    []anthropic.TextBlockParam{{Text: VoiceSystem}},
		Messages:  msgs,
	})
	out := make(chan string)
	go func() {
		defer close(out)
		defer stream.Close()
		for stream.Next() {
			if d, ok := stream.Current().AsAny().(anthropic.ContentBlockDeltaEvent); ok {
				if t, ok := d.Delta.AsAny().(anthropic.TextDelta); ok && !send(ctx, out, t.Text) {
					return // barge-in: отмена ctx закрывает HTTP-стрим, генерация останавливается
				}
			}
		}
		// ponytail: stream.Err() теряется по контракту интерфейса; в проде — лог и метрика.
	}()
	return out, nil
}

Тесты работают в testing/synctest: время внутри «пузыря» фейковое, поэтому латентность проверяется точными значениями. Например, 30 мс endpoint + 40 мс TTFT + две паузы между словами по 20 мс + 15 мс до первого звука TTS дают начало воспроизведения ровно на 125 мс, а без нарезки на фразы было бы 205 мс. Горутина, которая не отреагировала на отмену, роняет тест как deadlock — бесплатная проверка утечек, которую трудно получить с настоящими часами.

Контракт каналовКаждая реализация STT, LLM и TTS обязана отправлять в канал через select с ctx.Done() и закрывать канал при отмене. Реализация, которая пишет в канал без select, после barge-in навсегда повиснет на отправке. Это утечка горутины на каждый перебитый ход, а у голосового сервиса перебитых ходов тысячи в час.

Телефония

Звонок с обычного телефона приходит через SIP-транк (Twilio и аналоги) на ваш медиасервер или сразу к провайдеру: Realtime API OpenAI принимает SIP-звонки и сообщает о входящем вебхуком. Что меняется:

  • Узкая полоса: G.711 μ-law, 8 кГц, именно так Twilio отдаёт звук в Media Streams. WER на таком звуке хуже, чем на 16 кГц из браузера, поэтому STT тестируйте на телефонных записях, а не на студийных.
  • Латентность: телефонная сеть съедает часть бюджета, запас меньше, чем в браузере.
  • DTMF: тональный набор надёжнее голоса для номеров и PIN. Номер карты вообще не должен попадать в LLM и логи (PCI DSS): его собирают DTMF-ом в обход агента.
  • Перевод на оператора — штатный сценарий, а не авария: звонок переводится вместе с кратким резюме разговора.

Где держать состояние

  • Звонок закреплён за процессом. Медиапоток, VAD, текущий ход, позиция воспроизведения и история живут в памяти одного воркера на всё время звонка, как sticky-сессия WebSocket. Мощность планируют в одновременных звонках на воркер, а не в RPS.
  • Долговечное — асинхронно наружу. Транскрипты, вызовы инструментов и их результаты пишутся в журнал событий или БД, не блокируя ход. Падение воркера рвёт звонок, а восстановление — это переподключение с историей из хранилища.
  • Граница стейтфул и стейтлесс. Голосовой оркестратор стейтфул, а всё за ним устроено как в текстовом агенте: RAG-сервис проекта A, инструменты и LLM-шлюз (модуль 9) остаются стейтлесс.

Tool use голосом

  • Ожидание. Инструмент на 2 секунды — это 2 секунды тишины. Филлер запускается параллельно с инструментом («Секунду, смотрю заказ»), а долгую операцию лучше сделать асинхронной: «пришлю SMS, когда будет готово».
  • Подтверждение голосом перед действием с побочным эффектом: агент перечитывает ключевые параметры («Переношу доставку на пятницу, 16 октября, с десяти до двух. Подтверждаете?») и ждёт явного «да». STT ошибается в числах и именах, и это перечитывание — ваша проверка.
  • Числа и имена. Просите продиктовать по цифрам и повторяйте для подтверждения, а для чувствительного используйте DTMF или код из SMS.
  • Формат ответа. Никакого markdown, ссылок и списков, иначе TTS прочитает «звёздочка, звёздочка». Источники RAG озвучиваются названием раздела, а ссылка уходит в SMS или чат (промпт под TTS — модуль 3).
  • Безопасность. Голос — не аутентификация: его клонируют. Голосовая инъекция («игнорируй инструкции») — та же прямая инъекция, поэтому права проверяются в инструментах (модуль 7).

Evals и наблюдаемость голосовых агентов

Голосового агента проверяют на четырёх уровнях: качество каждого звена, ход разговора, решение задачи и впечатление человека.

WER (word error rate) = (S + D + I) / N: замены, удаления и вставки слов относительно эталона из N слов (см. разбор суммаризации звонков в модуле 12; в Python его считает библиотека jiwer). Подвохов два. Первый — нормализация: «25» и «двадцать пять», регистр, пунктуация. Без единой нормализации эталона и гипотезы WER мерит форматирование, а не распознавание. Второй — веса: ошибка в номере заказа или фамилии ломает задачу, а в «ну вот» — нет, поэтому рядом с WER считайте точность сущностей.

Авторы primer'а советуют следить за двумя метриками перебиваний: агента перебивают чаще, когда ответы слишком длинные, а сам агент перебивает людей, когда endpointing слишком агрессивен. Обе метрики — прямые рычаги настройки.

Симуляция звонков. LLM играет звонящего по сценарию (цель, характер, манера перебивать), его реплики озвучивает TTS, иногда с шумом и акцентом. Ваш агент разговаривает с ним через весь голосовой стек, а судья оценивает транскрипт по рубрике. Это регрессионный набор для голоса: прогон перед каждым изменением промпта, модели или порогов VAD (модуль 8). Для исследований turn-taking есть академические бенчмарки, например Full-Duplex-Bench.

Наблюдаемость. Трейс на ход со спанами сегментов из урока о латентности и событиями barge-in: когда случилось, ложное или нет, сколько слов успело прозвучать. Звук записывается только по согласию и с политикой хранения. Запись голоса — персональные данные, а если голос используется для идентификации человека, то и биометрические, с отдельными требованиями. Что именно применимо к вашей системе, определяет юрист (модуль 11).

Самопроверка

Почему «сколько позиций в накладной?» — плохой вопрос к VLM и как его переформулировать?

Счёт объектов у VLM приблизителен, особенно для множества мелких элементов, и ошибка не видна по ответу. Попросите список позиций по JSON-схеме и посчитайте их в коде; заодно сверьте сумму позиций с итогом документа. Модель переписывает, код считает и проверяет.

Вы отправили скан 4000×3000 px с мелким текстом. Что произойдёт и что делать?

Изображение уменьшится до лимита модели (по длинной стороне 1568 px на стандартном уровне, 2576 px на высоком), мелкий текст станет нечитаемым, а модель всё равно уверенно его «прочитает». Нужно резать страницу на фрагменты или кадрировать нужную область и выбирать разрешение по eval, на котором видна кривая «качество / стоимость».

Когда классический OCR-пайплайн лучше VLM?

Большие объёмы чистой печати (дёшево, быстро, CPU), когда нужны координаты и уверенность по каждому символу, детерминизм и аудит, работа офлайн. VLM сильнее на сложной вёрстке, таблицах, графиках, смешанных и новых форматах и там, где нужен смысл. Частый компромисс — гибрид: OCR-текст плюс изображение страницы в VLM и сверка между ними.

Чем каскад отличается от speech-to-speech по контролю и логированию?

В каскаде на каждом шаге есть текст: можно применить guardrails и PII-редакцию до озвучки, сохранить транскрипт и ответ, прогнать обычные текстовые evals, заменить любое звено. В S2S аудио идёт в модель и из модели напрямую, транскрипция — побочная и не всегда надёжна, проверить ответ до того, как он прозвучал, сложнее, а провайдер один.

Из каких сегментов складывается voice-to-voice латентность и какой из них чаще всего забывают?

Аудиостек и сеть вверх, endpointing, финализация STT, TTFT LLM, генерация первой фразы, TTS до первого звука, сеть вниз и воспроизведение. Забывают endpointing: ожидание тишины в сотни миллисекунд не видно в спанах STT и LLM, хотя часто это крупнейший сегмент.

Что даёт спекулятивный старт LLM и чем за него платят?

LLM начинает отвечать на ранней гипотезе конца реплики, и ответ готов к моменту подтверждения, что экономит часть endpointing. Платят лишними вызовами: если пользователь продолжил, черновик отменяется (Deepgram оценивает прирост вызовов LLM в 50–70%). Звук до подтверждения не играет, иначе агент будет перебивать.

Что должно попасть в историю после barge-in и почему не весь ответ?

Только фактически прозвучавшая часть с отметкой обрыва. Если записать весь сгенерированный ответ, модель будет считать, что пользователь слышал то, чего он не слышал (окно доставки, цену), и сошлётся на это позже. Результаты уже вызванных инструментов при этом остаются: действие произошло независимо от того, услышал ли пользователь подтверждение.

Почему при barge-in мало остановить генерацию LLM?

К моменту перебивания текст обычно уже сгенерирован, TTS синтезировал звук быстрее реального времени, а сервер отправил клиенту секунды аудио вперёд. Остановить нужно воспроизведение там, где оно идёт: на клиенте, в медиасервере или у телефонного провайдера (clear в Twilio, truncate в Realtime API OpenAI для WebSocket).

Назовите три источника ложных перебиваний и защиту от каждого.

Эхо собственного голоса агента — AEC. Шум и кашель — порог минимальной длительности речи, шумоподавление до VAD, продолжение фразы, если STT не вернул слов. Поддакивание «угу» — минимальное число слов или классификатор перехвата хода.

Почему между клиентом и сервером обычно WebRTC, а между сервером и STT/TTS-провайдером — WebSocket?

На последней миле теряются пакеты и скачет задержка: WebRTC поверх UDP с jitter buffer и Opus деградирует плавно, а в браузере даёт AEC и шумоподавление из коробки. Внутри дата-центра сеть стабильная, и простота WebSocket поверх TCP перевешивает: head-of-line blocking там почти не проявляется.

Вопросы с собеседований

Спроектируйте голосового ассистента записи к врачу для сети клиник: телефон, 5 000 звонков в день.

Требования. Сценарии: запись, перенос, отмена, вопросы о подготовке к приёму. Канал — телефон. Целевые метрики, о которых договариваемся с бизнесом: p95 до первого звука в пределах полутора секунд, доля звонков без оператора, ноль записей без явного подтверждения. Нагрузка небольшая: 5 000 звонков по 3 минуты — это десятки одновременных звонков в пик, планирование мощности ведём в одновременных звонках.

Архитектура. Каскад: SIP-транк → оркестратор (Pipecat, LiveKit Agents или свой на Go) → стриминговый STT с моделью конца реплики → быстрая LLM с инструментами find_slots, book, cancel → TTS с кэшем частых фраз. Каскад, а не S2S, потому что здесь критичны инструменты и подтверждения, нужен текст для аудита, evals и PII-редакции. Все сервисы в одном регионе, соединения к STT и TTS открыты на весь звонок.

Диалог. Barge-in с фильтром ложных срабатываний. Подтверждение перед записью: агент перечитывает врача, дату и время и ждёт явного «да». Фамилию и дату рождения просит продиктовать и повторяет. Пока ищутся слоты — филлер. Перевод на регистратуру с резюме разговора — штатный путь при неуверенности или по просьбе.

Данные. Медицинские и персональные данные: минимизация того, что попадает в LLM и логи, запись звонков по согласию, сроки хранения, разграничение доступа к записям. Конкретные требования определяет юрист.

Evals и эксплуатация. WER и точность сущностей на телефонных записях с фамилиями врачей и медицинскими терминами; симуляция звонков по сценариям как регрессия перед каждым изменением; task success — запись создана верно; в проде — p95 по сегментам, доли ложных перебиваний и переводов на оператора, выборочное прослушивание.

На что смотрит интервьюер: обоснован ли выбор каскада или S2S, а не просто назван; есть ли бюджет латентности по сегментам; подумал ли кандидат о перебивании, подтверждении действий и ошибках STT в именах и датах; есть ли путь к человеку и план evals на телефонном звуке.

Пользователи жалуются, что голосовой агент «тормозит». Как найдёте причину и что сделаете?

Сначала измерить. Трейс хода со спанами по сегментам и p50/p95 каждого, плюс 10–20 стереозаписей звонков, чтобы увидеть реальную voice-to-voice латентность вместе с сетью и аудиостеком клиента.

Типичные находки по частоте: консервативный endpointing (500–800 мс тишины на каждом ходу); TTS ждёт весь ответ, а не первую фразу; длинный TTFT из-за последовательного retrieval, включённого thinking, большой модели или длинного системного промпта без кэша; холодные соединения к STT и TTS на каждом ходу; сервисы в разных регионах; долгие инструменты без филлера.

Лечение по сегментам: модель конца реплики вместо голой тишины, стриминг по фразам и короткая первая фраза, быстрая модель и prompt caching, параллельный retrieval, тёплые соединения, один регион, филлер на долгие шаги. Каждое изменение проверяем A/B: латентность против доли перебиваний агентом и task success, чтобы ускорение не превратилось в агента, который перебивает людей.

На что смотрит интервьюер: начинает ли кандидат с измерений, а не с «поставим модель побыстрее»; помнит ли про endpointing и запись на клиенте; понимает ли, что p95 важнее среднего; видит ли компромисс между скоростью и перебиваниями.

Каскад или speech-to-speech для голосового ассистента банка? Обоснуйте.

Каскад, и причины в требованиях банка, а не во вкусе. Нужен текст на каждом шаге: аудит, PII-редакция до хранения, guardrails и проверка политики до озвучки. Нужны надёжные инструменты с подтверждением операций, а S2S-модели, по наблюдениям практиков, вызывают инструменты менее надёжно, чем текстовые. Нужны текстовые evals и регрессия в CI. И нужна возможность заменить вендора любого звена.

Где S2S мог бы выиграть: естественность и эмоции, смешанная речь. Это реальные плюсы, но для банка они вторичны. Возможен гибрид, но действия всё равно остаются за детерминированным кодом с подтверждением. Решение я бы пересматривал раз в полгода прогоном одних и тех же сценариев на обоих вариантах: рынок S2S быстро меняется.

На что смотрит интервьюер: выводит ли кандидат выбор из требований (аудит, комплаенс, tool use, evals), а не из «S2S быстрее»; знает ли сильные стороны S2S; предлагает ли проверяемый критерий пересмотра решения.

Агент перебивает пользователей, а пользователи постоянно перебивают агента. Что настраивать?

Это две разные проблемы с разными рычагами, и обе нужно сначала измерить по событиям VAD и записям.

Агент перебивает людей — слишком ранний endpointing: человек задумался, а тишина уже засчитана как конец реплики. Решения: модель конца реплики, которая учитывает смысл (после «мой номер…» ждать дольше), адаптивный порог, более длинная пауза после незаконченной фразы.

Люди перебивают агента — ответы слишком длинные или неуместные. Решения: короче ответы и первая фраза по делу, без монологов и перечислений, уточняющий вопрос вместо лекции. Отдельно проверить ложные перебивания (эхо, «угу», шум): если агент замолкает от поддакивания, пользователи не перебивают, а агент сам обрывается.

Метрики после изменений: обе доли перебиваний, латентность до первого звука и task success. Ускорение endpointing почти всегда увеличивает первую долю, поэтому ищем точку компромисса, а не минимум одной метрики.

На что смотрит интервьюер: различает ли кандидат две проблемы; знает ли про модели конца реплики и ложные перебивания; предлагает ли метрики и компромисс, а не один «правильный» порог.

Как вы реализуете barge-in в Go-сервисе и как это протестируете?

Этапы — горутины, стримы — каналы, на ход — один context.WithCancelCause. Сигнал VAD о речи пользователя вызывает cancel(ErrBargeIn), и отмена останавливает LLM-стрим (закрывается HTTP-соединение), синтез TTS и воспроизведение. Все реализации отправляют в каналы через select с ctx.Done(), а каждый этап дочитывает свой вход до закрытия. Так к концу хода все горутины завершены, а гонок по общим меткам нет.

Плеер возвращает успех, только если чанк прозвучал целиком; чанк несёт текст, который в нём звучит (выравнивание от TTS). В историю попадает текст доигранных чанков с отметкой обрыва. Если звук играет на клиенте, клиент сообщает, сколько проиграно. Результаты вызванных инструментов из истории не удаляются.

Тесты: фейковые STT, LLM и TTS с задержками и фейковый плеер, который на N-м чанке сигналит barge-in. Проверяем историю, флаг перебивания и то, что перебивание до первого звука не оставляет ответа в истории. Гоняем в testing/synctest: фейковое время даёт точные латентности, а зависшая горутина роняет тест как deadlock. Плюс -race.

На что смотрит интервьюер: понимает ли кандидат, что останавливать нужно воспроизведение, а не только генерацию; как он обрезает историю; знает ли контракт каналов и отмены; умеет ли тестировать конкурентный код детерминированно, без time.Sleep и флаков.

Нужно извлекать поля из миллиона сканов счетов в месяц. VLM или OCR? Посчитайте.

Расчёт VLM. Страница на стандартном уровне разрешения — до ~1,5K визуальных токенов, плюс ~500 токенов промпта и ~300 токенов JSON на выходе. На Haiku 4.5 ($1/$5): 2K × $1/1M + 300 × $5/1M ≈ $0.0035 за страницу, ≈ $3.5K в месяц, через Batch API (−50%, никто не ждёт интерактивно) ≈ $1.75K. На Opus 5 ($5/$25) с высоким разрешением (до ~4,8K токенов на страницу) — до ≈ $0.034 за страницу, ≈ $34K в месяц, через Batch ≈ $17K. Модель выбирается по eval, а не по цене заранее.

Архитектура. Маршрутизация: цифровые PDF с текстовым слоем разбираются без VLM. Сканы идут в VLM по JSON-схеме или в гибрид «OCR + VLM» со сверкой. Обязательная валидация: суммы сходятся, даты и реквизиты корректны. Провал валидации → повтор с кропом в большем разрешении → очередь на человека. Идемпотентная запись результата по custom_id.

Качество. Размеченный набор из реальных сканов по слоям качества; точность по полям и доля документов без ошибок; прогон на нескольких разрешениях для выбора даунскейла; доля ручной проверки как метрика стоимости и дрейфа.

На что смотрит интервьюер: есть ли расчёт стоимости с batch и разрешением; предлагает ли кандидат маршрутизацию и гибрид вместо «всё в VLM»; есть ли валидация и путь к человеку; понимает ли, что ошибка в сумме опаснее отказа.

Как оценивать качество голосового агента до релиза и в проде?

По четырём уровням. Звенья: WER с единой нормализацией и точность сущностей на своих записях (телефонный звук отдельно), произношение чисел и имён в TTS, текстовые evals ответов LLM. Ход разговора: p50/p95 по сегментам, доли ложных перебиваний, перебиваний агентом и агента. Задача: task success, доля звонков без оператора, число ходов. Человек: прослушивание выборки по рубрике с калибровкой оценщиков, CSAT.

До релиза — симуляция: LLM играет звонящих по сценариям (включая шум, акценты, перебивания), разговор идёт через весь голосовой стек, судья оценивает транскрипты. Набор сценариев работает как регрессия в CI при изменении промпта, модели, порогов VAD или голоса. После релиза — канареечный запуск с онлайн-метриками и прослушиванием, плохие звонки превращаются в новые сценарии.

На что смотрит интервьюер: не сводит ли кандидат качество к WER; есть ли метрики turn-taking и задачи; есть ли воспроизводимая регрессия через симуляцию; связаны ли офлайн- и онлайн-метрики и цикл «инцидент → новый кейс».
